# 의뢰 접수·저장·이어가기 설계 (총괄 의뢰 자동 넘김, 0단계)

고객사 일반회원이 AI 대화방에서 한 의뢰를 총괄이 받아 알맞은 부서로 넘긴다. 이 문서는 그중 0단계
(저장과 재시작 이어가기)의 설계다. 접수(대화)·분류(LLM)·부서에 시키기는 이후 단계에서 이 기록 위에 붙는다.
조사한 일 목록은 `request-catalog.md`.

## 원칙

- LLM은 "의뢰인지 질문인지 가르고, 어떤 일인지 고르기"만 한다. 접수·저장·전달·검사는 코드가 한다.
- 흐름의 **첫 작업 부서부터** 시키고, 부서 사이 전달은 총괄이 **결과 번호**(`result_ref`)만 넘긴다.
  큰 결과는 부서 저장소에 두고 총괄 기록에는 번호만 둔다.
- 장애 대응 기존 동작은 바꾸지 않는다.

## 저장 항목 (`work_requests` 표, `work_requests.py`)

의뢰 하나가 한 줄(JSON)이다.

| 칸 | 내용 |
| --- | --- |
| `request_id`, `account`, `text` | 의뢰 번호, 의뢰자, 문장 원문(2000자까지) |
| `status` | `received` → `classified` → `running` ⇄ `waiting` → `done`·`failed`·`rejected`·`needs_human` |
| `task`, `confidence`, `reason`, `alternatives` | 고른 일, 확신도, 한 줄 이유, 차선 후보 (분류가 채움) |
| `plan` | 단계 목록 `{step_id, dept, skill, label, after[]}`. `after`는 앞서 끝나야 하는 단계 |
| `steps` | 단계별 진행: `status`, `attempts`, `grade`, `result_ref`, `review_id`, `handoff_task_id`, `async_task_id`, 시각 |
| `log`, `context_id` | 진행 로그, 연결된 이슈 번호 |

일반회원은 자기 의뢰만 본다(`list(account)`). 닫힌 의뢰는 오래된 것부터 1000건을 넘으면 지운다(열린 의뢰는 지우지 않는다).

## 재시작 이어가기

장애 이벤트는 재시작하면 진행 중이던 단계를 "중단됨"으로 닫는다. 의뢰는 닫지 않고 단계 상태별로 이어 간다.

| 단계 상태 | 재시작 뒤 |
| --- | --- |
| `completed`·`failed`·`skipped`·`rejected_by_human` | 그대로 |
| `pending` | 그대로 (선행 단계가 끝났으면 시킬 수 있음: `ready_steps`) |
| `held`·`waiting_human`·`waiting_async` | 그대로. 저장해 둔 번호(`review_id` 등)로 계속 기다림 |
| `running` (부서에 보내던 중) | 읽기(`grade == read`)면 `pending`으로 되돌려 다시 시킴. 그 밖(A·B·C, 등급을 모르는 것)은 이미 처리됐을 수 있어 **다시 보내지 않고** `waiting_human`(이유 `restart_unconfirmed`)으로 사람 확인 |

닫힌 의뢰(`done` 등)는 건드리지 않는다. 정리한 결과는 바로 저장돼 한 번 더 켜도 같은 상태다.
`IncidentManager.restore()`가 `resumed_requests`(복원·열림·다시 시킬 단계·확인 필요 단계 수)를 남긴다.

## 0단계가 하지 않는 것

- 실제로 이어서 시키는 일: 의뢰 실행(2단계)이 `ready_steps`를 보고 한다. 0단계는 기록과 정책까지다.
- 접수 대화와 분류 LLM은 1단계(아래), 화면·API는 이후 단계.

## 1단계: 접수와 분류 (`request_intake.py`, `request_classifier.py`, `request_tasks.py`)

대화로 온 글을 먼저 분류기가 본다(`chat/turn.py`의 `_try_intake`). 한 글에 LLM을 한 번 부른다.

| 결과 | 하는 일 |
| --- | --- |
| 질문 / 분류 못 함(LLM 설정 없음·실패·시간 초과) | 아무것도 기록하지 않고 기존 설명 대화로 보낸다 |
| 일을 정함(`task`) | 의뢰 기록을 만들고 일 목록의 계획을 붙인다(`classified`). 접수 안내를 하고 실행(2단계)을 시작한다. 실행할 준비가 안 된 일(`blocked_by`)은 접수만 한다 |
| 일을 못 정함(`clarify`) | 되묻는다. 기록은 `received`로 둔다 |
| 목록에 맞는 일이 없음(`unknown`) | 담당 불명으로 사람에게(`needs_human`) |
| 위험·권한 밖(`rejected`) | 거절하고 기록한다. 이유는 고객에게 보이지 않는다 |
| 같은 사람이 같은 글을 10분 안에 다시 | 중복으로 돌려주고 LLM을 부르지 않는다 |
| 하루 20건 초과 | 한도 안내 |

- LLM은 일 목록에서 **고르기만** 한다. 출력은 정해진 모양(`Classification`: kind·task·confidence·reason·alternatives·question)이고,
  코드가 목록에 없는 일 이름을 버리고(`unknown`), 확신이 `CONFIDENCE_MIN`(0.6) 미만이면 되묻고, 범위(0~1)를 맞춘다.
- 고객 글은 지시문이 아니라 데이터 블록(`untrusted`)으로만 넣는다. LLM이 쓴 이유·되묻는 말은 길이를 자르고, 링크가 있으면 기본 문장으로 바꾼다.
  부서에는 고객 원문만 간다.
- 일 목록(`request_tasks.TASKS`)은 18개: 흐름 1(홍보 영상) + 단독 의뢰 17(읽기 15 + 상태 변경 2). 부서 카드의 skill·등급·
  `allowed_requesters`와 맞는지 시험이 확인한다.
- 숫자 칸에 최소·최대(`ge`/`le`)를 쓰면 제공사가 스키마를 거절한다(400). 실제 호출로 확인했고, 범위는 코드가 맞춘다.
- 분류 결과(지시문 버전·종류·확신도·이유·차선 후보)는 기록(`classification`)에 남겨 17번 정확도 평가에 쓴다.

## 2단계: 순서대로 시키기 (`request_runner.py`)

장애용 엔진(`engine.py`)은 이벤트 전제라 건드리지 않고, 의뢰 기록 위에서 도는 실행기를 따로 둔다.
부서를 찾고 부르는 길(레지스트리·호출기)은 엔진의 것을 쓴다. LLM은 부르지 않는다.

| 하는 일 | 방식 |
| --- | --- |
| 첫 부서 시키기(7) | 접수가 일을 정하면 실행기가 뒤에서 시작한다. 시킬 수 있는 단계(`ready_steps`)부터, 앞 단계가 성공해야 뒤 단계를 시킨다. 고객 글은 부서에 `untrusted` 칸으로만 간다 |
| 실패 | 읽기 단계만 실패 2회·마감 초과 1회 다시 부른다. 앞 단계가 끝나지 못하면 뒤 단계는 건너뜀 |
| 결과 번호(8) | 부서 결과에서 일 목록이 정한 칸(`ref_key`, 예: `report_id`)의 번호만 `result_ref`에 둔다. 번호 모양(영문·숫자·`_:.-`, 80자)이 아니면 버린다. 다음 단계(`takes_ref`)에는 번호만 입력으로 넘기고 본문·문장은 넘기지 않는다. 번호가 없으면 시키지 않고 실패(`no_ref`) |
| 사람 확인(9) | 사람 확인 단계와 상태를 바꾸는 단계(A·B·C)는 `waiting_human`으로 멈춘다(`human_check`·`needs_approval`). 사람 토큰으로 `POST /api/requests/{id}/steps/{step}/decision`을 부르면 승인은 다음으로 이어지고 거절은 `rejected_by_human`. 승인된 상태 변경도 부서의 안전 관문을 따로 거친다 |
| 의뢰자 알림(9) | 기다림·실패·끝남을 접수한 대화에 정해진 문장 틀로 한 줄 붙인다. 부서가 쓴 문장은 알림에 넣지 않는다 |
| 재시작 | 서버가 켜질 때 시킬 단계가 남은 열린 의뢰를 이어서 시킨다(`resume_open`) |

- 부서가 긴 작업(`working`)이나 사람 승인(`held`)·할 일함으로 넘기면 번호만 적고 멈춘다.
  이어 받기(진행 알림·결정 이벤트로 이어 가기)는 이후 단계다.
- 부서 스킬마다 필요한 입력(기간·캠페인 번호 등)이 달라서, 지금은 고객 글(`untrusted`)과 앞 단계 번호만
  보낸다. 입력이 더 필요한 스킬은 부서가 되묻거나 거절해 단계가 실패로 남는다. 스킬별 입력 만들기는
  이후 단계의 일이다.

## 3단계: 예외 대응 (`request_inbox.py`, 접수·실행기 보강)

의뢰가 멈추지 않고 사람에게 가게 하고, 위험한 글과 바뀐 계획은 부서에 보내지 않는다.

| 경우 | 하는 일 |
| --- | --- |
| 담당 불명(`unknown`) | 의뢰를 `needs_human`으로 닫고 사람 받은 요청(할 일함)에 올린다. 고객에게는 사람이 확인해서 알려 준다고 답한다 |
| 모호함 | 같은 대화에서 **한 번만** 되묻는다(기록 `received`). 되물은 뒤에도 정하지 못하면 `needs_human`으로 사람에게 넘긴다. 되물은 뒤 답해서 일이 정해지면 기다리던 기록은 이어졌다고 닫는다 |
| 단계 실패 | 읽기 단계는 재시도(2회·마감 초과 1회) 뒤에도 실패하면 의뢰를 `needs_human`으로 닫고 실패한 단계와 함께 받은 요청에 올린다. 사람이 거절했거나 앞 단계 때문에 건너뛴 경우는 `failed`(사람에게 다시 올리지 않음) |
| 위험·권한 밖 | 분류가 위험(`unsafe`)이면 실행하지 않고 `rejected`로 기록한다. 이유는 기록에만 남고 고객에게는 보이지 않는다 |
| 일 목록 밖 단계 | 실행기가 단계의 부서·skill이 고른 일의 목록과 같은지, 부서 카드의 부서와 같은지 확인한다. 다르면 어떤 부서에도 보내지 않고 `out_of_scope`/`no_agent`로 닫는다 |

- 받은 요청에는 의뢰 번호·이유·고객 원문(데이터 칸)만 올린다. 같은 의뢰의 같은 이유는 한 번만 올린다.
  올리지 못해도(연결 없음·할 일함 오류) 의뢰 기록에 이유가 남는다. 목 모드는 올리지 않는다.
- **의뢰 속 지시 방어**: LLM이 속아서 상태를 바꾸는 일을 골라도 승인 없이는 부서에 아무것도 가지 않는다
  (시험: 속은 LLM 5문장). LLM이 쓴 이유·차선 후보는 부서로 가지 않고, 부서에는 고객 원문(데이터 칸)과
  앞 단계 결과 번호만 간다.
- 실제 LLM 시범(주입 시도 14문장): 11개는 거절. 3개(환불 접수 2, 기능 요청 1)는 진짜 의뢰 내용이 섞여
  있어 일로 접수됐고, 모두 상태를 바꾸는 일이라 승인 대기에서 멈췄다. 실행된 것은 없다.

## 4단계: 받은 의뢰 화면 (`GET /api/requests`, 총괄 화면 `WorkRequestsCard`)

직원이 총괄 화면에서 의뢰 하나의 진행과 고른 근거를 보고, 확인·승인하고, 잘못 골랐으면 다시 돌린다.
고객 글이 들어 있어 아래 API는 모두 사람 토큰(`require_human`)만 받는다.

| 길 | 하는 일 |
| --- | --- |
| `GET /api/requests` | 접수된 의뢰(최근 것부터 100건)와 고를 수 있는 일 목록(`meta.tasks`) |
| `GET /api/requests/{id}` | 의뢰 하나 |
| `POST /api/requests/{id}/steps/{step}/decision` | 사람 확인·승인 대기 단계를 승인·거절 (2단계에서 만듦) |
| `POST /api/requests/{id}/rerun` `{task}` | 일을 바꿔 다시 돌린다. 계획과 단계 진행은 새로 시작하고, 이전 선택은 `corrections`에 남긴다(17번 정확도 평가의 정답). 부서가 일하는 중이거나 기다리는 단계가 있으면 409 |

- 화면에는 부서가 돌려준 문장이 없다(의뢰 기록에 없다). 상태·번호·정해진 문구와 고객 글(글자 그대로)만 나온다.
- 일반회원이 본인 의뢰만 보는 길은 이번에 하지 않았다. 로그인 세션(역할)이 바뀌는 중이라 다음 PR로
  나눈다(대화방 알림으로는 본인 의뢰 진행을 이미 받는다).
- 14번(대화방·AI 오피스 확인) 결과: 두 화면은 장애 이슈(`incidents`)만 그린다. 의뢰의 부서 간
  넘김은 보이지 않는다. 의뢰를 이슈에 섞으면 장애 통계가 오염돼 이번에는 고치지 않고 따로 설계한다.

## 5단계(일부): 긴 작업 이어받기와 홍보 영상 3단계 (15-2·15-3)

데이터분석의 트렌드 보고서(#1466)는 몇 분 걸리는 긴 작업이다. 총괄이 이어 받는 방법과 홍보 영상 흐름을 맞췄다.

- **긴 작업으로 부르기:** 일 목록의 `trend_report_create` 단계는 입력에 `caller="orchestrator"`와 고객 문장
  (`request_text`)을 넣어 보낸다. `caller`가 `human`(기본)이면 부서가 동기로 끝내 알림이 오지 않는다. 이 부서는
  문장을 `input.request_text`로만 읽는다(`untrusted`는 읽지 않는다). 단계의 `fixed_input`·`text_key`가 이 값이다.
- **알림 받기:** 부서가 `WORKING` + `task_id`로 받으면 단계는 `waiting_async`가 된다. 이벤트 `task.progress`·
  `task.completed`(`context_id`는 의뢰의 `ctx_<의뢰번호>`)가 오면 `manager`가 장애 이벤트가 아닌 것을 의뢰 실행기
  (`RequestRunner.receive_async`)로 넘긴다. 보낸 부서·skill이 맡긴 곳과 다르면 무시한다(위조 방지).
  - 진행: 진행률(%)만 기록하고 부서가 쓴 문장은 옮기지 않는다.
  - 완료(`done`): `output.report_id`를 결과 번호로 읽어 단계를 끝내고 다음 단계를 이어 시킨다. `failed`면 단계 실패.
  - 접수 응답보다 먼저 온 알림은 보관했다가 대기에 오르면 반영한다. 끝난 작업의 되풀이는 반영하지 않는다.
  - 알림이 300초 넘게 없으면(`ASYNC_SILENCE`, 엔진의 기준과 같다) 응답 끊김으로 단계를 실패로 닫고 사람에게 넘긴다.
    서버가 도는 동안 60초마다 점검하고, 다시 켤 때는 침묵 시간을 새로 센다.
  - 다시 켜도 `waiting_async`와 작업 번호가 남아 있어 늦게 온 알림으로 이어 간다.
- **의뢰 상태:** 부서의 긴 작업만 기다릴 때는 `running`(확인 대기가 아니다), 사람 확인·승인을 기다릴 때만 `waiting`.
- **홍보 영상 흐름:** `trend_report_create` → `trend_report_insight`(번호 `report_id`만 받음) → `receive_insight`(A,
  승인) → 사람 확인 → `generate_media`(B). `trend_report_insight`의 결과 중 `insight`만 통째로 다음 단계의 입력이
  된다(그 밖의 결과는 번호만 넘어간다). 이 값은 의뢰 기록의 `carry`에 두었다가 쓰고 나면 지우며, 조회 API에는
  내지 않는다. `receive_insight`가 A 등급이라 `idempotency_key`가 필요하다(`의뢰번호:skill:단계` 그대로).
- **근거가 없을 때:** `insight`가 `null`이거나 `facts`가 비면(기획은 1~12개를 요구) 기획 단계는 승인도 묻지 않고
  `skipped`(`no_insight`)로 닫고, 뒤 단계도 건너뛰며 의뢰는 `needs_human`이 되어 사람 받은 요청에 올라간다. 부서가
  쓴 이유 문장은 옮기지 않는다.
- `blocked_by`를 홍보 영상과 트렌드 보고서에서 뗐다(장치는 남아 있다).
- **아직 안 된 것:** 마지막 `generate_media`는 입력(`post_draft_id`, `scene_template_id` 등)을 만들어 줄 곳이 없어
  승인 뒤 부서가 입력 오류로 돌려준다. 입력 채우기(19번)에서 이어서 한다.

## 5단계(일부): 입력 채우기 (18번, `request_inputs.py`)

부서 skill은 기간·월·시간 구간 같은 구조화된 입력을 요구하는데 총괄은 입력을 비워 보냈다(17번 조사:
입력 없이 도는 단독 의뢰는 5개뿐). 고객 문장의 기간 말을 규칙으로 부서가 받는 값으로 바꾼다.

- **LLM을 쓰지 않는다.** 정규식 규칙이고 결과는 부서가 받는 값의 모양뿐이다. 고객 문장은 지시가 아니라
  기간 말·숫자를 찾는 데이터로만 읽는다. 날짜는 서울 시간 기준이다. 일 목록의 단계 `fill`에 규칙 이름을 적는다.
- **규칙(일 → 부서 입력):**

  | 규칙 | 일 | 입력 | 말 → 값 |
  | --- | --- | --- | --- |
  | `sales_period` | 매출 분석 | `period` | 오늘 → `today`, 이번 주·7일 → `7d`, 이번 달·30일 → `30d`, 말이 없으면 부서 기본(7일) |
  | `closing_period` | 손익 정리 | `period`+`date` | 이번 달·지난달·N월 → month, 이번 주·지난주 → week, 어제 → day, 말이 없으면 오늘 하루 |
  | `month_upcoming` | 이벤트 제안 | `month` | 다음 달·N월(지난 달 이름은 내년)·2027년 3월 |
  | `month_any` | 팀별 인원 | `month` | 이번 달·다음 달·N월(올해) |
  | `settlement_week` | 판매자 정산 | `period`(ISO 주) | 지난주·이번 주, 말이 없으면 부서 기본 주 |
  | `anomaly_window` | 지표 이상 점검 | `window_from`·`window_to` | 어제·오늘·지난 N시간(최대 168)·이번 주, 말이 없으면 최근 24시간 |
  | `customer_text` | 고객층 분석 | `text`(200자) | 문장 그대로 |
  | `search_query` | 비슷한 과거 기록 | `query`(500자) | 문장 그대로 |

- **못 채우면 지어내지 않고 되묻는다.** 부서가 지원하지 않는 기간(매출의 "어제·지난달", 정산의 "달 단위")이나
  월이 없는 이벤트·인원 의뢰는 접수 때 정해진 문장으로 한 번만 되묻고(`received`, 기존 되묻기와 같은 길), 답이
  또 없으면 사람에게 넘긴다(`needs_human`, 이유 `unclear`). 이때 부서에는 보내지 않는다. 고객이 답하면 새
  의뢰로 이어지고 되묻던 기록은 닫힌다.
- **접수 안내에 어떻게 읽었는지 붙인다.** 예: "…데이터분석에 시켰어요. (최근 7일 기준)"
- **실행기도 한 번 더 채운다.** 사람이 일을 바꿔 다시 돌린 경우처럼 접수 점검을 거치지 않은 의뢰가 입력을 못
  채우면 그 단계를 `failed`(`no_input`)로 닫아 부서에 보내지 않고 사람에게 넘긴다. 고객 문장은 이전처럼 `untrusted`로도
  함께 간다.
- 아직 안 된 것(19번): 문장만으로 채울 수 없는 입력(캠페인 번호·담당자 번호·주문 번호·공지/기획안 번호·영상 초안·템플릿)은
  고객이 고르거나 로그인 정보·앞 단계에서 받아야 한다. 이번에는 규칙을 만들지 않았다.

## 운영 점검 수정: 승인 범위·옛 계획·분류 이름 (11/20)

#1474 배포 뒤 대화방에서 "캣북스 홍보 영상"을 돌려 보고 막힌 곳(재현 님 점검)을 고쳤다.

- **사람 승인 범위를 줄였다.** 전에는 읽기가 아닌 단계를 모두 총괄이 먼저 사람 승인으로 막았다. 부서의 안전 관문
  (`execute()`)이 이미 등급대로 처리하는데(A 자동·B 교차검증·C 사람 보류) 총괄이 한 겹 더 막은 셈이었다. 이제
  - 입력이 앞 부서 결과에서 오는 A·B 단계(홍보 영상의 기획 단계·영상 제작)는 총괄이 막지 않고 부서에 보낸다.
  - **고객 문장에서 입력이 나오는 상태 변경은 사람 승인을 유지한다**(`TaskStep.human_gate`: 기능 개발 요청·환불
    접수). 분류 LLM이 고객 글에 속아도 승인 없이는 실행되지 않게 하는 방어(작업표 12번)라서 풀지 않았다. 입력을
    고객 문장에서 채우는 일(19번)이 늘어도 이 단계들은 그대로 막힌다.
  - C 등급 단계도 총괄이 승인을 먼저 받는다. 사람 확인 단계(`human_check`)는 홍보 영상에 그대로 있다.
  - 접수 안내: 사람 승인이 필요한 일은 "승인을 거친 뒤에", 그 밖의 상태 변경은 "안전 확인을 거쳐" 진행된다고 말한다.
  - 아직 안 된 것: 부서의 안전 관문이 C로 보류한 단계(`held`)가 승인된 뒤 의뢰가 이어 가는 길은 의뢰 쪽에 없다
    (장애 이벤트에만 있다). 지금 일 목록에는 해당하는 단계가 없다.
- **시작 전 의뢰의 옛 계획을 새로 만든다.** 접수 때 저장한 계획은 일 목록이 바뀌어도 그대로여서, 배포 전에 접수된
  의뢰가 서버를 다시 켠 뒤 옛 순서(트렌드 → 기획, 긴 작업 입력 없음)로 돌았다. 이제 실행을 시작할 때 아무 단계도
  시작하지 않은 의뢰의 계획이 지금 일 목록과 다르면 지금 기준으로 다시 만든다(`refresh_plan`, 일·확신도·이유는
  그대로). 이미 시작한 의뢰는 바꾸지 않는다. 화면의 "다시 돌리기"는 같은 일로도 처음부터 다시 돌릴 수 있다.
- **분류가 일 이름으로 와도 받는다.** LLM이 일 번호(`promo_video`) 대신 이름표("홍보 영상 만들기")를 돌려주면
  "담당 불명"이 되던 것을, 번호·이름표 둘 다(띄어쓰기·대소문자 무시) 일 목록의 일로 바꿔 받는다. 목록에 없는 값은
  그대로 담당 불명이다(지어내지 않는다). 차선 후보도 같다.
