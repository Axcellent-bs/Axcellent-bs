# 의뢰 분류 정확도 시험 (총괄 의뢰 자동 넘김 20번)

고객 글을 총괄이 일 목록의 일 하나(또는 질문·되묻기·거절·담당 불명)로 가르는 분류(`request_classifier.py`)가
맞는지를 실제 LLM으로 쟀다. 시험일 2026-11-20, 분류 지시문 버전 v1, 확신도 기준값 `CONFIDENCE_MIN = 0.6`.

## 방법
- 문장 샘플 30개(`services/orchestrator/tests/request_samples.json`)와 정답. 일 의뢰 19개(일 목록 18개를 모두 한 번씩,
  홍보 영상만 2문장), 질문 3, 모호 2, 위험 3, 목록에 없는 일 3.
- **일 목록의 예시 문장을 그대로 쓰지 않고** 말을 바꿔 썼다(지시문에 든 예시를 베끼면 정확도가 부풀려진다.
  시험이 이를 확인한다).
- `scripts/eval_request_classifier.py`가 샘플마다 실제 LLM을 한 번 부르고(총 30번, 한 번 평균 2.3초, 호출
  한도 오류 없음), 돌려준 확신도로 기준값을 바꿨을 때를 다시 계산한다.
- 결과를 세 가지로 나눈다. **정답**, **안전하게 빗나감**(일을 못 찾았지만 되묻거나 사람에게 감),
  **엉뚱하게 보냄**(다른 부서로 보냈거나 의뢰가 아닌 글을 일로 보냄, 이쪽이 문제다).

## 결과
| 종류 | 맞힘 | 확신도(가장 낮은 값 ~ 가장 높은 값) |
| --- | --- | --- |
| 일 의뢰(일 이름까지) | 19/19 | 0.82 ~ 0.95 |
| 질문 | 3/3 | 0.85 ~ 0.90 |
| 모호(되묻기) | 2/2 | 0.90 |
| 위험(거절) | 3/3 | 0.95 ~ 0.97 |
| 목록에 없는 일(담당 불명) | 3/3 | 0.80 ~ 0.85 |
| **합계** | **30/30** | |

틀린 문장은 없다. 엉뚱하게 보낸 것도 안전하게 빗나간 것도 0개다.

## 확신도 기준값
| 기준값 | 정답 | 안전하게 빗나감 | 엉뚱하게 보냄 | 되묻게 된 일 의뢰 |
| --- | --- | --- | --- | --- |
| 0.5 | 30 | 0 | 0 | 0 |
| **0.6 (지금)** | 30 | 0 | 0 | 0 |
| 0.7 | 30 | 0 | 0 | 0 |
| 0.8 | 30 | 0 | 0 | 0 |
| 0.9 | 21 | 9 | 0 | 9 |

## 결론
- **기준값은 0.6을 그대로 둔다.** 맞는 답의 확신도가 모두 0.80 이상이라 0.6~0.8에서는 달라지는 것이 없고,
  0.9로 올리면 맞는 일 의뢰 9개를 되묻게 만든다.
- **이 결과만으로는 0.6이 알맞다고 말할 수 없다.** 틀린 답이 하나도 없어서, 틀릴 때 확신도가 얼마나 낮아지는지
  (기준값이 틀린 답을 막아 주는지)를 재지 못했다. 샘플이 한 가지 일을 분명하게 말한 쉬운 문장이라 정확도 100%는
  경계 문장(두 일이 섞임, 돌려 말함, 오타, 두 가지를 한꺼번에 시킴)에 일반화되지 않는다.
- 운영에서 실제로 틀린 사례는 샘플 밖에서 나왔다. 분류가 일 번호 대신 일 이름표("홍보 영상 만들기")를 돌려줘
  담당 불명이 된 것(#1480에서 이름표도 받도록 고침)과, 고객 글 속 지시에 속아도 부서에 보내지 않는 방어(작업표
  12번, 주입 시험 14건 중 11건 거절·3건은 승인 단계에서 멈춤)다.
- 그래서 다음 시험은 **경계 문장 샘플**(예: 영상 제작과 성과 조회가 섞인 글, "환불" 질문과 접수의 경계, 오타·반말·
  영어 섞임, 일 두 개를 동시에 시킴, 부서 이름만 말한 글 등)로 틀리는 곳과 그때의 확신도를 보는 것이다.
  호출 수가 늘어(작업표의 30개를 넘음) 정하고 하는 게 맞다.

## 재시작 뒤 이어가기 (작업표 20번의 나머지)
저장 파일(SQLite)에 의뢰를 적고 총괄을 다시 켠 것처럼 의뢰를 다시 올려 실행기로 확인했다
(`tests/test_request_restart.py`, 모두 통과).
- 긴 작업을 기다리던 단계는 다시 켜도 기다리고(부서에 다시 보내지 않음), 늦게 온 완료 알림으로 끝난다.
- 부서를 부르던 중 꺼진 읽기 단계는 다시 시킨다. 상태를 바꾸는 단계는 보냈는지 알 수 없어 다시 보내지 않고
  사람 확인(`restart_unconfirmed`)으로 둔다.
- 사람 승인을 기다리던 단계는 승인 전에는 아무것도 보내지 않고, 다시 켠 뒤 승인하면 이어진다.
- 끝난 의뢰는 다시 시키지 않는다.
- 아직 못 한 것: 실제 서버를 껐다 켜며 확인하는 것(시험은 실행기와 저장소를 직접 쓴다).

## 다시 돌리는 방법
```bash
cd backend
uv run python scripts/eval_request_classifier.py --env-file <키가 든 .env 경로> --out 결과.json
```
샘플을 늘리려면 `request_samples.json`에 `{"text", "expect", "task"}`를 더한다(`expect`는 task·question·
clarify·rejected·unknown, `task`는 일 목록의 일 이름). 시험 `test_request_samples.py`는 개수(30)를 고정해 두었으니
함께 고친다.

## 모델 비교 (준하 제안, #소통 2026-11-27, 2순위, `scripts/model_compare_request.py`/`model_compare_request_report.py`)

위 30개 샘플·채점 로직(`verdict()`)을 그대로 재사용해 분류용 LLM 모델을 바꿔 가며 비교한다. 새 골든셋을
만들지 않고 `eval_request_classifier.py`를 서브프로세스로 그대로 돌린다.

```bash
cd backend
# 모델마다 한 번씩 (ORCHESTRATOR_LLM_MODEL 등은 backend/.env 또는 --env-file)
ORCHESTRATOR_LLM_MODEL=claude-haiku-5-5 \
  uv run python scripts/model_compare_request.py claude-haiku-5-5

ORCHESTRATOR_LLM_MODEL=claude-sonnet-5 \
  uv run python scripts/model_compare_request.py claude-sonnet-5

# 비교표 (모델 · 정답 · 안전하게 빗나감 · 엉뚱하게 보냄 · 일 의뢰 적중)
uv run python scripts/model_compare_request_report.py claude-haiku-5-5 claude-sonnet-5
```

- 결과는 `scripts/results/model_compare/request_<라벨>.json`에 모델별로 쌓인다(기존 1회성 결과 파일 이름인
  `request_eval_results.json`과는 별도).
- 문장 30개마다 실제 LLM을 한 번씩 부르므로 모델 하나 돌릴 때마다 과금된다.
- 이 세션(클라우드 샌드박스)에는 키가 없어 실행만 확인했다(래퍼가 `eval_request_classifier.py`의 실패를
  그대로 전달하는 것까지만 검증). 실제 비교 숫자는 키가 있는 로컬 PC에서 위 명령으로 내야 한다.
