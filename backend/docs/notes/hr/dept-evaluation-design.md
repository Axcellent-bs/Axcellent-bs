# 인사 부서 평가 설계 (장애 대응 시간) — 0단계 확인 결과

> 상태: 계획·확인 단계. 이 문서는 코드를 읽은 결과와 1~4단계에서 만들 필드·흐름을 정리한 것이고, 아직 만든 코드는 없다.
> 기준값은 모두 임시값(v1)이다. 실제 장애 기록이 쌓이면 조정한다.

## 1. 목적

장애 대응 때 부서 AI가 맡은 단계의 처리 시간을 인사가 기준값과 비교해, 부서별 지연과 반복 장애를 보여 준다.
판정은 시간 비교 계산으로만 하고 LLM은 쓰지 않는다. 최종 판단은 사람이 한다.

## 2. 코드에서 확인한 것

| 질문 | 확인 결과 | 위치 |
|---|---|---|

| 승인 대기 시각이 있는가 | `Hold.started_at`(보류에 올린 시각)이 있다. 그러나 `Hold.decide()`가 결정 시각을 남기지 않는다 | `engine.py` `Hold` |
| 승인 대기가 저장되는가 | 저장되지 않는다. `holds`·`handoffs`는 저장 형식에서 제외돼 있어 재시작하면 사라진다 | `store.py` `incident_to_dict` |

| 재시도 횟수가 저장되는가 | 저장됨(`attempts`). 실패 재시도 최대 2, 마감 초과 재시도 최대 1. 승인 뒤 재개 호출은 `attempts`에 안 센다 | `engine.py` `_call_and_handle` |
| 사람 할 일함 대기 시각이 있는가 | `HandoffWait.started_at`(넘긴 시각)·`finished_at`(사람이 끝낸 시각)이 있다. 처리를 시작한 시각은 없다. 이것도 저장되지 않는다 | `engine.py` `HandoffWait` |
| 외부 대기(shop-api 등)를 구분할 수 있는가 | 구분할 수 없다. 총괄은 부서에 요청을 보내고 답이 올 때까지의 시간만 안다. 부서 안에서 무엇을 기다렸는지는 모른다 | `engine.py` `_send` |
| 안전 관문이 승인 시각을 주는가 | 준다. `Review`에 `review_id`·`context_id`·`created_at`·`decided_at`·`status`(pending/approved/rejected/expired)·`expires_at`이 있고 `GET /api/safety/reviews`로 읽는다. `Hold.review_id`가 이 `review_id`와 같다 | `ax_safety/store.py`, `main.py` |
| 인사가 받는 시각 계약 | `RecordEventTimesInput`(`EventTimeline` 상속): `detected_at`, `cause_candidate_at`, `human_work_started_at`, `human_work_done_at`, `recovered_at`, `prior_case_id`. 이미 값이 있는 시각은 덮어쓰지 않고 비어 있던 것만 채운다 | `ax_contracts/schemas/hr.py`, `hr_agent/case_memory/service.py` |
| 인사가 이미 나누는 구간 | 감지→원인 후보(AI 처리), 사람 작업 시작→완료, 완료→정상 복귀(복구 대기). 부서별·단계별 구분은 없다 | `ax_contracts/schemas/hr.py` |
| 처리 시간 요약(`kpi_summary`) | 사건별 감지~복구 시간(`mttr_seconds`), 자동 처리율, 등급별 건수 등을 계산하는 순수 함수(LLM 없음). 부서별 단계 시간은 계산하지 않는다 | `data_agent/metrics/kpi.py` |

## 3. 확인으로 바뀌는 것

1. **외부 대기는 v1에서 뺀다.** 총괄은 구분할 수 없다. 외부 때문에 늦어진 것은 일한 시간에 그대로 들어가므로, 화면에 "외부 요인은 구분하지 않음"이라고 적는다.
2. **전달 대기의 뜻을 "사람 할 일함 대기"로 바꾼다.** 처리 시작 시각이 없어서 "넘긴 뒤 처리 시작까지"는 잴 수 없다. 잴 수 있는 것은 "넘긴 시각 → 사람이 끝낸 시각"이다.
3. **승인 대기는 총괄이 직접 기록한다.** `Hold.decide()`에서 결정 시각을 남기고, 승인 대기 초를 단계 기록에 저장한다. 안전 관문 `decided_at`은 같은 값을 맞춰 보는 용도다.
4. **복구 검증은 결과 지표로 둔다.** 복구까지 걸린 시간은 `kpi_summary`의 `mttr_seconds`를 쓸 수 있다.

## 4. 1단계에서 더할 필드 (총괄, 모두 추가만)

`StepRun`(저장 형식에 선택 값으로 추가)

| 필드 | 뜻 |
|---|---|
| `approval_wait_seconds` | 보류에 올린 시각부터 사람이 결정한 시각까지 |
| `human_wait_seconds` | 사람 할 일함으로 넘긴 시각부터 사람이 끝낸 시각까지 |
| `work_seconds` | `finished_at − started_at − approval_wait − human_wait` (0 미만이면 0) |

- `Hold`에 `decided_at`을 더하고, 결정 때 승인 대기 초를 단계에 옮긴다.
- `HandoffWait.finished_at`은 이미 있으니 끝날 때 단계에 옮긴다.
- 인사로 보내는 단계별 값:

```
{ step_id, dept, status, work_seconds, approval_wait_seconds,
  human_wait_seconds, attempts, reason_code }
```

## 5. 인사로 보내는 방법 (결정 필요)

| 안 | 내용 | 장단점 |
|---|---|---|
| A (추천) | `RecordEventTimesInput`에 선택 필드 `step_timings`를 추가(계약은 추가만) | 이미 있는 총괄→인사 호출·멱등성·카드 연결을 그대로 쓴다. 새 skill 등록(Agent Card·안전 등록부)이 필요 없다. 단 "이미 있는 값은 덮어쓰지 않음" 규칙과 단계 시간 갱신 방식을 정해야 한다 |
| B | 새 skill `record_step_timings`를 만든다 | 규칙이 깔끔하지만 계약·Agent Card·안전 등록부까지 늘어 범위가 커진다 |

1단계 크기는 **중간**으로 본다(총괄 필드 + 저장 + 전송 + 계약 + 시험).

처음에는 묶음별 정상·지연·확인 필요 표를 제안했으나, 총괄이 부서를 한 번 부를 때 30초에서 끊고 다시 시도하므로 30초를 넘었다는 것은 곧 재시도가 있었다는 뜻이다. 그래서 지연 구간 없이 모든 단계가 같은 기준을 쓴다(고객지원·인프라·개발·마케팅·데이터분석 합의).

| 판정 | 조건 |
|---|---|
| 정상 | 일한 시간 30초 이하이고 시도 횟수 1회(재시도 없음) |
| 확인 필요 | 그 밖의 경우(30초 초과 또는 재시도·시간 초과). 시도 횟수를 같이 표시 |

- 평가 제외: 기획 AI, 복구 검증(결과 지표)
- 시간이 아닌 상태: 기록 없음 / 실패·막힘 / 승인 만료 (외부 대기는 v1 제외)

## 8. 1단계 구현 메모 (총괄이 시간을 나눠 기록)

- 총괄 `StepRun`에 `approval_wait_seconds`·`human_wait_seconds`를 더했고(저장 형식에도 포함), `Hold.decide()`가 결정 시각을 남긴다.
- 일한 시간(`work_seconds`)은 `timeline.step_timings()`가 단계 전체 시간에서 두 대기를 빼서 계산한다(0 미만이면 0).
- 인사로는 5번의 A안대로 `record_event_times`의 선택 필드 `step_timings`로 보낸다. 이벤트가 끝난 뒤에만 보내고, 사람 처리가 늦게 끝나 값이 바뀌면 다시 보낸다. 인사는 단계 시간을 마지막 값으로 바꿔 저장하고, 시각은 지금처럼 덮어쓰지 않는다.
- 이번에 넣지 않은 것: 외부 대기(총괄이 구분할 수 없음), 고객지원 보상 승인 대기(고객지원 자체 큐이고 단계 시간에 섞이지 않는다는 병환 님 확인).
- 로컬 실제 장애로 확인: 되돌리기 단계 전체 약 38초 중 승인 대기 34.9초, 일한 시간 3.5초로 따로 기록됐고 인사 카드(`extra.step_timings`)에 18개 단계가 저장됐다.
- 알려진 한계: 사람 할 일함으로 넘긴 단계는 일한 시간이 0에 가깝게 나온다(대기가 거의 전부라서). 복구 검증은 쇼핑몰 복구를 기다린 시간이 일한 시간에 들어가므로 부서 평가에서는 빼고 결과 지표로 본다.

## 9. 2단계 구현 메모 (인사가 단계별 판정을 저장)

- 위치: `backend/domains/hr/src/hr_agent/dept_eval/` (`criteria.toml` 기준값, `criteria.py` 읽기, `stages.py` 배정표, `judge.py` 판정).
- 기준값은 `criteria.toml` 한 곳이다. `version`·`updated`와 `[default]`(30초, 시도 1회)가 있고, 묶음별로 다르게 해야 할 때만 `[group."묶음 이름"]`을 덧붙인다(지금은 없음). 값이 올바르지 않거나 파일을 못 읽으면 기본값으로 숨기지 않고 오류를 낸다. 사람만 PR로 바꾸고 바꾸면 `version`을 올린다.
- 배정표(`stages.py`)는 총괄 장애 대응 계획의 단계 번호 19개(늦게 도는 `late_compensation` 포함)를 모두 대상 또는 제외로 정한다. 제외는 `cause_check`(기획)와 `recovery`(복구 검증). `related_prs`·`link_incident`는 개발로 센다. 표에 없는 단계(다른 계획의 `cost` 등)는 판정하지 않는다.
- 판정 순서(`judge.py`): 승인 만료(`review_timeout`) → 실패·막힘(`failed`·`rejected_by_human`·`transfer_queued`) → 진행 중(미완료 상태는 판정 보류) → 기록 없음(건너뜀·시간 모름) → 일한 시간·시도 횟수를 기준과 비교(`normal`/`check`). 30초 정확히는 정상, 30.001초부터 확인 필요.
- 저장: 1단계의 `record_event_times`가 단계 시간을 바꿔 저장할 때마다 같은 자리에서 판정을 다시 계산해 카드 `extra.step_judgments`(`criteria_version`과 `items`)로 둔다. 새 skill·계약 변경은 없다. 기준값 파일을 읽지 못해도 시각 기록은 막지 않고 감사 기록(`dept_eval.criteria_unreadable`)만 남긴다.
- 지난 판정은 그때의 `criteria_version`을 들고 있어서 기준을 바꿔도 섞이지 않는다. 기준을 바꾼 뒤 지난 이벤트를 새 기준으로 다시 보는 기능은 이번에 만들지 않았다.
- 로컬 실제 장애(1단계에서 저장된 카드)에 판정 함수를 돌려 확인: 18개 단계 중 16개가 대상, 14개 정상, 2개 기록 없음(정상화 공지 2단계가 돌지 않음).

## 10. 3단계 구현 메모 (에이전트 평가 화면)

- 이름: 화면과 문구는 "부서 평가" 대신 **"에이전트 평가"**를 쓴다(결정 11/9). 메뉴는 인사 AI 아래 결정 기록과 조직 변동 사이(`/agent-eval`). 내부 코드 이름(`dept_eval`)은 그대로 둔다.
- 점수·등급·순위는 만들지 않는다. 사람이 "제때 끝냈다 / 늦었다"를 읽도록 ① 에이전트마다 한 줄 문장 ② 최근 이벤트를 점(●▲✕○) 한 줄로 ③ 늦은 이유(다시 시도 N회·N초 걸림)를 보인다. 이벤트가 3건 미만이면 문장 평가를 미루고 "아직 기록이 적어서 판단하기 이릅니다"로 안내한다. 화면에 "시간만 본 결과이며 일의 품질이 아님"을 적는다.
- 백엔드: 인사 읽기 전용 skill `evaluate_agents`(`dept_eval/summary.py`, 결정 기록 서비스 `decisions`에 올림, 요청자 dashboard-api)가 카드에 저장된 `step_judgments`·`step_timings`를 모아 에이전트별 건수·점·이유·반복 유형·평균/최대 시간, 날짜별 추이, 이벤트별 단계 목록을 준다. 판정은 저장된 값을 그대로 쓰고 다시 계산하지 않는다(그때의 기준값 버전이 이벤트마다 남는다). 대시보드 API는 `GET /api/dashboard/agent-evaluation?limit=`로 부른다. 계약은 추가만 했다(`EvaluateAgents*`, `AgentSummary` 등). 목 모드는 가짜 판정 없이 빈 결과를 준다.
- 한 이벤트에서 에이전트의 단계가 여럿이면 점은 가장 걸리는 판정으로 줄인다(승인 만료 > 실패·막힘 > 확인 필요 > 진행 중 > 제때 끝냄 > 기록 없음). 앞 단계가 안 돌아 건너뛴 단계(기록 없음)는 다른 단계가 제때 끝났다면 점에 올리지 않는다(그 에이전트 탓이 아니다). 단계 목록에는 그대로 남는다.
- **"사람에게 넘김"은 실패·막힘이 아니다(판정 `handed_off`).** 원인을 확정하지 못해 되돌리기를 사람에게 넘기는 것처럼 스스로 끝내지 않고 사람이 보도록 넘기는 건 설계된 동작이다. 단계 상태 `transfer_queued`(이관 큐로 넘김)와 `waiting_human`(사람 할 일함에서 처리 대기)을 이 판정으로 가르고, 화면에서는 빨강·노랑 대신 중립 색(⇢)과 "실패나 지연이 아니에요" 문구로 보인다. 확인이 필요한 이벤트·반복 유형 집계에도 세지 않는다. 사람에게 넘김이 생기기 전에 저장된 판정(`blocked`+`transfer_queued`, `in_progress`+`waiting_human`)은 읽을 때 같은 판정으로 바로잡는다. `blocked`는 실패하거나 사람이 거절한 경우만이다.
- 승인 대기와 사람 할 일함 대기는 에이전트 카드에 넣지 않고, 이벤트를 열었을 때의 단계 타임라인에서만 색 막대로 따로 보인다.
- 서비스 등록: 화면 메뉴 `agent-eval`은 프론트 서비스 목록에만 있고, 백엔드 서버는 새로 띄우지 않고 기존 `decisions`(8114)가 skill을 받는다(서버를 하나 더 늘릴 만큼의 일이 아님). 이미 서비스 선택을 저장해 둔 브라우저는 서비스 고르기에서 "에이전트 평가"를 켜야 메뉴가 보일 수 있다.
- 로컬 실제 장애 두 번으로 확인: 원인을 특정하지 못해 되돌리기가 사람에게 넘어간 이벤트 2건이 인프라 AI "실패·막힘(사람에게 넘김)", 나머지 에이전트 "제때 끝냄"으로 나왔다. 다시 시도나 30초 초과는 이 장애 흐름에 나오지 않아 시험으로만 확인했다.
- 다시 시도·30초 초과("확인 필요")는 평소 로컬 장애에서 나오지 않아 `backend/scripts/slow_agent.ps1`(Windows)로 부서 서버를 잠깐 멈췄다 풀어 실제로 만든다. 총괄의 한 번 호출 마감(30초)보다 길게 멈추면 다시 시도가 난다.
- 서비스 선택을 저장해 둔 브라우저에서 새 서비스가 꺼진 채 남는 문제: 저장할 때 그 시점의 서비스 목록(`axcellent-demo-services-known`)도 남기고, 목록에 없던 서비스는 "새로 생긴 것"으로 보고 켠다. 이미 끈 서비스는 그대로 끈다.
- **복구 뒤 영향 분석 재계산이 단계 시간을 부풀리던 문제를 고쳤다.** 총괄은 복구 신호를 받으면 영향 분석을 같은 구간(복구 시각까지)으로 다시 돌리는데(`refresh_impact`), 이때 `finished_at`을 다시 계산한 시각으로 덮어써서 첫 시작~재계산까지(몇 분)가 일한 시간이 됐다. 로컬 실제 장애에서 영향 분석이 250초·62초로 "확인 필요"가 되는 것으로 발견했다. 이제 다시 계산한 시각은 `StepRun.refreshed_at`에 따로 남기고 `finished_at`은 첫 분석이 끝난 시각 그대로 둔다. 이 수정 전에 저장된 로컬 이벤트의 영향 분석 시간은 부풀려진 채 남는다.
- 실제 장애로 확인(다시 시도): 장애를 넣고 데이터분석 서버를 40초 남짓 멈췄다 풀자 영향 분석이 "다시 시도 1회 · 48초 걸림(기준 30초)"로 확인 필요가 되었고, 이어 복구 신호로 재계산이 돌아도(`refreshed_at` 기록) 시간은 48초 그대로였다.

## 11. 4단계 마무리 결정 (2026-11-09)

- **의견 남기기(확인 필요 건에 담당자가 의견 남기기)는 하지 않기로 했다.** 지금까지 만든 것은 모두 읽기였고 이건 처음 저장하는 기능이라(인사 저장 skill, 안전 관문 등록, 계약, 입력 화면) 일이 크며, 팀이 써 본 뒤에야 필요한 의견 종류를 알 수 있다. 필요해지면 팀 반응을 본 뒤 별도 작업으로 한다.

- 용어 점검: 화면에 보이는 영어는 에이전트 이름의 "AI"뿐이고, "임시 설정값 v1"은 "임시 기준 1판"으로 바꿨다. 에이전트 카드는 문장, 점, 늦은 이유, 반복 유형만 남기고 평균·최대 시간과 건수 줄은 뺐다.
