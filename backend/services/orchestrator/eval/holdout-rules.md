# 총괄 AI holdout(훈련용·테스트용 분리) 시험: 방법과 판정 기준 (테스트 결과를 보기 전에 정함)

2026-11-10, 이태윤 님의 요청("각각의 a2a에 holdout 테스트")에 따라 총괄 AI에서 한다.
인사 AI의 시험(`backend/domains/hr/eval/holdout-rules.md`)과 같은 틀이다.

## 1. 총괄에는 훈련으로 정하는 값이 없다

총괄은 학습 모델도 임계값도 없다. 이벤트 처리는 plan(단계·선행 관계·필수 여부)과 엔진 규칙으로 움직인다.
그래서 이 시험은 "값을 정하고 재기"가 아니라 **"규칙이 처음 보는 장애 조합에서도 설계대로 움직이는가"** 를 훈련용과 테스트용으로 나눠 잰다.

## 2. 시험할 규칙 (엔진 코드를 읽고 오라클을 따로 썼다)

가짜 부서(`FakeDepartments`)에 부서별 응답을 미리 정해 주고(성공 `ok`, 실패 `fail`, 마감 초과 `timeout`),
총괄이 이벤트를 끝까지 처리한 결과를 **독립적으로 다시 짠 기준표(오라클)** 와 비교한다.

| 규칙 | 오라클이 예상하는 것 |
|---|---|
| 선행 단계(`after`) | 선행 단계가 모두 `completed`가 아니면 그 단계는 `skipped`, 호출하지 않는다 |
| 끝나기만 기다리는 선행(`also_after`) | 선행이 성공이든 실패든 끝나면 실행한다 |
| 실패(`fail`) 재시도 | 최대 2번 다시 시도(총 3회), 그래도 실패면 `failed` |
| 마감 초과(`timeout`) 재시도 | 최대 1번 다시 시도(총 2회), 그래도 초과면 `failed` |
| 재시도 중 성공 | 그 시점에 `completed`, 시도 횟수는 실제 호출 횟수 |
| 이벤트 최종 상태 | 필수 단계가 모두 `completed`면 `resolved`, 하나라도 아니면 `degraded` |
| 판단 단계(gate)로 건너뛰는 단계 | 장애 없이 한 번 돌린 기준 실행에서 건너뛴 단계는, 선행이 성공이면 계속 건너뛴다 |
| 원인 확인 요청(`cause_check`) | 원인 후보(`root_cause`)가 성공해 확신 높은 후보가 있으면 건너뛰고, **원인 후보가 실패·건너뜀이면 요청을 보낸다**. (Train 첫 실행에서 오라클이 이 규칙을 빠뜨려 4건이 어긋났고, 총괄 설계 주석 "원인 후보에 확신도 high가 있으면 원인 확인 업무를 넘기지 않는다"를 확인해 오라클을 고쳤다. 총괄 코드는 바꾸지 않았다) |

비교 항목: 단계별 최종 상태, 단계별 호출 횟수(시도), 이벤트 최종 상태.

## 3. 분리

| 구분 | 사례 수 | 용도 |
|---|---|---|
| Train | 60개 (시드 20261110) | 오라클이 틀리지 않았는지 **확인하고 고치는 데만** 쓴다. 총괄 코드는 이 시험을 위해 고치지 않는다 |
| Test | 60개 (시드 2026111002) | Train에서 오라클을 확정(고정)한 **뒤에 한 번만** 돌린다. 결과를 본 뒤 오라클을 고치지 않는다 |

사례 하나는 장애를 넣을 수 있는 12개 단계 중 1~3개를 골라 응답 순서를 정한다.
응답 순서는 `fail`, `fail×2`, `fail×3`, `timeout`, `timeout×2`, `fail→timeout`, `timeout→fail×3`, `timeout→ok`, `fail→ok`, `fail×2→ok` 중에서 고른다(시드 고정).
장애를 넣지 않는 단계(공지 4개, 이벤트 기록, 복구 검증)는 같은 부서·같은 skill을 두 단계가 같이 써서 응답 순서가 섞이기 때문에 뺐다.

## 4. 판정 기준

1. Test 단계별 상태 정확도가 Train 대비 **5%p 넘게 떨어지지 않는다**.
2. Test 사례 전체가 완전히 일치하는 비율이 Train 대비 **10%p 넘게 떨어지지 않는다**.
3. Test 이벤트 최종 상태 정확도가 **95% 이상**이다.
4. Test 단계별 호출 횟수 정확도가 Train 대비 **5%p 넘게 떨어지지 않는다**.

## 5. 보고

기준 통과 여부와 상관없이 Train·Test를 모두 적는다. 불일치가 있으면 사례를 그대로 적고, 총괄이 틀렸는지 오라클이 틀렸는지는 따로 판단해 적는다(Test 결과를 본 뒤 오라클을 고치지 않는다).

### 한계 (결과보다 중요하다)
- **학습 모델이 아니라 규칙 점검이다.** 총괄에는 훈련으로 정하는 값이 없어서, "성능이 올랐다"가 아니라 "처음 보는 장애 조합에서도 설계대로 움직인다"를 확인한 것이다.
- **오라클은 내가 plan과 엔진 규칙을 읽고 다시 짠 것이라, 같은 이해에서 나왔다.** 총괄과 오라클이 같은 오해를 하고 있으면 둘 다 맞게 나온다.
- Train 첫 실행에서 오라클이 `cause_check` 규칙을 빠뜨려 4건이 어긋났다. 총괄 설계 주석을 확인해 오라클을 고쳤다(총괄이 맞았다). Test는 오라클을 고정한 뒤(파일 해시 `d04defb9`) 한 번만 돌렸다.
- **판단 단계(gate)로 건너뛰는 단계와 장애를 넣지 않은 단계는 오라클이 장애 없는 기준 실행의 총괄 결과를 그대로 쓴다.** 이 부분은 검증이 아니다. 실제로 장애 주입과 선행·재시도·필수 여부 규칙을 검증한 단계는 18개 중 12개다.
- 가짜 부서로 한 시험이다(실제 부서 서버가 아니다). 시나리오 A 하나이고, 장애는 `fail`·`timeout` 두 가지만 넣었다. 승인 대기(`hold`), 사람 할 일함 이관, 단계별 시간 기록, 복구 신호는 이 시험에 없다.
- 공지 4개 단계, 복구 검증, 이벤트 기록에는 장애를 넣지 않았다(같은 부서·skill을 두 단계가 같이 써서 응답 순서가 섞인다).
- 판정 기준은 Test 결과를 보기 전에 적었다. 다만 Train 결과를 본 뒤 오라클을 한 번 고쳤다.
