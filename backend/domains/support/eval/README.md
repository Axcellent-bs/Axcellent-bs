# 고객지원 AI holdout 평가

고객지원 AI에서 정답을 문서대로 코드 규칙으로 계산할 수 있는 영역이 처음 보는 입력에서도 맞게 동작하는지 잰다.
(다른 부서 holdout과 같은 방식: 개발 AI `domains/dev/eval`, 재무 AI `domains/finance/eval`)

```bash
cd backend
uv run python domains/support/eval/holdout.py --n 200 --show 4   # dev seed (하네스 고칠 때, 틀린 입력을 보여 줌)
uv run python domains/support/eval/holdout.py --n 200 --holdout  # holdout seed (한 번만, 숫자만)
```

## 대상

| 영역 | 부르는 코드 | 정답 기준 |
| --- | --- | --- |
| 답변 가드 | `guard.check_reply` | README "답변 가드": 환불·보상 단정은 `promise_refund`, 개인정보가 있으면 `pii_in_reply`(error), 확인·조건을 말하는 문장과 주문번호·날짜는 통과 |
| 개인정보 가리기 | `guard.mask_pii` | 휴대전화(+82 포함)·이메일·주민등록번호·Luhn 통과 카드번호·"계좌번호" 단서가 붙은 계좌번호는 가려지고, 주문번호·금액·날짜·Luhn 실패 송장번호는 그대로 |
| 욕설 규칙 | `abuse_rules.assess` | 모듈 설명: 단계 순서(위협 > 모욕 > 비속어), 정당한 권리 행사(신고·고소·소비자원)와 일반 낱말(시발점·쓰레기통·"두개같이")은 그대로. 비속어·모욕은 "찾았나"로, 위협은 정확히 보며, 낱말별 단계는 문서가 정하지 않아 세지 않는다 |
| 분류 필요 판정 | `triage.assess` | README "분류 필요 문의": `general`이면 `unclassified`, `payment`인데 주문이 없거나 실패한 결제가 없으면 `no_error_code`, 진행 중 사건(`ctx_inc_`)·이미 표시가 있음·주문을 못 읽음(시드)은 올리지 않음 |
| 문의 급증 판정 | `insights.detect_surge` | 최근 창 안 건수 ≥ 기준 건수이고, 평소 창당 건수의 기준 배수 이상이거나 평소가 0이면 급증. 정답은 원자료에서 따로 센다 |
| 언어 판별 | `languages.detect_detail` | 넣은 언어(한·영·일·중·스·프·독·포·이·러·우크라이나·아랍·히브리·태국·힌디) |

뺀 것: 분류·초안·순화·대화방 답(LLM이라 정답이 하나가 아님), 영수증 사진 분석(비전 모델), 접수 경로 전체(shop-api·저장소가 섞임).

## 방법

- seed로 입력을 무작위로 만들고, 넣은 값으로 정답을 이미 아는 입력(예: 전화번호를 넣은 문장은 "가려져야 함")을 만든다.
- 정답은 고객지원 코드를 쓰지 않고 이 파일 안에서 문서대로 따로 정한다. 급증은 원자료에서 문서의 규칙으로 센다.
- 고객지원 코드는 **함수를 직접 부른다**. 다른 부서처럼 `POST /a2a`로 부르지 않는다(이 영역들은 skill 안에서 LLM·저장소와 섞여 있어서).
- 문서가 정한 한계(일반전화·"계좌" 단서 없는 계좌번호·기호로 비튼 욕설·이름·주소)는 정답에 넣지 않는다.
- 말뭉치(언어별 문장, 욕설·답변 예시)는 dev용과 holdout용을 따로 썼다. holdout 말뭉치는 dev seed에서 쓰지 않는다.

## 결과

| seed | 입력 | 전체 | 답변 가드 | 개인정보 | 욕설 | 분류 필요 | 급증 | 언어 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `dev` | 1,040 | 100% | 100% | 100% | 100% | 100% | 100% | 100% |
| **`20261110_01` (holdout)** | 1,040 | **99.9%** | 100% | 100% | 100% | 100% | 100% | 99.5% (이탈리아어 5/6) |

- 결과 파일: `results/dev.json`, `results/holdout_20261110_01.json`
- 코드는 고치지 않았고 하네스만 dev seed로 고쳤다. 처음 돌렸을 때 틀린 것은 코드가 아니라 하네스의 오류였다.
  - 13자리 송장번호를 "가려지면 안 되는 값"으로 넣었는데, 문서는 Luhn을 통과한 13~19자리를 카드번호로 가리므로(무작위 13자리의 약 10%가 통과) Luhn을 통과하지 않는 번호만 쓰게 고쳤다.
  - 중국어 문장 뒤에 한글 "원"을 붙여 한국어로 판별됐다. 언어에 중립인 덧붙임만 쓰게 고쳤다.
  - 문서가 낱말별 단계(`병신`이 비속어인지 모욕인지)를 정하지 않는데 하네스가 정해 놓고 있었다. 욕설·모욕은 "찾았나"로 보게 고쳤다.
- holdout seed의 유일한 틀린 입력은 이탈리아어다(내용은 열지 않았다). 짧은 라틴 문자 글은 흔한 낱말이 적으면 영어로 남는다(PR #927 리뷰의 참고 1·4와 같은 종류).

## 알아 둘 점

- **holdout 말뭉치를 한 번 잘못 썼다.** `--seed dev2`가 holdout 말뭉치를 쓰게 되어 있는 것을 모르고 돌려 집계(이탈리아어 틀림 비율)를 한 번 봤다. 그 동작은 고쳐서 holdout seed에서만 holdout 말뭉치를 쓴다. 입력 내용은 열지 않았고 코드는 이 숫자에 맞춰 고치지 않았다. 공식 숫자는 위 표의 한 번 돌린 결과다.
- 데이터는 모두 합성이고 정답 입력은 사람(Claude)이 만든 문장이라, 실제 고객 글의 다양함은 재지 못했다. 사전 등록한 판정 기준도 없다.
- 영역마다 입력 200개(급증은 40개)라 한 건이 0.5%p(급증은 2.5%p)를 움직인다.
- LLM 영역(분류·초안·순화)은 이 평가에 없다. 순화문이 한국어인지, 분류가 맞는지는 따로 재야 한다.

## 규칙

- 하네스는 dev seed로만 고친다. holdout seed는 한 번 돌려 숫자만 보고, 틀린 입력 내용은 열지 않는다(`--show`가 holdout에선 꺼진다).
- 평가 정의(입력 만들기·정답·비교)를 바꾸는 PR과 고객지원 코드를 고치는 PR은 나눈다.
- holdout을 다시 만들 때는 seed를 바꾸고 이유를 위 표에 적는다. seed는 만든 날 `YYYYMMDD_nn`.
- **holdout 말뭉치는 이 하네스 파일에 커밋되어 머지 뒤에는 누구나 볼 수 있다.** 그래서 이 말뭉치와 seed `20261110_01`은 더 이상 "처음 보는 입력"이 아니다. 다음 holdout은 새 seed와 새 말뭉치로 만들어 돌린다(예진 님 #929 리뷰 참고).
- 위 표의 숫자는 #927(언어 판별 15종)이 들어간 `dev`에서 돌린 것이다(하네스가 `detect_detail`을 부른다). `dev`를 다시 받아 같은 seed로 돌려도 숫자가 같음을 확인했다(전체 1,039/1,040, 이탈리아어 5/6).
