# data 에이전트 정확도 평가

정답지(`cases/`)로 이상 탐지·영향 분석·원인 추정·사기 점수·LLM 설명을 재고, 기준값(`baseline.json`)보다 나빠졌는지 본다.

```bash
cd backend
uv run python domains/data/eval/run.py   # 결과: eval/results/latest.json
```

## 규칙

- **평가 정의 변경은 코드 수정과 별도 PR로 한다.** 평가 정의는 정답지(`cases/`, `make_cases.py`), 채점 방식(`run.py`의 `SIGNALS`·지표 계산), 데이터 생성(`eval_world.py`)이다. 같은 PR에서 둘 다 바꾸면 숫자가 좋아진 것이 코드 덕분인지 정의 덕분인지 가릴 수 없다.
- 기준값(`baseline.json`)은 나빠진 지표가 없을 때만 갱신한다. 나빠졌으면 갱신하지 않고 PR 본문에 원인을 적는다.
- 코드 변경 PR에서 지표가 나빠지면 에이전트가 baseline을 낮추지 않는다. 커밋하지 말고 보고하고, 사람이 채팅에서 허용한 경우에만 낮춘다.
- PR 본문에는 전·후 숫자를 적는다. 평균에 묻히지 않게 바뀐 케이스도 함께 적는다.
- 평가 정의를 바꾼 PR은 기준값이 나빠져도 갱신한다. 대신 PR 본문에 "정의 변경으로 인한 하락"과 나빠진 케이스를 적는다.
- 판정 코드를 고칠 때 holdout 케이스 내용을 보고 맞추지 않는다. holdout은 결과 숫자만 본다. holdout을 다시 만들 때는 seed를 바꾸고 이유를 적는다.
- **평가 허용 숫자는 실서버 explain facts와 같은 함수로 만든다.** LLM 설명의 지어낸 숫자 검사(`llm.fabricated_number_rate`)가 허용하는 영향 설명 숫자는 실서버가 설명에 넘기는 facts를 만드는 함수(`skills/impact_analysis.impact_facts`)를 평가(`run.py _impact_allowed`)가 import해서 만든다(#130). 그래서 facts 목록을 바꾸는 코드 PR은 평가 허용 숫자도 함께 바뀐다. 이것은 평가 정의 변경이기도 하므로, 그런 PR은 본문에 평가 지표 전·후를 적고 지표가 바뀌면 이유를 적는다. 한쪽만 넓으면 평가가 진짜 계산 숫자를 "지어냄"으로 세거나, 지어낸 숫자를 놓친다.
  - 영향 설명: 실패 주문 수, 영향 고객 수, 피해 금액 + 초과분(`excess_failed_order_count`, skill 출력) + 평소 실패 수(소수 둘째 자리)
  - 평소 실패 수만은 실서버 계산값을 쓰지 않는다. 실서버 계산을 검증하려고 근거 문장을 읽지 않고, 평가가 케이스의 지난 7일 결제 기록으로 직접 센 값을 `impact_facts`에 넣는다(`eval_world.usual_fault_failures`). 방식은 영향 분석 초과분(#102)과 같다: 같은 시각 ±1시간, 결제가 기록된 5분의 장애 쪽 실패 평균 × 구간 길이

## holdout (처음 보는 케이스)

`cases/` 27개는 규칙을 고치며 계속 본 케이스다. 처음 보는 케이스에서도 성능이 나오는지 따로 재려고 `holdout/` 40개를 둔다. 지표 이름 앞에 `holdout.`이 붙는다.

- 생성: `uv run python domains/data/eval/make_cases.py --holdout` (`--seed`로 seed를 바꾼다)
- **seed `20261029`**, 40개 (장애 없음 20 · 장애 20)

| seed | 만든 날 | 이유 |
| --- | --- | --- |
| `20261029` | 2026-10-29 | 처음 만듦 |
| `20261029` | 2026-10-29 | 같은 seed로 다시 만듦. 시나리오는 같고 영향 분석 정답 정의만 바뀜 |
| `20261029` | 2026-10-29 | **분석에 사용함 (본 holdout)**: 틀린 케이스(놓친 2개, 감시 오경보 2개, 최대 지연 30분 1개)의 내용을 열어 원인을 분석했다. 이 seed는 더 이상 "처음 보는 케이스"가 아니다. 판정 코드 개선 PR이 끝난 뒤 새 seed로 다시 만든다 |

seed `20261029` 분석 결론:
- 틀린 5개 중 3개(`_29`, `_06`, `_18`)는 데이터로 구분할 수 없고, 1개(`_33`)는 생성 조합(세일 + 주문 급감) 문제, 1개(`_19`)는 약한 장애의 탐지 지연이다.
- 판정 규칙은 더 조정하지 않고 보류한다 (오탐 0% 우선).
- 다음 seed에서는 세일과 주문 급감을 함께 고르지 않는다 (별도 평가 정의 PR).

- 무작위로 고르는 것
  - 시각(0~23시)
  - 장애 종류: 결제 100%·50%·20%, 타임아웃 `PG_TIMEOUT`, 주문 급감 10·30·50%
  - 길이(5~60분)
  - 세일 여부(25%, 구간 전체 2·3배)
  - 잡음 건수(0~3건, 결제사 타임아웃, 지난 7일에도 넣을지)
- 데이터는 기존 케이스와 같이 shop-api 코드로 만든다(`eval_world.build`).
- 정답은 생성 조건에서 정한다. 결제 장애는 실제로 만들어진 장애 쪽 실패 수로 다듬는다(아래 "장애 쪽 실패가 0건·1건일 때").
- 케이스마다 생성 조건이 `holdout` 필드에 있다. 결과 파일에는 `holdout.wrong`(틀린 항목)과 `holdout.conditions`가 남는다. `run.py`는 화면에 틀린 항목 수만 보여 준다.

## 영향 분석 정답 정의

- **정답 = 장애 구간 안의 장애 쪽 실패 결제 전부** (주입한 장애로 실패한 결제 + 그 구간에 난 잡음 실패). 건수·영향 고객·피해 금액 모두 이 기준이다(`impact.match_rate`, `impact.mean_abs_amount_error*`).
  - 이유 1: 운영에서는 주입한 장애와 잡음을 구분할 수 없다. 둘 다 결제 서버 쪽 실패 코드이고, 결제 기록에는 "이건 장애, 이건 잡음" 표시가 없다.
  - 이유 2: 잡음으로 실패한 고객도 실제로 결제에 실패했다. 보상 대상이다.
  - 카드 거절(`PG_DECLINED`) 같은 결제한 사람 쪽 사유는 넣지 않는다(예전과 같음).
  - 처음 보는 실패 코드면 숫자를 내지 않아야 맞다(예전과 같음).
- 정답 파일 `expected.impact`
  - `failed_order_count`·`affected_customer_count`·`damage_amount`: 위 정답
  - `injected_*`: 주입한 장애로 생긴 실패만(2026-10-29 이전 정의). `noise_failed_orders`: 구간 안 잡음 실패
- 바꾼 날: 2026-10-29. 기존 27개와 holdout 40개 모두 다시 만들었다. holdout seed는 그대로다(시나리오는 같고 정답 정의만 바뀜).

### 초과분 지표 (`impact.excess_*`)

- 장애 때문에 **평소보다 더** 실패한 건수를 따로 잰다.
- 정답 = 주입한 장애로 생긴 실패만 (`injected_failed_order_count`, 예전 정의)
- 비교 대상 = 장애 구간 실패 − 지난 7일 같은 시간대 평균 실패 (반올림). 영향 분석 skill이 출력 `excess_failed_order_count`로 내야 하는 값이다.
- `impact.excess_mean_abs_error`: 건수 오차 평균 (낮을수록 좋음)
- 지금 영향 분석 skill은 이 값을 내지 않는다. 그래서 "확인할 수 없음"(null)이다. skill에 이 출력이 생기면 `run.py`가 그대로 읽는다.

## 결제 장애에서 장애 쪽 실패가 0건·1건일 때 (채점 규칙)

결제 장애를 넣었어도, 그 구간에 주문이 적으면 장애로 실패한 결제가 거의 없을 수 있다. 데이터에 남은 흔적으로 채점한다(#91에서 정함).

- **0건 → "이상 아님"으로 채점한다.** 주문이 없어 실패할 기회가 없었다. 데이터에 장애 흔적이 없어 이상이라고 말할 근거가 없다.
- **1건 → 사건(이상)이 아니라 low 기록으로 채점한다.** 잡음 1건과 데이터로 구분할 수 없다(`anomaly.low_recorded_rate`, `pay_half_10m_03h_night`와 같은 기준).
- 여기서 세는 실패는 **주입한 장애로 생긴 것만**이다(`injected_failed_order_count`). 잡음은 장애가 아니므로 0건·1건 판단에 넣지 않는다.
- 지금은 holdout 생성기(`make_cases.holdout_expected`)가 이 규칙을 쓴다. 기존 27개는 명세에서 직접 정한다(`_low`).

## 평가와 감시의 차이 (감시 재현 지표)

- 평가의 이상 탐지 채점(탐지율·오탐률)은 케이스 구간 전체를 **한 번** 판정한다.
- 실제 주기 감시(`monitor.py`)는 **5분마다 최근 구간**을 판정하고, 이상이면 이벤트를 낸다. 구간 전체로 보면 정상이어도, 감시 시점마다 잘라 보면 잠깐 이상이 나올 수 있다. 예를 들어 잡음 1건 직후의 짧은 구간이 그렇다.
- 그래서 감시를 재현하는 지표를 따로 둔다. 모든 케이스를 5분마다 최근 15분으로, 감시와 같은 판정 함수(`detect.judge_window`)와 같은 지표로 판정한다.
  - `anomaly.monitor_false_alarm_count`: 정답이 이상 아님인 케이스에서 감시가 이상을 낸 횟수 (감시마다 센다)
  - `anomaly.monitor_false_alarm_cases`: 그런 케이스 수
  - 케이스별 경보 시각은 `results/latest.json`의 `cases[].anomaly.monitor_alarms`에 남는다.
- 지연은 두 가지로 잰다.
  - `anomaly.payment_*_delay_minutes`: 장애를 넣은 시각부터 잰다.
  - `anomaly.payment_delay_from_first_fault_failure_max`: 첫 장애 쪽 실패가 든 5분부터 잰다. 주문이 없어 실패할 기회가 없던 시간을 빼고 본다.

### `pay_full_20m_03h_night` 지연 20분

두 번째 실패가 03:35에야 나서 데이터상 그 전에 잡으면 잡음과 구분 불가. 오탐 0%를 지키는 대가.

- 장애를 넣은 시각은 03:20이지만 그 5분엔 주문이 없었다. 첫 실패는 03:25에 1건(low), 03:30은 주문 0건, 03:35에 2건이다. 03:40 감시에서 이상이 된다.
- 첫 장애 쪽 실패(03:25)부터 재면 15분이다.

## 케이스 종류

정답은 `make_cases.py`가 shop-api 코드로 데이터를 만든 뒤(`eval_world.build`) 그 결제 기록에서 센다. 명세를 바꾸면 `uv run python domains/data/eval/make_cases.py`로 다시 만든다.

| 종류 | 케이스 | 이유 |
| --- | --- | --- |
| 결제 장애 | `pay_*` (아래 low 케이스 제외) | 길이·세기(100·50·20%)·시간대(낮·저녁·새벽)별로 잡는지와 지연을 본다 |
| 처음 보는 실패 코드 | `pay_full_20m_14h_new_code` | 분류할 수 없는 코드면 영향 숫자를 지어내지 않고 "확인할 수 없음"으로 답하는지 본다 |
| 주문 급감 | `order_drop_*` | 감소 방향도 잡는지 본다 |
| 평소 | `normal_*` | 카드 거절만 있는 평소 구간에서 오탐이 없는지 본다 |
| 세일 | `sale_*` | 주문 증가만으로 이상이라 하지 않는지 본다 |
| 빈 구간 | `empty_*` | 자료가 없으면 "이상 없음"이 아니라 "확인할 수 없음"인지 본다 |
| 잡음: 평소 타임아웃 | `noise_timeout_14h`, `noise_timeout_03h_night` | 매일 결제사 타임아웃이 가끔 1건씩 나는 평소 구간(낮·새벽)을 장애로 보지 않는지 본다. 장애 쪽 실패 절대 기준의 오탐을 재려고 넣었다 |
| 잡음: 한 번 난 타임아웃 | `noise_single_timeout_03h_night` | 새벽에 장애 쪽 실패 1건만 나고 끝나면 이상이 아닌지 본다 |
| 새벽 타임아웃 장애 | `pay_timeout_25m_03h_night` | 새벽에 장애 쪽 실패(알려진 코드 `PG_TIMEOUT`)가 여러 5분 구간 이어지면 이상으로 잡는지, 영향 숫자를 내는지 본다 |
| 새벽 약한 장애 (low 기록) | `pay_half_10m_03h_night` | 새벽 10분 50% 장애는 실패 1건이라 잡음 1건과 데이터로 구분 불가. 기록 여부로 채점. 사건(이상)이 아니어야 하고, 지표 판정이 normal 또는 unknown + severity `low` + 이유에 "장애 쪽 실패 1건"이면 맞다(`anomaly.low_recorded_rate`) |
| 새벽 약한 장애 (이상) | `pay_half_20m_03h_night` | 새벽 20분 50% 장애(03:40~04:00)로 장애 쪽 실패가 3건 나온다. 데이터로 장애라고 말할 수 있어 이상으로 잡는지 본다 |
| 판매자 | `sellers.json` (24명: 사기 9, 정상 15) | 사기 점수 등급. 정상 쪽에 경계 케이스(신규인데 정상, 세일로 저가가 많은 정상, 대량 등록하는 큰 판매자)를 넣었다. 판매자마다 shop-api 코드로 임시 DB를 만들어 `facts` 중 shop-api에 넣을 수 있는 것(가입 일수·저가 비율·24시간 등록 수)을 넣고, fraud_score 핸들러가 실제 shop-api 조회 경로로 읽는다(`eval_sellers.py`). 사업자 중복·유사 카드는 넣을 수 없어 핸들러에서 "확인할 수 없음"이다. `fraud.precision`·`recall`은 그 핸들러 결과(`level` high=사기), `fraud.conservative_precision`·`conservative_recall`은 같은 결과의 보수적 상한(`max_possible_level` high=사기), `fraud.complete_rate`는 빠진 규칙 없이 답한 비율, `fraud.rule_*`는 `facts` 전부로 낸 참고 점수다 |
