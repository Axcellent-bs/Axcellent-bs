# data 에이전트 정확도 평가

정답지(`cases/`)로 이상 탐지·영향 분석·원인 추정·사기 점수·LLM 설명을 재고, 기준값(`baseline.json`)보다 나빠졌는지 본다.

```bash
cd backend
uv run python domains/data/eval/run.py   # 결과: eval/results/latest.json
```

## 규칙

- **평가 정의 변경은 코드 수정과 별도 PR로 한다.** 평가 정의는 정답지(`cases/`, `make_cases.py`), 채점 방식(`run.py`의 `SIGNALS`·지표 계산), 데이터 생성(`eval_world.py`)이다. 같은 PR에서 둘 다 바꾸면 숫자가 좋아진 것이 코드 덕분인지 정의 덕분인지 가릴 수 없다.
- 기준값(`baseline.json`)은 나빠진 지표가 없을 때만 갱신한다. 나빠졌으면 갱신하지 않고 PR 본문에 원인을 적는다.
- 코드 변경 PR에서 지표가 나빠지면 에이전트가 baseline을 낮추지 않는다. 커밋하지 말고 보고하고, 사람이 채팅에서 허용한 경우에만 낮춘다.
- PR 본문에는 전·후 숫자를 적는다. 평균에 묻히지 않게 바뀐 케이스도 함께 적는다.
- 평가 정의를 바꾼 PR은 기준값이 나빠져도 갱신한다. 대신 PR 본문에 "정의 변경으로 인한 하락"과 나빠진 케이스를 적는다.
- 판정 코드를 고칠 때 holdout 케이스 내용을 보고 맞추지 않는다. holdout은 결과 숫자만 본다. holdout을 다시 만들 때는 seed를 바꾸고 이유를 적는다.

## holdout (처음 보는 케이스)

`cases/` 27개는 규칙을 고치며 계속 본 케이스다. 처음 보는 케이스에서도 성능이 나오는지 따로 재려고 `holdout/` 40개를 둔다. 지표 이름 앞에 `holdout.`이 붙는다.

- 생성: `uv run python domains/data/eval/make_cases.py --holdout` (`--seed`로 seed를 바꾼다)
- **seed `20261029`**, 40개 (장애 없음 20 · 장애 20)

| seed | 만든 날 | 이유 |
| --- | --- | --- |
| `20261029` | 2026-10-29 | 처음 만듦 |

- 무작위로 고르는 것
  - 시각(0~23시)
  - 장애 종류: 결제 100%·50%·20%, 타임아웃 `PG_TIMEOUT`, 주문 급감 10·30·50%
  - 길이(5~60분)
  - 세일 여부(25%, 구간 전체 2·3배)
  - 잡음 건수(0~3건, 결제사 타임아웃, 지난 7일에도 넣을지)
- 데이터는 기존 케이스와 같이 shop-api 코드로 만든다(`eval_world.build`).
- 정답은 생성 조건에서 정한다. 결제 장애는 실제로 만들어진 장애 쪽 실패 수로 다듬는다.
  - 1건뿐이면 지금 정의대로 low 기록으로 채점한다.
  - 0건이면(주문이 없어 실패할 기회가 없었음) 데이터에 흔적이 없어 이상 아님으로 본다.
- 케이스마다 생성 조건이 `holdout` 필드에 있다. 결과 파일에는 `holdout.wrong`(틀린 항목)과 `holdout.conditions`가 남는다. `run.py`는 화면에 틀린 항목 수만 보여 준다.

## 평가와 감시의 차이 (감시 재현 지표)

- 평가의 이상 탐지 채점(탐지율·오탐률)은 케이스 구간 전체를 **한 번** 판정한다.
- 실제 주기 감시(`monitor.py`)는 **5분마다 최근 구간**을 판정하고, 이상이면 이벤트를 낸다. 구간 전체로 보면 정상이어도, 감시 시점마다 잘라 보면 잠깐 이상이 나올 수 있다. 예를 들어 잡음 1건 직후의 짧은 구간이 그렇다.
- 그래서 감시를 재현하는 지표를 따로 둔다. 모든 케이스를 5분마다 최근 15분으로, 감시와 같은 판정 함수(`detect.judge_window`)와 같은 지표로 판정한다.
  - `anomaly.monitor_false_alarm_count`: 정답이 이상 아님인 케이스에서 감시가 이상을 낸 횟수 (감시마다 센다)
  - `anomaly.monitor_false_alarm_cases`: 그런 케이스 수
  - 케이스별 경보 시각은 `results/latest.json`의 `cases[].anomaly.monitor_alarms`에 남는다.
- 지연은 두 가지로 잰다.
  - `anomaly.payment_*_delay_minutes`: 장애를 넣은 시각부터 잰다.
  - `anomaly.payment_delay_from_first_fault_failure_max`: 첫 장애 쪽 실패가 든 5분부터 잰다. 주문이 없어 실패할 기회가 없던 시간을 빼고 본다.

### `pay_full_20m_03h_night` 지연 20분

두 번째 실패가 03:35에야 나서 데이터상 그 전에 잡으면 잡음과 구분 불가. 오탐 0%를 지키는 대가.

- 장애를 넣은 시각은 03:20이지만 그 5분엔 주문이 없었다. 첫 실패는 03:25에 1건(low), 03:30은 주문 0건, 03:35에 2건이다. 03:40 감시에서 이상이 된다.
- 첫 장애 쪽 실패(03:25)부터 재면 15분이다.

## 케이스 종류

정답은 `make_cases.py`가 shop-api 코드로 데이터를 만든 뒤(`eval_world.build`) 그 결제 기록에서 센다. 명세를 바꾸면 `uv run python domains/data/eval/make_cases.py`로 다시 만든다.

| 종류 | 케이스 | 이유 |
| --- | --- | --- |
| 결제 장애 | `pay_*` (아래 low 케이스 제외) | 길이·세기(100·50·20%)·시간대(낮·저녁·새벽)별로 잡는지와 지연을 본다 |
| 처음 보는 실패 코드 | `pay_full_20m_14h_new_code` | 분류할 수 없는 코드면 영향 숫자를 지어내지 않고 "확인할 수 없음"으로 답하는지 본다 |
| 주문 급감 | `order_drop_*` | 감소 방향도 잡는지 본다 |
| 평소 | `normal_*` | 카드 거절만 있는 평소 구간에서 오탐이 없는지 본다 |
| 세일 | `sale_*` | 주문 증가만으로 이상이라 하지 않는지 본다 |
| 빈 구간 | `empty_*` | 자료가 없으면 "이상 없음"이 아니라 "확인할 수 없음"인지 본다 |
| 잡음: 평소 타임아웃 | `noise_timeout_14h`, `noise_timeout_03h_night` | 매일 결제사 타임아웃이 가끔 1건씩 나는 평소 구간(낮·새벽)을 장애로 보지 않는지 본다. 장애 쪽 실패 절대 기준의 오탐을 재려고 넣었다 |
| 잡음: 한 번 난 타임아웃 | `noise_single_timeout_03h_night` | 새벽에 장애 쪽 실패 1건만 나고 끝나면 이상이 아닌지 본다 |
| 새벽 타임아웃 장애 | `pay_timeout_25m_03h_night` | 새벽에 장애 쪽 실패(알려진 코드 `PG_TIMEOUT`)가 여러 5분 구간 이어지면 이상으로 잡는지, 영향 숫자를 내는지 본다 |
| 새벽 약한 장애 (low 기록) | `pay_half_10m_03h_night` | 새벽 10분 50% 장애는 실패 1건이라 잡음 1건과 데이터로 구분 불가. 기록 여부로 채점. 사건(이상)이 아니어야 하고, 지표 판정이 normal 또는 unknown + severity `low` + 이유에 "장애 쪽 실패 1건"이면 맞다(`anomaly.low_recorded_rate`) |
| 새벽 약한 장애 (이상) | `pay_half_20m_03h_night` | 새벽 20분 50% 장애(03:40~04:00)로 장애 쪽 실패가 3건 나온다. 데이터로 장애라고 말할 수 있어 이상으로 잡는지 본다 |
| 판매자 | `sellers.json` | 사기 점수 등급. 판매자마다 shop-api 코드로 임시 DB를 만들어 `facts` 중 shop-api에 넣을 수 있는 것(가입 일수·저가 비율·24시간 등록 수)을 넣고, fraud_score 핸들러가 실제 shop-api 조회 경로로 읽는다(`eval_sellers.py`). 사업자 중복·유사 카드는 넣을 수 없어 핸들러에서 "확인할 수 없음"이다. `fraud.precision`·`recall`은 그 핸들러 결과, `fraud.rule_*`는 `facts` 전부로 낸 참고 점수다 |
