# 캠페인 예산 논의에 고객 반응 근거 붙이기: 책별 집계 A2A 연결 (설계)

상태: 초안(코드 없음). 제안: 배병환(고객지원), 2026-11-14. 마케팅·재무·기획·데이터 담당과 호출 모양을 맞춰야 한다.
앞 단계: `support-book-issue-stats-design.md`(`book_issue_stats` 완성, #1096~#1100).

## 목적
2026-11-13 멘토링: 기능을 더하지 말고 부서 AI가 A2A로 같이 일하는 장면을 보여 준다. 대표 사례는 **캠페인 예산**
(마케팅·데이터·재무·기획이 함께 논의·결정). 예: 아재개그 쇼츠 조회수가 잘 나오면 그쪽 제작비를 올린다.

여기에 고객지원이 줄 수 있는 근거는 하나다: **"이 책(상품)은 팔리지만 클레임·불량·문의가 많다."**
예산을 올리기 전에 이 신호가 같이 보이면, 불만 많은 책에 광고비를 올리는 결정을 막을 수 있다.
새 기능을 만드는 게 아니라 이미 있는 `book_issue_stats`를 이미 있는 두 호출 길에 얹는 설계다.

## 원칙
- 고객지원은 숫자(클레임·불량·반품·환불·문의·비율)와 "못 읽은 것"을 낸다. **막거나 승인하지 않는다.**
  재무도 이미 비용을 승인·반려하지 않고 의견만 낸다(2026-11-06). 판단은 받는 쪽과 사람이 한다.
- 새 skill을 만들지 않는다. `book_issue_stats`(read, 요청자에 `data` 포함)를 쓰고, 필요한 만큼 요청자만 늘린다.
- 계약은 `shared/contracts`에 **추가만**(선택 필드). 모르는 값은 `None`+이유, 지어내지 않는다.
- 고객 이름·구매자 ID·글은 넘기지 않는다 (집계 숫자와 상품 ID·제목뿐).
- 고객지원에 닿지 못하면 막지 않고 "고객 반응 근거 없음"으로 계속한다 (재무에 닿지 못하면 멈추는
  fail-closed와 다르다: 이건 근거 하나가 빠지는 것이지 승인 관문이 아니다).

## 지금 있는 호출 길 (확인한 것)
| 길 | 위치 | 상품 정보 |
|---|---|---|
| 기획 → 마케팅 | 기획이 사람이 확정한 제안을 `receive_campaign_brief`(A)로 보낸다. `CampaignBriefInput`: `facts: list[InsightFact]`(데이터 근거), `products: list[str]` | 상품 **이름**(문자열). 상품 ID 없음 |
| 마케팅 → 재무 | 마케팅 `start_campaign`이 재무 `review_campaign_budget`(read)에 묻고 `execute("start_campaign")`. 입력 `CampaignBudgetReviewInput`: `campaign_id`, `campaign_name`, `channel`, `requested_krw` | **상품 정보 없음**. 재무 의견은 예산 규칙만으로 낸다 |
| 데이터 → 기획 | 데이터 인사이트 브리프(`trend_insight_brief`)가 `InsightFact`를 기획에 준다 | — |
| 고객지원 → 데이터 | 고객의 소리 일일 보고(`receive_idea_report`), `book_issue_stats` 요청자에 `data`가 이미 들어 있음 | 상품 ID |

빈칸 둘: ① 기획안·예산 요청에 **상품 ID가 없어** 책별 집계와 이어 붙일 열쇠가 없다. ② 재무 예산 의견이 상품 신호를 모른다.

## 연결 안 (세 갈래, 앞에서부터 가볍다)

### A. 기획안에 "고객 반응" 근거를 한 줄 더하기 (기획·데이터 쪽, 가장 가볍다)
데이터가 브리프에 `InsightFact`를 만들 때 고객지원 `book_issue_stats`를 A2A로 읽어(이미 `data` 허용) 제안 상품의
고객 반응을 한 줄 더한다.
- `label`: "OO 책 클레임·문의 (최근 30일)", `value`: "클레임 비율 7.5% · 불량 3건", `source`: `book_issue_stats`.
- 기획안·마케팅은 계약을 바꾸지 않아도 `facts`로 이미 받는다 (**계약 변경 없음**).
- 상품 이름 → 상품 ID 매핑은 데이터가 판매 서버 상품 목록으로 한다 (열린 질문 1).
- 단점: 브리프를 만드는 시점의 숫자라서 기획안이 확정될 때까지 낡을 수 있다 → `value`에 기준 기간·시각을 적는다.

### B. 재무 예산 의견에 상품 신호 반영 (사례의 핵심: "제작비를 올릴까")
`CampaignBudgetReviewInput`에 **선택** 칸 `product_ids: list[str] = []`를 추가하고, 마케팅 `start_campaign`이 기획안의
상품 ID를 실어 보낸다. 재무가 `review_campaign_budget` 안에서 고객지원 `book_issue_stats`(요청자에 `finance` 추가)를
읽어, 상품에 클레임 비율·불량이 높으면 의견에 이유를 더한다.
- 규칙은 재무 설정(`finance_rules.toml`)에 둔다: 예) 클레임 비율이 기준 이상이면 `opinion`을 한 단계 낮추고
  `reasons`에 "OO 책 클레임 비율 7.5% (기준 5%)"를 적는다. 기준값은 재무·마케팅이 정한다 (열린 질문 3).
- 신호를 못 읽으면(`missing`, 판매 수량 못 읽음 등) 의견을 바꾸지 않고 `reasons`에 "고객 반응 근거 없음"만 적는다.
- 재무가 고객지원을 부르는 새 A2A 길이 생긴다 (`allowed_requesters`에 `finance` 추가, 읽기라 안전 관문 없음).
- 계약: `CampaignBudgetReviewInput.product_ids`(선택)만 추가. 옛 요청은 그대로 받는다.

### C. 마케팅이 시작 전에 직접 확인 (재무를 건드리지 않는 대안)
마케팅 `start_campaign`이 재무에 묻기 전에 고객지원 `book_issue_stats`를 읽어 결과를 `output.review` 옆
`output.customer_signal`에 그대로 싣는다. 의견이 아니라 숫자만 돌려주고 판단은 사람에게 둔다.
- 재무 계약을 바꾸지 않는다. 마케팅 쪽 변경만 필요하다 (`allowed_requesters`에 `marketing` 추가).
- 단점: 재무의 예산 의견에는 반영되지 않는다 (사람이 두 숫자를 같이 본다).

## 추천
**A → B 순서.** A는 계약 변경이 없고 데이터 한 곳만 바꾸면 보인다. B는 멘토가 말한 "여러 부서가 같이 결정하는 장면"
(마케팅이 묻고, 재무가 고객지원 근거를 읽어 의견을 내고, 사람이 정한다)을 가장 직접 보여 준다. C는 B가 어려울 때 대안이다.
세 안 모두 새 skill은 없고, 고객지원 쪽 변경은 `allowed_requesters` 추가와 문서뿐이다.

## 구현 순서 (합의되면)
1. **상품 ID 열쇠**: 기획안 `products`(이름)를 상품 ID로 바꾸는 방법 합의 (데이터가 판매 서버 상품 목록으로 매핑 vs 기획안에 `product_ids` 추가).
2. **A**: 데이터가 `book_issue_stats`를 읽어 브리프 `InsightFact`로 만든다 (고객지원 변경 없음).
3. **B**: 계약 `product_ids` 추가 PR → 마케팅이 실어 보내기 → 재무가 읽고 의견에 반영 → 고객지원 카드에 `finance` 요청자 추가.
4. 테스트는 각 부서 작업이 끝난 뒤 한 번에, 실제 모드에서 "불만 많은 책 예산 요청 → 의견에 이유가 붙는다" 한 장면을 확인한다.

## 열린 질문
1. 기획안의 `products`가 이름(문자열)이다. 상품 ID 매핑을 누가 어디서 하나? 같은 이름의 상품이 둘이면?
2. A·B 중 무엇부터? 멘토 시연에는 B가 더 잘 보이지만 재무·마케팅 변경이 필요하다. 담당자는?
3. 클레임 비율·불량 기준값(예: 5%)과 의견을 얼마나 낮출지 — 재무·마케팅이 정한다. 판매가 적은 책(예: 10권 미만)은 비율이 흔들려서 최소 판매 수량 기준이 필요하다.
4. 캠페인 예산 화면(재무 "캠페인 재무" → "캠페인 예산"으로 이름 변경 예정)에 이 근거를 보일지, 보인다면 고객지원 근거 한 줄의 모양.
5. 비율의 한계를 받는 쪽이 알아야 한다: 접수 기간 기준이라 1을 넘을 수 있고, 한 번에 3만 주문이 넘는 기간은 판매 수량을 못 낸다 (`missing`로 알림).
