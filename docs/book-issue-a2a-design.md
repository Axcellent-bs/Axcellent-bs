# 캠페인 예산 논의에 고객 반응 근거 붙이기: 책별 집계 A2A 연결 (설계)

상태: **A안은 구현·머지됨(2026-11-16~17), B안은 미정**. 제안: 배병환(고객지원), 2026-11-14. 마케팅·재무·기획·데이터 담당과 호출 모양을 맞춰야 한다.
2026-11-16 갱신: 데이터(재현)·운영(재헌 11/14)·예진 의견을 반영했다. **A안 합의**, 상품 ID는 **`product_ids`(선택)로 기획안까지 싣는 쪽으로 합의**,
운영 쪽 조건(카드 두 곳 맞추기·캐시·호출 상한)이 정해졌다 (아래 "합의와 운영 의견"). 남은 것: B안 담당, 계약 PR을 누가 올릴지, 기준값.
2026-11-17 갱신: **A안과 상품 ID 열쇠가 구현됐다.** 데이터 #1125(브리프 인사이트마다 연결 상품의 고객 반응 숫자를 근거로 담는다), 기획 #1128(근거 줄 `source=trend_insight_brief:book_issue_stats`, `ReceiveInsightInput`·`CampaignBriefInput`에 선택 칸 `product_ids`). 고객지원은 데이터 요청으로 #1129(`product_ids`로 물은 상품은 0건이어도 한 행씩), #1145(판매 수량을 판매 서버 `sales-summary`로 읽고 7일씩·5분 캐시, 옛 서버는 주문 목록 폴백), #1147(사유별 클레임 수 `claims_by_reason`)을 더했다. 남은 것은 **B안(재무 예산 의견에 반영)**의 담당과 기준값이다.
앞 단계: `support-book-issue-stats-design.md`(`book_issue_stats` 완성, #1096~#1100).

## 목적
2026-11-13 멘토링: 기능을 더하지 말고 부서 AI가 A2A로 같이 일하는 장면을 보여 준다. 대표 사례는 **캠페인 예산**
(마케팅·데이터·재무·기획이 함께 논의·결정). 예: 아재개그 쇼츠 조회수가 잘 나오면 그쪽 제작비를 올린다.

여기에 고객지원이 줄 수 있는 근거는 하나다: **"이 책(상품)은 팔리지만 클레임·불량·문의가 많다."**
예산을 올리기 전에 이 신호가 같이 보이면, 불만 많은 책에 광고비를 올리는 결정을 막을 수 있다.
새 기능을 만드는 게 아니라 이미 있는 `book_issue_stats`를 이미 있는 두 호출 길에 얹는 설계다.

## 원칙
- 고객지원은 숫자(클레임·불량·반품·환불·문의·비율)와 "못 읽은 것"을 낸다. **막거나 승인하지 않는다.**
  재무도 이미 비용을 승인·반려하지 않고 의견만 낸다(2026-11-06). 판단은 받는 쪽과 사람이 한다.
- 새 skill을 만들지 않는다. `book_issue_stats`(read, 요청자에 `data` 포함)를 쓰고, 필요한 만큼 요청자만 늘린다.
- 계약은 `shared/contracts`에 **추가만**(선택 필드). 모르는 값은 `None`+이유, 지어내지 않는다.
- 고객 이름·구매자 ID·글은 넘기지 않는다 (집계 숫자와 상품 ID·제목뿐).
- 고객지원에 닿지 못하면 막지 않고 "고객 반응 근거 없음"으로 계속한다 (재무에 닿지 못하면 멈추는
  fail-closed와 다르다: 이건 근거 하나가 빠지는 것이지 승인 관문이 아니다).

## 지금 있는 호출 길 (확인한 것)
| 길 | 위치 | 상품 정보 |
|---|---|---|
| 기획 → 마케팅 | 기획이 사람이 확정한 제안을 `receive_campaign_brief`(A)로 보낸다. `CampaignBriefInput`: `facts: list[InsightFact]`(데이터 근거), `products: list[str]` | 상품 **이름**(문자열). 상품 ID 없음 |
| 마케팅 → 재무 | 마케팅 `start_campaign`이 재무 `review_campaign_budget`(read)에 묻고 `execute("start_campaign")`. 입력 `CampaignBudgetReviewInput`: `campaign_id`, `campaign_name`, `channel`, `requested_krw` | **상품 정보 없음**. 재무 의견은 예산 규칙만으로 낸다 |
| 데이터 → 기획 | 데이터 인사이트 브리프(`trend_insight_brief`)가 `ReceiveInsightInput`(`facts: list[InsightFact]`, `products: list[str]` 관련 회사 상품 **이름**, `audience` 타깃 연령대)를 기획에 준다 | 이름만 (아래) |
| 데이터 내부 | `product_link`가 소재를 회사 실제 상품과 잇는다 (판매 서버 상품 목록 `GET /api/shop/products`를 읽어 이름·카테고리 일치와 임베딩 유사도). 결과 `LinkedProduct`에 `product_id`·이름·근거(`match`, `reason`)가 있다 | **상품 ID가 있다** |
| 고객지원 → 데이터 | 고객의 소리 일일 보고(`receive_idea_report`), `book_issue_stats` 요청자에 `data`가 이미 들어 있음 | 상품 ID |

빈칸 둘: ① 기획안·예산 요청에 **상품 ID가 없어** 책별 집계와 이어 붙일 열쇠가 없다. ② 재무 예산 의견이 상품 신호를 모른다.

①은 새로 만들 문제가 아니다. 데이터의 `product_link`가 소재를 상품과 이을 때 `LinkedProduct.product_id`를 이미 갖고 있는데,
데이터가 기획에 넘기는 `ReceiveInsightInput.products`가 이름(문자열)만 싣는 곳에서 ID가 떨어진다. 즉 **ID는 데이터에 있고,
데이터 → 기획 넘기기에서 이름으로 줄어든다.** 이름→ID 매핑을 새로 만들 필요 없이 이 ID를 계속 들고 가면 된다
(새 이름 매칭은 이름이 겹치거나 바뀌면 틀린다).

## 연결 안 (세 갈래, 앞에서부터 가볍다)

### A. 기획안에 "고객 반응" 근거를 한 줄 더하기 (기획·데이터 쪽, 가장 가볍다)
데이터가 브리프에 `InsightFact`를 만들 때 고객지원 `book_issue_stats`(서비스 이름은 `claims`)를 A2A로 읽어(이미 `data` 허용) 제안 상품의
고객 반응을 한 줄 더한다.
- `label`: "OO 책 클레임·문의 (최근 30일)", `value`: "클레임 비율 7.5% · 불량 3건", `source`: `book_issue_stats`.
- 기획안·마케팅은 `InsightFact`(`facts`)를 이미 받으므로 **이 줄 자체는 계약 변경이 없다**. **합의(재현 11/16): 데이터가 찬성했고** 클레임 비율·불량·파손 건수를 붙이며, "불만 많은 책은 이벤트 후보에서 뺀다"는 근거로도 쓴다.
- 상품 ID는 데이터가 `product_link`로 이미 구한 `LinkedProduct.product_id`를 쓴다 (이름에서 다시 찾지 않는다). **재현 님 추천을 받아** 이 ID를 `product_ids`(선택)로 기획안까지 함께 싣는다(아래 구현 순서 1). 아래 부록 참고.
- 단점: 브리프를 만드는 시점의 숫자라서 기획안이 확정될 때까지 낡을 수 있다 → `value`에 기준 기간·시각을 적는다.
- **구현된 모양(2026-11-16, #1125·#1128)**: 근거 줄 예시는 `고객 반응 · 고양이 그림책 (최근 한 달)` / `클레임 3건 · 판매 120권 중 2.5%`다. 데이터는 `period=month`, `product_ids`=브리프 연결 상품(최대 100), `include_inquiries=false`로 한 브리프에서 한 번만 부르고 결과를 하루(한국 날짜) 캐시한다. **판매 5권 미만·판매 수량 못 읽음·호출 실패면 근거에 넣지 않고 이유를 `evidence.missing`에 남긴다**(열린 질문 3의 "최소 판매 수량"은 데이터가 5권으로 정했다). 클레임이 없어 집계에 안 나오던 상품은 #1129로 0건 행이 와서 "고객 반응 없음"이 아니라 "클레임 0건"으로 보인다.

### B. 재무 예산 의견에 상품 신호 반영 (사례의 핵심: "제작비를 올릴까")
`CampaignBudgetReviewInput`에 **선택** 칸 `product_ids: list[str] = []`를 추가하고, 마케팅 `start_campaign`이 기획안의
상품 ID(`CampaignBriefInput.product_ids`, 아래 합의)를 실어 보낸다. 재무가 `review_campaign_budget` 안에서 고객지원 `book_issue_stats`(요청자에 `finance` 추가)를
읽어, 상품에 클레임 비율·불량이 높으면 의견에 이유를 더한다.
- 규칙은 재무 설정(`finance_rules.toml`)에 둔다: 예) 클레임 비율이 기준 이상이면 `opinion`을 한 단계 낮추고
  `reasons`에 "OO 책 클레임 비율 7.5% (기준 5%)"를 적는다. 기준값은 재무·마케팅이 정한다 (열린 질문 3).
- 신호를 못 읽으면(`missing`, 판매 수량 못 읽음 등) 의견을 바꾸지 않고 `reasons`에 "고객 반응 근거 없음"만 적는다.
- 재무가 고객지원을 부르는 새 A2A 길이 생긴다 (`allowed_requesters`에 `finance` 추가, 읽기라 안전 관문 없음).
- 계약: `CampaignBudgetReviewInput.product_ids`(선택)만 추가. 옛 요청은 그대로 받는다.

### C. 마케팅이 시작 전에 직접 확인 (재무를 건드리지 않는 대안)
마케팅 `start_campaign`이 재무에 묻기 전에 고객지원 `book_issue_stats`를 읽어 결과를 `output.review` 옆
`output.customer_signal`에 그대로 싣는다. 의견이 아니라 숫자만 돌려주고 판단은 사람에게 둔다.
- 재무 계약을 바꾸지 않는다. 마케팅 쪽 변경만 필요하다 (`allowed_requesters`에 `marketing` 추가).
- 단점: 재무의 예산 의견에는 반영되지 않는다 (사람이 두 숫자를 같이 본다).

## 합의와 운영 의견 (재헌 11/14, 예진·재현 11/16)
- **재헌 님 (251 운영, 2026-11-14 13:12)**: 방향이 맞다(고객지원은 숫자와 못 읽은 것만 내고 막거나 승인하지 않는다).
  1. `allowed_requesters`를 늘리는 변경은 **재시작이 필요 없다**: dev 머지 뒤 자동 배포가 백엔드를 다시 띄운다. 다만 **서비스 카드와 도메인 카드를 같이 맞춰야 한다**(#1045에서 `FORBIDDEN_SKILL`이 났던 부분). B안(`finance` 요청자)·C안(`marketing` 요청자)을 구현할 때 `backend/services/*/agent-card.json`과 `backend/domains/support/agent-card.json`을 한 PR에서 같이 고친다.
  2. 판매 수량 주문 조회가 251에서 부담인지는 주문 건수를 세어 봐야 안다. **기간·상품별 결과를 몇 분 캐시**하는 쪽이 안전하다.
  3. 재무가 예산 요청마다 부르면 호출이 늘어난다: **요청당 호출 상한과 같은 상품·기간 재호출 방지(캐시)를 같이 둔다**(재헌 님 찬성).
  4. 서비스끼리 내부 호출이라 **nginx 허용 경로는 필요 없다.** 예산 화면에서 부르는 새 쓰기 경로가 생기면 그때 알린다.
- **예진 님 (11/16, Catbooks-demo #12 리뷰)**: 251 `shop.db`는 주문이 30만 건쯤이라 93일을 한 번에 읽으면 몇 초 동안 연결을 잡고 결제도 기다려 결제 모니터가 지연으로 잡을 수 있다 → 고객지원은 **짧게 나눠 읽거나 몇 분 캐시**한다. 연령대는 주문 시점이 아니라 지금 `buyers.age_band`로 묶인다.
- **판매 수량 읽기 전환**: 새 레포 판매 서버에 `GET /api/shop/sales-summary`(Catbooks-demo #12, 상품·연령대·분류별, 93일 상한, `gross_qty`=클레임 비율 분모, `net_qty`=전액 환불 제외)가 들어갔다. 판매 서버가 새 레포로 뜬 뒤 `book_issue_stats`가 주문 목록 대신 이 경로를 읽는다(3만 주문 상한이 사라짐). 옛 판매 서버에는 경로가 없어 404·연결 실패면 기존 주문 목록 읽기로 되돌아간다. 읽을 때는 7일 정도로 나눠 부르고 몇 분 캐시한다.
- **고객지원 쪽에서 둘 것**: `book_issue_stats` 결과를 (상품 ID, 기간) 키로 몇 분 캐시하고, 요청당 상품 수 상한을 둔다(상한 값은 재무·재헌 님과 정한다). 재무·데이터가 같은 상품을 짧은 간격으로 다시 부르면 캐시를 돌려준다.
- **데이터 쪽(재현 님)**: A안 구현은 데이터가 맡는다. 데이터가 "20대 여성이 좋아하는 책" 같은 고객·시장 분석을 만드는 중이라, 판매 서버에 구매자 성별·직업과 상품 장르가 필요하다고 요청했다(`age_band`와 같은 방식으로 Catbooks-demo에서 같이 맞추기로. 연령별 파이프라인 설계 `age-bestseller-pipeline-design.md` 참고).

## 추천
**A → B 순서.** A는 계약 변경이 없고 데이터 한 곳만 바꾸면 보인다. B는 멘토가 말한 "여러 부서가 같이 결정하는 장면"
(마케팅이 묻고, 재무가 고객지원 근거를 읽어 의견을 내고, 사람이 정한다)을 가장 직접 보여 준다. C는 B가 어려울 때 대안이다.
세 안 모두 새 skill은 없고, 고객지원 쪽 변경은 `allowed_requesters` 추가와 문서뿐이다.

## 구현 순서 (1·2는 2026-11-16~17 구현됨, 3·4는 남음)
1. **상품 ID 열쇠 (합의됨, 재현 11/16 → 구현됨 #1128)**: 이름 매칭을 새로 만들지 않고, 데이터가 이미 가진 `LinkedProduct.product_id`를 `product_ids`(선택, 상품 ID 문자열 목록)로 **기획안까지 싣는다**. `products`(이름)는 그대로 두고 나란히 넘긴다. 계약 변경은 추가만이다: `planning.py`의 `ReceiveInsightInput`(데이터→기획)과 `CampaignBriefInput`(기획→마케팅)에 선택 칸 `product_ids`. 데이터는 인사이트를 보낼 때 관련 상품 ID를 같이 싣는다. **누가 계약 PR을 올릴지 미정**(데이터가 `ReceiveInsightInput`의 보내는 쪽이라 재현 님이 자연스럽고, 필요하면 고객지원이 올린다).
2. **A (합의됨 → 구현됨 #1125·#1128)**: 데이터가 `product_ids`의 상품마다 `book_issue_stats`를 읽어 브리프 `InsightFact`로 만든다 (고객지원 변경 없음, 요청자에 `data`는 이미 허용). 읽을 때 아래 "합의와 운영 의견"의 캐시·호출 상한을 지킨다.
3. **B**: **순서가 중요하다**(`AxModel`이 `extra="forbid"`라 새 칸을 채워 보내는 쪽이 받는 쪽보다 먼저 배포되면 거절한다, 예진 11/17):
   ① 계약 PR — `CampaignBudgetReviewInput.product_ids`(선택) 추가, 그리고 **`BookIssueInput`·`BookIssueReport`를 도메인(`backend/domains/support/.../book_issue_schemas.py`)에서 `shared/contracts`로 옮긴다(추가)**. `domains`끼리 import하지 않는 규칙 때문에 재무가 이 응답을 읽으려면 계약에 있어야 한다. (A안은 데이터가 자기 모델로 읽고 `extra="ignore"`라 이미 동작하지만, B는 계약이 필요하다.)
   ② 재무가 새 칸을 읽도록 고친다 → ③ 마케팅이 새 칸을 채워 보낸다 → ④ 고객지원 카드에 `finance` 요청자를 더한다. 카드는 **`backend/services/claims/agent-card.json`(`book_issue_stats`는 `claims` 서비스에 있다)과 `backend/domains/support/agent-card.json` 두 곳을 같이** 고친다(재무가 `call_agent` 대상을 `claims`로 불러야 한다).
4. 테스트는 각 부서 작업이 끝난 뒤 한 번에, 실제 모드에서 "불만 많은 책 예산 요청 → 의견에 이유가 붙는다" 한 장면을 확인한다.

## 부록: A안의 `InsightFact` 모양 (실제 출력 기준)
2026-11-14에 로컬 실제 모드에서 판매 서버에 실제 주문 15건·클레임 4건·문의 3건을 접수하고 `book_issue_stats`(`period: week`)를
데이터 토큰으로 호출한 결과다. 숫자는 시험 접수 4건이라 통계로서 의미는 없고 **출력 모양과 변환**을 보이려는 용도다.

| 상품 | 클레임 | 불량·파손 등 | 문의(주문 단위) | 판매 수량 | 클레임 비율 |
|---|---|---|---|---|---|
| 파이썬 입문서 (`prd_0001`) | 3건 | 3건 | 2건 | 10권 | 30.0% |
| 데이터 분석 실전 (`prd_0002`) | 1건 | 0건 | 1건 | 8권 | 12.5% |

위 출력 한 줄(`BookIssueRow`)을 데이터가 기획 `InsightFact`(`label` ≤120자, `value` ≤80자, `source` ≤60자)로 바꾸면:

```json
{
  "label": "파이썬 입문서 클레임·문의 (최근 7일, 판매 10권 기준)",
  "value": "클레임 비율 30.0% · 클레임 3건(불량 등 3건) · 문의 2건",
  "source": "book_issue_stats",
  "link": null
}
```

변환 규칙(데이터가 코드로 한다):
- `label`: 상품 이름·기간·판매 수량. `value`: 비율과 건수. 문장은 `BookIssueRow.reason`(코드가 만든 한 줄)을 줄여 쓸 수 있다.
- 비율(`claim_rate`)이 `None`이면 건수만 쓰고 이유를 덧붙인다 (`missing`의 문장). 0이나 "문제 없음"으로 바꾸지 않는다.
- `sales_read=false`·`inquiries_read=false`이면 그 칸이 없다고 `value`에 적는다 ("판매 수량 못 읽음").
- 비율은 접수 기간 기준이라 1을 넘을 수 있다(`missing`에 있음). 판매가 적은 책(예: 10권 미만)은 비율이 흔들리니 `value`에
  판매 수량을 같이 보인다. 최소 판매 수량 기준은 재무·마케팅이 정한다 (열린 질문 3).
- 고객지원 집계가 오지 않으면(닿지 못함) `InsightFact`를 만들지 않는다. 근거 없는 줄을 지어내지 않는다.
- 값은 숫자·건수뿐이고 고객 이름·구매자 ID·글은 들어가지 않는다.
