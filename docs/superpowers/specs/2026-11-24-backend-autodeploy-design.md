# 운영 서버 백엔드 자동 배포 설계 초안

- 상태: **초안 — 사람 확인 전. 아무것도 설치·변경하지 않았다.**
- 작성일: 2026-11-24
- 대상: Tencent 운영 서버의 `axcellent-backend` 서비스
- 근거: 2026-11-24 서버 읽기 전용 확인(스크립트·정책·감사 로그)과 `origin/dev` `d74057a9` 기준 레포
- 시각 표기: 서버 시계는 CST(UTC+8)이고 한국 시간(KST)보다 1시간 늦다. 이 문서의 시각은 따로 적지 않으면 KST다.

## 1. 요구사항 (재현 님 제안 5개)

| # | 조건 |
|---|---|
| 1 | dev 최신 커밋의 CI(`ci`·`backend`)가 초록일 때만 배포 |
| 2 | 태윤 님의 `deploy-bundle` 게이트를 그대로 쓰고 #소통에 자동 공지 |
| 3 | 백엔드 서비스만 재시작. 배포 뒤 헬스 체크(정책 URL 19개)가 실패하면 직전 버전으로 되돌림 |
| 4 | PR 본문에 "배포 메모"(서버 설정·DB 이관·nginx)가 있으면 자동 배포하지 않고 알림만 |
| 5 | 사람 승인 대기·긴 작업 중이면 재시작을 미룸. 배포 시간은 9~22시 |

추가 제약: GitHub-hosted 러너와 클라우드 세션을 새로 쓰지 않는다. 판단과 실행은 모두 서버 안에서 한다.

## 2. 현재 구조 (확인한 사실)

### 2.1 프런트·홍보 자동 배포 `ax-autodeploy`

- `/usr/local/sbin/ax-autodeploy`(레포 원본 `docs/ops/autodeploy/ax-autodeploy`)를 `ax-autodeploy.timer`가 끝난 뒤 90초마다 부른다. `ubuntu` 계정으로 돈다.
- 빌드 전용 트리 `/opt/axcellent/autodeploy-src`에서만 fetch·빌드한다. 운영 트리는 건드리지 않는다.
- 기준 커밋은 `/var/lib/ax-autodeploy/last-deployed-ref`, 중복 실행 방지는 같은 폴더의 `lock`(flock)이다.
- `backend/` 변경이 있으면 `backend-changed: manual deploy needed` 로그만 남긴다.
- **CI 확인은 지금 꺼져 있다.** 토큰 파일 `/etc/ax-autodeploy/gh-readonly-token`이 없어서 로그에 `ci-check=off`로 찍힌다.
- **게이트의 정지 표시도 연결돼 있지 않다.** 정책에 `[autodeploy]` 섹션이 없어 `autodeploy-pause`가 동작하지 않는다.
- 서버에 `gh`는 없다. `curl`·`jq`·`python3`은 있다.

### 2.2 게이트 `ax-gate` (v0.3.0)

`/usr/local/sbin/ax-gate` 한 파일에 세 동작이 모두 들어 있다(레포 원본 `docs/ops/ssh-gate/ops-gate.sh`). 정책은 `/etc/ax-gate/policy.toml`, 감사 로그는 `/var/log/ax-gate/audit.log`다.

| 동작 | 실제로 하는 일 | 하지 않는 일 |
|---|---|---|
| `deploy-bundle <SHA>` | 운영 트리를 그 SHA로 앞으로 감기(ff) + 프런트 두 곳 재빌드·교체 + 번들 토큰 검사. 직전 HEAD를 `deploy-prev-head.bak-before-<SHA8>`에 남김 | 백엔드 재시작, `uv sync`. 뒤로 가는 SHA는 거부 |
| `restart-backend <SHA> --ack-data-loss` | 운영 트리 HEAD가 그 SHA인지 확인 → sqlite·`.data` 백업 → `systemctl restart` → health 19개가 모두 200이 될 때까지 최대 180초 대기 | 코드 이동, `uv sync`, 실패 시 되돌림 |
| `rollback-bundle <SHA>` | 프런트 번들만 그 SHA 배포 직전으로 복원 | **코드(운영 트리)는 그대로 둔다.** 스크립트가 "코드 롤백은 게이트에 없다"고 출력한다 |

- 신원은 OS 계정이다. 계정별 SSH 강제 명령으로 들어오고, 뒷단은 `axgate` 그룹만 `sudo`로 부를 수 있다.
- 세 동작 모두 `--announced`가 필요하다. 게이트는 슬랙에 글을 올리지 않는다. 문안만 만들어 주고 "올렸다"는 확인만 받는다.
- 실행 중 중복은 `/run/lock/ax-gate.run`으로 막고, 배포 금지 잠금은 `/etc/ax-gate/deploy.lock`이다.
- 어제(11/23) 태윤 님의 수동 배포는 `deploy-bundle` 약 70초, `restart-backend` 약 25~60초였다.
- `restart-backend`는 매번 `shop.db`(약 475MiB)를 포함해 백업을 뜨고 5세트를 보관한다.

### 2.3 그 밖에 확인한 것

- 운영 트리 HEAD는 `8dd9039b`, dev는 `d74057a9`다. 백엔드 9개 파일이 아직 배포되지 않았다.
- `/home/ubuntu/restart-be.sh`는 게이트를 거치지 않고 `sudo systemctl restart`를 직접 한다. 오늘 12:16(KST)의 재시작은 감사 로그에 없다. 게이트 밖 재시작이 실제로 일어나고 있다.
- `ubuntu` 계정은 비밀번호 없는 전체 sudo를 가진다.
- 서버에 슬랙 웹훅 설정은 없다.
- 레포에 PR 템플릿과 라벨 정의가 없다(`.github/`에 workflows만 있다).
- CI `ci.yml`은 dev push마다 `ci`·`backend`·`data-eval` 잡을 돌린다. 같은 브랜치에 push가 이어지면 앞 커밋의 실행은 취소된다(`cancel-in-progress`).
- DB 마이그레이션 체계는 없다. 서버들이 시작할 때 `CREATE TABLE IF NOT EXISTS`로 스키마를 만든다. 수동 이관 스크립트가 따로 있다.

## 3. 제안 구조

`ax-autodeploy`에 **백엔드 단계**를 붙인다. 타이머·락·로그·정지 표시를 그대로 쓰고, 백엔드용 상태 파일만 따로 둔다.

```
타이머(90초) → flock → 정지 표시·배포 금지 잠금 확인
  → fetch → 운영 트리 HEAD..dev 최신에 backend/ 변경이 있는가
  → [조건 1] CI ci·backend 초록
  → [조건 4] 배포 메모·위험 경로 없음
  → [조건 5] 9~22시, 조용한 구간, 승인 대기·긴 작업 없음
  → #소통 공지 → deploy-bundle → restart-backend
  → [조건 3] 실패하면 되돌림 → 결과 공지
```

원칙은 세 가지다.

1. 서버를 바꾸는 동작은 게이트로만 한다. 감사 로그에 사람 배포와 같은 형식으로 남는다.
2. 확인할 수 없으면 배포하지 않는다. API 오류, 판정 불가, 공지 실패는 모두 "이번 주기 건너뜀"이다.
3. 기준은 `last-deployed-ref`가 아니라 **운영 트리의 실제 HEAD**다. 사람이 손으로 배포하면 자동 배포가 저절로 따라온다.

### 3.1 실행 계정

게이트 전용 계정(예: `axautodeploy`)을 새로 만들어 `axgate` 그룹에 넣고, 정책 `[permissions]`에 `status`·`deploy-bundle`·`restart-backend`·`rollback-bundle`만 준다. 자동 배포 스크립트는 이 계정으로 게이트 앞단을 부른다. 감사 로그에 `user=axautodeploy`로 남아 사람 배포와 구분된다.

`ubuntu`의 sudo로 `systemctl`을 직접 부르는 방식은 쓰지 않는다. 백업·health 대기·감사 기록을 건너뛰게 된다.

## 4. 조건별 구현

### 조건 1 — CI 초록

- 서버에서 GitHub API를 읽는다: `GET /repos/{repo}/commits/{SHA}/check-runs`. 기존 `ci_check` 함수를 고쳐 쓴다.
- 지금 함수는 모든 check-run이 성공해야 통과한다. 백엔드 단계는 **이름이 `ci`와 `backend`인 두 개**만 본다. 둘 다 `completed` + `success`여야 한다.
- `cancelled`·진행 중·없음은 "대기"다. 다음 주기에 다시 본다. dev에 push가 이어져 앞 실행이 취소돼도 최신 커밋만 보면 되므로 문제없다.
- 필요한 것: 읽기 전용 토큰 파일(root 소유 600). 권한은 Checks 읽기와 Pull requests 읽기만.
- 새 러너를 쓰지 않는다. 기존 CI가 이미 내놓은 결과를 읽기만 한다.

### 조건 2 — 게이트 사용과 자동 공지

- 순서: 공지 올림 → 성공하면 `deploy-bundle <SHA> --announced` → `restart-backend <SHA> --ack-data-loss --announced`.
- 공지는 슬랙 Incoming Webhook으로 #소통에 올린다. 웹훅 주소는 root 소유 600 파일에 둔다.
- **공지가 실패하면 배포하지 않는다.** `--announced`는 "올렸다"는 확인이므로 거짓이 되면 안 된다.
- `deploy-bundle`은 프런트 두 곳도 다시 빌드한다. 같은 주기의 프런트 단계는 건너뛰고 기준 ref만 갱신한다.

### 조건 3 — 백엔드만 재시작, 실패하면 되돌림

- 재시작은 `restart-backend`가 한다. health 판정도 게이트의 것을 그대로 쓴다(19개 모두 200, 최대 180초).
- 게이트가 끝 코드 0이 아니면 되돌림 절차(5절)로 간다.
- nginx·`.env`·DB는 건드리지 않는다.

### 조건 4 — 배포 메모가 있으면 알림만

레포에 PR 템플릿이 없으므로 먼저 만들어야 한다. 판정은 6절에 적었다.

### 조건 5 — 미루기와 시간대

- 시간대: `TZ=Asia/Seoul`로 시각을 구해 09:00~22:00만 허용한다. 서버 시계로 직접 비교하지 않는다(1시간 어긋난다).
- 미루기 판정은 7절에 적었다.

## 5. 되돌림 방식과 한계

### 5.1 절차

게이트에는 코드 롤백이 없다. `deploy-bundle`은 뒤로 가는 SHA를 거부한다. 그래서 되돌림은 세 단계다.

1. `rollback-bundle <새 SHA>` — 프런트 번들을 배포 직전으로 복원한다.
2. 운영 트리를 직전 HEAD로 옮긴다. 직전 HEAD는 `deploy-prev-head.bak-before-<SHA8>`에 있다. **이 단계가 지금 게이트에 없다.**
3. `restart-backend <직전 SHA> --ack-data-loss` — HEAD가 직전 SHA이므로 게이트 검사를 통과한다. health를 다시 기다린다.

2단계는 두 가지 방법이 있다.

| 방법 | 내용 | 평가 |
|---|---|---|
| A (권장) | 게이트에 `rollback-code <SHA>` 동작을 추가한다. 기록된 직전 HEAD로만 옮긴다 | 감사 로그에 남고 원칙 1을 지킨다. 태윤 님의 게이트 변경이 필요하다 |
| B | 자동 배포 스크립트가 `ubuntu`로 `git checkout --detach`를 직접 한다 | 바로 쓸 수 있다. 게이트 밖 변경이 하나 생긴다 |

### 5.2 되돌린 뒤

- 실패한 SHA는 건너뛸 커밋으로 적는다. 새 커밋이 dev에 올 때까지 다시 시도하지 않는다.
- 되돌림 재시작도 실패하면 **더 하지 않는다.** 자동 배포를 멈추고 #소통에 사람을 부르는 공지를 올린다.

### 5.3 한계

- **메모리에만 있는 상태는 되돌릴 수 없다(`--ack-data-loss`).** 재시작 한 번에 사라지고, 되돌리면 두 번 사라진다. 확인된 것:
  - 총괄의 승인 대기(holds·handoffs)
  - 마케팅 영상 생성 등 진행 중 작업 표. 장부에 `reserved`가 남아 다시 시도할 때 막힐 수 있다
  - 고객지원 문의·클레임, 기획(planning) 상태
  - 인프라 배포 기록·잠금, 안전 기준값 변경, 총괄 사용량, 데이터 LLM 정지 표시
- **데이터는 되돌리지 않는다.** 새 코드가 시작하면서 만든 테이블·컬럼과 그 사이에 쓰인 데이터는 남는다. 백업(`.data.bak-before-<SHA8>`)은 있지만 복원하면 그 뒤의 쓰기가 사라지므로 자동으로는 하지 않는다.
- **health는 얕다.** 200만 본다. 프로세스는 떴지만 기능이 깨진 경우는 잡지 못한다.
- **`uv sync`를 아무도 하지 않는다.** 게이트도 `deploy.sh`도 하지 않는다. 의존성이 바뀐 커밋은 자동 배포하면 뜨지 않는다. 6절에서 위험 경로로 막는다.
- 실패부터 복구까지 최대 약 7분이 걸린다(180초 대기 두 번 + 번들 복원).

## 6. 배포 메모 판정

### 6.1 표식

PR 템플릿(`.github/pull_request_template.md`)을 새로 만들고 아래 섹션을 넣는다.

```markdown
## 배포 메모
<!-- 서버 설정(.env), DB 이관, nginx 변경이 필요하면 적는다. 없으면 "없음"만 남긴다. -->
없음
```

판정은 **라벨과 본문을 둘 다 본다.** 하나라도 걸리면 자동 배포하지 않는다.

| 근거 | 조건 |
|---|---|
| 라벨 | PR에 `manual-deploy` 라벨이 있다 |
| 본문 | `## 배포 메모` 섹션의 내용이 비어 있지 않고 "없음"이 아니다 |
| 섹션 없음 | 템플릿 도입 뒤 머지된 PR인데 섹션이 없다 → 메모가 있는 것으로 본다 |
| 위험 경로 | 아래 경로가 바뀌었다(메모가 없어도 막는다) |

위험 경로: `backend/uv.lock`, `backend/**/pyproject.toml`, `backend/scripts/run_all.sh`, `backend/.env.example`, `backend/scripts/migrate_*`, `docs/ops/ssh-gate/`, `docs/ops/autodeploy/`, nginx 설정 파일.

### 6.2 방법

- 운영 트리 HEAD부터 대상 SHA까지의 커밋마다 `GET /repos/{repo}/commits/{SHA}/pulls`로 PR을 찾아 라벨과 본문을 읽는다.
- **범위 안에 하나라도 걸리면 범위 전체를 배포하지 않는다.** 뒤 커밋만 골라 배포할 수 없다.
- PR을 찾지 못하거나 API가 실패하면 배포하지 않는다.
- 걸리면 #소통에 한 번만 알린다(같은 SHA로 다시 알리지 않는다). 사람이 손으로 배포하면 운영 트리 HEAD가 따라가서 막힘이 저절로 풀린다.

## 7. 긴 작업·승인 대기 감지

### 7.1 지금 밖에서 볼 수 있는 것

| 대상 | 조회 | 비고 |
|---|---|---|
| 안전 승인 대기 | `GET 127.0.0.1:8001/api/safety/reviews?status=pending` | 인증 없이 되는지 실제 호출로 확인 필요 |
| 총괄 사건 진행 | `GET 127.0.0.1:8000/api/incidents` | 사건·단계의 `status` |
| 개발 AI 보류 | `.../holds` | 토큰 필요 |
| 영상 생성 등 긴 작업 | **조회 수단 없음** | 메모리 전용 표, 엔드포인트 없음 |

### 7.2 제안

- **1단계(코드 변경 없음):** 위 두 주소를 읽어 대기·진행 건이 있으면 미룬다. 긴 작업은 볼 수 없으므로 조용한 구간으로 보완한다.
- **2단계(백엔드 변경):** 공통 서버 틀(agent-template)에 `GET /busy`를 추가한다. 각 서버가 `{"busy": 개수, "reasons": [...]}`를 준다. 자동 배포는 19개를 읽어 합이 0일 때만 재시작한다. 영상 생성 표와 총괄 holds를 여기에 싣는다.

### 7.3 묶음과 상한

- **조용한 구간:** dev 최신 커밋이 10분 동안 바뀌지 않았을 때만 배포한다. 어제는 30분 사이에 6번 머지됐다. 그때마다 재시작하면 메모리 상태가 6번 사라진다.
- **최소 간격:** 재시작과 재시작 사이는 30분 이상.
- **미루기 상한:** 승인 대기는 며칠씩 남을 수 있다. 상한 없이 미루면 배포가 영영 안 된다. 4시간을 넘기면 강제로 재시작하지 않고 #소통에 "미뤄지고 있다"고 알려 사람이 정하게 한다.

## 8. 공지 문구

게이트가 만드는 문안 형식(`[tencent] <계정>: <동작> ... 되돌리는 방법: ...`)을 따른다.

배포 전:

```
[tencent] 자동 배포: 백엔드 8dd9039b → d74057a9 를 곧 배포하고 재시작합니다.
포함 PR: #1670, #1672 (backend 9개 파일) / CI: ci·backend 통과
재시작하면 메모리에만 있는 상태(승인 대기·진행 중 작업)가 지워집니다.
되돌리는 방법: 실패하면 자동으로 8dd9039b 로 되돌립니다. 멈추려면 autodeploy-pause.
```

성공:

```
[tencent] 자동 배포 끝: 백엔드 d74057a9, health 19/19 (약 40초).
```

되돌림:

```
[tencent] 자동 배포 실패 → 8dd9039b 로 되돌렸습니다. health 19/19 복구.
실패 지점: restart-backend health-timeout 17/19. d74057a9 는 새 커밋이 올 때까지 다시 시도하지 않습니다.
```

되돌림 실패(사람 호출):

```
[tencent] 자동 배포 실패, 되돌림도 실패했습니다. 자동 배포를 멈췄습니다. 서버 확인이 필요합니다.
```

알림만(배포 메모):

```
[tencent] 자동 배포 보류: #1675 에 배포 메모가 있습니다(DB 이관). 손으로 배포해 주세요. 대상 d74057a9.
```

미뤄짐(상한 초과):

```
[tencent] 자동 배포가 4시간째 미뤄지고 있습니다(승인 대기 2건). 대상 d74057a9.
```

## 9. 실패·중복 실행 방지

| 장치 | 내용 |
|---|---|
| 자동 배포 락 | 기존 `/var/lib/ax-autodeploy/lock`(flock)을 프런트·백엔드 단계가 같이 쓴다 |
| 게이트 실행 락 | `/run/lock/ax-gate.run`. 사람이 게이트를 쓰는 중이면 게이트가 `busy`로 거부하고 다음 주기에 다시 한다 |
| 배포 금지 잠금 | `lock`이 걸려 있으면 게이트가 거부한다. 따로 구현할 것이 없다 |
| 정지 표시 | 정책에 `[autodeploy] pause_file`을 연결해 `autodeploy-pause`가 듣게 한다. **도입 전 필수** |
| 실패 횟수 | 기존 `fail-count`·`skipped-ref` 방식을 백엔드용 파일로 따로 둔다. 백엔드는 **1회 실패로 건너뛴다**(프런트는 3회). 재시작을 반복하면 손실이 커진다 |
| 진행 표시 | 배포 시작 때 `backend-in-progress`에 단계와 SHA를 적고 끝나면 지운다. 스크립트가 중간에 죽으면 다음 주기가 이 파일을 보고 **아무것도 하지 않고** 사람을 부른다 |
| 공지 중복 | 보류·미뤄짐 알림은 SHA마다 한 번만 올린다 |
| 디스크 | 재시작 전 백업 자리(약 1GB)가 있는지 확인한다. 모자라면 배포하지 않는다 |
| 시간 초과 | 유닛 `TimeoutStartSec`(1500초) 안에 끝나게 한다. 배포 70초 + 재시작 180초 + 되돌림 약 250초 |

## 10. 위험

| 위험 | 완화 |
|---|---|
| 메모리 상태 소실이 하루에도 여러 번 생긴다 | 조용한 구간 10분, 최소 간격 30분, 9~22시, 미루기 |
| 긴 작업을 볼 수 없다(1단계) | `/busy` 엔드포인트(7.2절 2단계). 그 전까지는 영상 생성 중 재시작이 일어날 수 있다 |
| 의존성·설정이 필요한 커밋이 메모 없이 머지된다 | 위험 경로 자동 차단. 그래도 새 환경 변수가 필요한 코드는 잡지 못한다 |
| health는 통과했지만 기능이 깨졌다 | 사람이 보고 `autodeploy-pause` 뒤 손으로 되돌린다. 자동으로는 잡지 못한다 |
| 게이트 밖 재시작(`restart-be.sh`)과 겹친다 | 자동 배포는 게이트 락만 본다. 게이트 밖 동작은 막지 못한다. 손 재시작도 게이트로 하도록 정한다 |
| 봇 계정에 `restart-backend` 권한이 생긴다 | 권한을 4개 동작으로 좁힌다. 토큰·웹훅 파일은 root 600 |
| 야간·주말에 실패해 아무도 못 본다 | 시간대 제한. 주말 포함 여부는 질문 4 |
| 슬랙 웹훅이 죽으면 배포가 멈춘다 | 의도한 동작이다(공지 없이 배포하지 않는다). 로그와 heartbeat에 남긴다 |
| 백업이 디스크를 채운다 | 게이트 `backup_keep = 5`가 정리한다. 배포 전 여유 공간 확인 |

## 12. 결정이 필요한 질문

1. **코드 되돌림을 게이트에 넣을까(5.1절 A), 스크립트가 직접 할까(B)?** A는 태윤 님 작업이 필요하다. 권장은 A.
2. **공지를 어떻게 올릴까?** 서버에 슬랙 웹훅이 없다. #소통용 Incoming Webhook을 새로 만들어도 되는가. 배포마다 2건(전·후)이 올라온다. #소통이 시끄러우면 전용 채널을 둘 수도 있다.
3. **`uv.lock`이 바뀐 커밋은?** 지금 안은 "자동 배포하지 않고 알림만"이다. 자동으로 `uv sync --frozen`까지 하게 할 수도 있다(게이트 변경 필요).
4. **주말·공휴일에도 자동 배포할까?** 조건은 "9~22시"만 있다.
5. **미루기 상한은 몇 시간인가? 넘기면 알림만 할까, 강제로 재시작할까?** 지금 안은 4시간, 알림만.
6. **조용한 구간(10분)과 최소 간격(30분) 숫자가 맞는가?**
7. **`data-eval` 잡도 초록이어야 하는가?** 제안은 `ci`·`backend`만이다.
8. **봇 계정 이름과 권한.** `axautodeploy`에 `restart-backend`·`rollback-bundle`을 주는 것에 동의하는가. 지금 이 권한은 세 사람만 가진다.
9. **배포 메모 표식.** 라벨 이름 `manual-deploy`, 섹션 제목 `## 배포 메모`, "섹션이 없으면 막는다" 규칙에 동의하는가.
10. **1단계 알림 기간.** 1주면 충분한가.
11. **손 재시작(`restart-be.sh`)을 게이트로 옮길까?** 지금은 감사 로그에 남지 않는 재시작이 있다.
