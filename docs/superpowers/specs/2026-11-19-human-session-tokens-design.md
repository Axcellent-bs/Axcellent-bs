# 사람별 토큰(로그인 세션)으로 쓰기 권한 바꾸기 — 설계

2026-11-19 · 결정: 예진(11/18 보안 점검 스레드, 태윤 님 제안 수용)

## 왜

- 232 화면은 자리표시자 토큰을 보내고, 앞단 nginx가 진짜 **공용 사람 토큰**으로 바꿔 붙인다. 그래서 사내망에서 화면에 닿는 사람은 누구나 nginx로 열린 모든 쓰기(승인·정산·클레임·캠페인·회사 연결·연결 키)를 "사람"으로 통과한다. 11/18 빈 요청 한 번에 회사 연결 기록이 지워진 것도 이 구조 때문이다
- 기록의 "누가"가 전부 `공용`이라 감사 기록이 의미가 없다
- 운영팀(관제 센터)과 고객사 관리자·일반회원을 서버가 구분하지 못한다. 연결 키 발급·폐기(운영자)와 연결·끊기(고객사 관리자)를 나눌 수 없다
- `run_web.sh`로 띄운 화면은 진짜 토큰이 JS 번들에 평문으로 들어간다

## 목표 / 하지 않는 것

목표
1. 쓰기는 로그인한 사람마다 다른 토큰으로만 된다. 기록에 실제 사람 이름이 남는다
2. 역할(운영자·고객사 관리자·일반회원)을 서버가 안다. 경로마다 필요한 역할을 검사한다
3. 화면 번들에 비밀값이 없다. 토큰은 로그인 응답으로만 받는다
4. 서비스들이 같은 규칙으로 토큰을 검사한다(한 군데 구현)

하지 않는 것
- 외부 로그인(구글·SSO), 비밀번호 찾기, 2단계 인증
- 읽기(GET) 인증. 실제 고객 데이터를 올리기 전 단계에서 따로 한다(재헌 님 이관 문서 9장 조건)
- AI끼리 호출(A2A 에이전트 토큰) 변경

## 설계

### 1. 계정 (dashboard-api)
- 서버 파일 `accounts.json`(회사 연결 파일 옆, 연결 키와 같은 방식). 칸: id, 이름, 이메일, 역할(`operator`·`admin`·`member`), 비밀번호 해시(scrypt), 만든 시각
- 첫 계정: `.env`의 `AX_BOOTSTRAP_ADMIN`(이메일·초기 비밀번호)로 운영자 1명을 만든다. 데모 계정(admin·member·axc)은 이 운영자가 화면에서 만든다
- 관리자 가입(/setup)은 연결 키 확인 뒤 고객사 관리자 계정을 서버에 만든다. 일반회원은 관리자가 초대한다(지금 화면 흐름 그대로)

### 2. 로그인과 토큰
- `POST /api/dashboard/auth/login` {이메일, 비밀번호} → 세션 토큰. `POST /auth/logout`, `GET /auth/me`
- 토큰 = 서명한 문자열(이름·역할·만료). 서명 키는 `.env`의 `AX_SESSION_SECRET` 하나. 기본 만료 12시간
  - 서명 토큰이라 서비스들이 dashboard-api에 묻지 않고 각자 검사할 수 있다
  - 로그아웃·계정 정지는 서버의 "끊은 토큰 목록"으로 막는다(만료까지만 보관)
- 화면은 토큰을 `sessionStorage`에 두고 쓰기 요청에 `Authorization: Bearer`로 붙인다. 번들에는 넣지 않는다

### 3. 서비스 공통 검사 (agent-template)
- `ax_agent_template.human_auth.verify_human(authorization) -> Human(name, role)`
  - 세션 토큰이면 서명·만료·끊은 목록 확인
  - 옮기는 동안 기존 공용 토큰(`*_HUMAN_TOKENS`)도 받되, 이름을 `공용`으로 두고 경고 로그. 마지막 단계에서 끈다(`AX_ALLOW_SHARED_HUMAN_TOKEN=0`)
- dashboard-api·safety·finance·orchestrator·workflow-core·archive/hr 대화가 지금 각자 가진 검사를 이 함수로 바꾼다(domains끼리 import 없음, 공용 모듈만)
- 역할 검사: `require_role("operator")` 같은 의존성. 연결 키 발급·폐기는 operator, 연결·끊기·회사 정보는 admin, 그 밖의 사람 쓰기는 로그인한 누구나

### 4. nginx
- 쓰기 경로에서 공용 토큰 주입을 뺀다. 화면이 보낸 `Authorization`을 그대로 넘긴다
- 읽기와 A2A 중계 경로의 주입은 지금처럼 둔다
- `/dashboard-api/api/dashboard/auth/login`·`logout` POST를 연다(게이트)

### 5. run_web.sh
- `VITE_SAFETY_HUMAN_TOKEN`·`VITE_SHOP_ADMIN_TOKEN`·`VITE_DATA_A2A_TOKEN`을 번들에 넣지 않는다. 화면은 로그인으로 토큰을 받는다
- 번들로 나간 적이 있는 A2A 토큰은 교체한다(태윤 님 권고)

## 나눠 올리는 순서 (PR)

1. 공용 검사 `human_auth` + 계정·로그인 API(dashboard-api). 공용 토큰도 계속 받음 → 지금 동작 그대로
2. 화면 로그인: 데모 로그인을 서버 로그인으로 바꾸고 쓰기에 세션 토큰. 연결 키 화면에 역할 검사
3. 다른 서비스(safety·finance·orchestrator·workflow·대화)가 `human_auth` 사용
4. 서버 작업(태윤·재헌 님): `AX_SESSION_SECRET`·`AX_BOOTSTRAP_ADMIN` 설정, 로그인 경로 열기, 쓰기 경로 공용 토큰 주입 제거
5. 공용 토큰 끄기(`AX_ALLOW_SHARED_HUMAN_TOKEN=0`)와 `run_web.sh` 정리, A2A 토큰 교체

1~3은 공용 토큰을 계속 받아 데모가 끊기지 않는다. 4·5에서 막힌다.

## 정한 것 (2026-11-19, 예진이 판단을 맡김)

- 비밀번호를 실제로 검사한다(지금 데모 로그인은 보지 않는다). 시연 계정 비밀번호는 팀 채널로만 공유
  - 근거: 비밀번호를 안 보면 이메일만 알면 누구나 그 사람으로 로그인한다. 그러면 사람별 토큰이 공용 토큰과 같아져 목표 1(실제 이름)·2(역할 구분)가 무너진다. 비용은 로그인 때 한 번 더 입력하는 것뿐
- 세션 만료 12시간
  - 근거: 근무 시간·시연 하루를 한 번 로그인으로 버티는 길이. 1시간처럼 짧으면 시연 도중 풀리고, 7일처럼 길면 토큰이 새었을 때 오래 쓰인다(서명 토큰은 만료 전에 막으려면 끊은 목록에 따로 올려야 해서 짧을수록 안전). 하루를 끊지 않는 범위에서 가장 짧게
- 계정은 공용 계정과 팀원별 개인 계정을 같이 둔다 (11/19 오후에 바꿈, 예진 결정)
  - 공용 운영자 1개(`AX_BOOTSTRAP_ADMIN`, 관제 센터용), 공용 관리자 1개(`team@`, 고객사 화면용), 팀원별 개인 계정 1개씩
  - 평소 시연·확인은 공용 관리자로 해도 된다. 누가 승인했는지 기록을 남겨야 하거나 테스트할 때는 개인 계정으로 로그인한다
  - 근거: 팀이 같이 시연하는 단계라 공용 계정이 편하다. 다만 공용 계정만 쓰면 11/18처럼 기록에 같은 이름만 남아 누가 했는지 알 수 없으니, 그게 필요한 일은 개인 계정으로 한다
  - 비밀번호는 서버 담당이 각자에게 직접 전하고 채팅에 올리지 않는다. 받은 사람은 머리글 메뉴의 "비밀번호 바꾸기"로 바꾼다(#1428)

## 위험

- 4단계 전후로 화면 쓰기가 막히는 순간이 생길 수 있다 → 4와 화면 배포를 한 번에, 되돌리기는 nginx 백업 + `AX_ALLOW_SHARED_HUMAN_TOKEN=1`
- 서명 키가 새면 누구나 토큰을 만들 수 있다 → `.env`에만, 교체하면 모두 다시 로그인
