# 기획 제안: 방향 선택지로 아이디어 고르기 (설계)

2026-11-18 · 기획 담당 예진 · 상태: 검토 반영, 승인 대기

## 왜

데이터분석 인사이트를 받으면 기획 제안의 "기획 판단"이 인사이트를 다시 말하는 데 그친다.
예: PROP-7 "챌린지" — `"챌린지" 숏츠 중앙값 조회 506만` → 할 일 "캣북스 독서 챌린지 숏폼을 만든다".
같은 인사이트라도 기획이라면 갈래를 나눠 봐야 한다. **지금 뜨는 챌린지에 올라탈지, 캣북스가 자체 챌린지를 만들지**.
그리고 고객사 형편(작은 사이트, 팔로워 적음)에 맞는 쪽을 골라야 한다. 지금은 이 판단이 없어서 제안이 "단순 데이터"로 보인다.

## 목표

- 인사이트를 받으면 기획이 **방향 질문 하나**를 선택지 버튼으로 낸다(예: 유행에 올라타기 / 자체 기획 퍼뜨리기 / 우리 상품과 엮기)
- 고객사 규모를 **숫자로 재서** 그중 하나에 "추천"을 붙인다. 추천 이유는 그 숫자를 인용한 코드 문장이다
- 사람이 버튼 하나를 누르면 그 방향에 맞춰 기획 판단(할 일·이유·목표·형식)을 쓴다. 이후 흐름(고치기 → 확정 → 마케팅)은 지금 그대로다

## 하지 않는 것

- 자유 대화. 선택지만 고른다(대화를 선택지로 제한하는 게 이 기능의 핵심)
- 질문 여러 번. 방향만 묻는다. 대상·형식·목표는 기획이 채우고, 사람은 기존 "고치기"로 바꾼다
- 마케팅이 만드는 콘텐츠 자체(대본·영상)를 기획이 쓰는 것

## 실패로 보는 것 (anti-goals)

- 지금 뜨는 챌린지 이름이나 숫자를 기획(LLM)이 지어냄. 출처가 없으면 그 선택지는 "근거 없음"으로 막는다
- 같은 숫자인데 추천이 바뀜. 추천은 코드 규칙이 정한다
- 버튼 수가 늘어 제안 하나 처리가 지금보다 번거로워짐. 사람 클릭은 "방향 1번"만 늘어난다

## 지켜야 할 것

- 계약(`shared/contracts`)은 추가만 한다. 새 칸은 모두 선택(기본값 있음)
- 숫자는 다른 부서 코드가 낸 값만 쓴다. 기획이 넣는 숫자는 지금처럼 목표치 하나
- 부서끼리는 A2A로만 부른다. 상태 변경은 `execute()` 관문을 거친다
- LLM 모델 이름은 하드코딩하지 않는다. LLM이 없거나 실패하면 규칙 초안으로 대신한다(지금 `rule_draft`와 같은 원칙)
- 안전규칙 파일(registry.toml·thresholds.toml·gate.py)을 바꿔야 하면 태윤 님 리뷰, 자동 머지 금지

## 방법 (검토한 것)

1. **갈래는 코드가 정하고 추천도 숫자 규칙으로, 글만 LLM** — 같은 숫자면 같은 추천. 왜 골랐는지 숫자로 설명된다. 대신 갈래 종류가 정해진 틀 안에 있다
2. LLM이 갈래부터 추천까지 다 함 — 아이디어가 자유롭지만 추천이 흔들리고 근거 설명이 어렵다
3. 지금처럼 두고 "아이디어 더 보기" 버튼으로만 — 싸지만 "받자마자 기획다운 제안"이 안 된다
4. (예진 님 제안) **선택지 버튼으로 사람이 방향을 고르고, 그 답에 맞춰 기획안을 씀**

**고른 것: 1 + 4.** 갈래와 추천은 코드(1)가 정하고, 사람이 버튼으로 방향을 고르면(4) LLM이 그 방향의 할 일·이유를 쓴다.
질문은 방향 한 번만(예진 님 결정). 방향을 안 골라도 확정은 막지 않는다(예진 님 결정). 규모는 숫자로 잰다(예진 님 결정). 없는 숫자는 데이터분석·마케팅에 부탁한다(예진 님 결정).

## 설계

### 1. 갈래(방향) 목록 — 코드에 고정

| id | 이름 | 쓸 수 있는 조건 (아니면 버튼은 보이되 막힘 + 이유) |
|---|---|---|
| `ride_trend` | 유행에 올라타기 | 인사이트의 숏츠 형식(`ReceiveInsightInput.shorts_format`, 예: 챌린지)이 있고, 데이터분석 트렌드 목록에 같은 형식이면서 광고 재료로 쓸 수 있는(`ad_material is True`) **다른** 주제가 1개 이상. 형식이 없으면 막힘("형식 정보 없음") |
| `own_trend` | 자체 기획 퍼뜨리기 | 항상 |
| `with_product` | 우리 상품과 엮기 | 인사이트에 회사 상품(`products`)이 1개 이상 |

`ride_trend` 선택지에는 올라탈 후보(트렌드 주제 이름·그 주제 숏츠 중앙값 조회·기준 시각)를 최대 3개 붙인다. 값은 데이터분석 응답 그대로 옮긴다.
실존 인물·상표가 든 주제(`real_entity`)는 후보에서 뺀다(지금 프롬프트의 "실존 인물·상표를 새로 끌어오지 않는다"와 같음).
인사이트 자기 주제(같은 `insight_id` 또는 같은 topic)는 후보에서 뺀다. `ad_material`·`real_entity`가 비어 있는(분류 전) 주제도 뺀다(지어내지 않는 쪽으로).

### 2. 고객사 규모 숫자 (`ScaleFacts`)

| 숫자 | 받는 곳 | 지금 |
|---|---|---|
| 지난 캠페인 조회 | 기획이 가진 지난 결과(`past`, 최근 3건)·성과 기록 | 있음. 최근 3건의 **중앙값**, 1건뿐이어도 쓴다(그 사실을 이유 문장에 적음) |
| 공식 SNS 팔로워 수 | 마케팅 | **부탁 필요** (받는 곳 없음). 채널별로 받고, 규칙에는 **가장 큰 채널 값**을 쓴다(그 채널로도 퍼뜨리기 어려우면 다른 채널도 어렵다) |
| 지금 뜨는 같은 형식 주제 목록 | 데이터분석 `trend_insight_brief` | 있음(기획이 이미 부름). 형식(`shorts_format`) 값으로 거르는 게 맞는지 데이터분석 확인 필요 |

모르는 값은 "확인할 수 없음"으로 두고 지어내지 않는다.
하루 주문 수는 추천 규칙에 쓰지 않아 이번 범위에서 뺐다(검토 뒤 정리).

### 3. 추천 규칙 (코드, 같은 숫자면 같은 결과)

1. `ride_trend`가 쓸 수 있고, 받은 규모 숫자 중 **하나라도** 기준보다 낮으면(팔로워 < 기준 또는 지난 캠페인 조회 중앙값 < 기준) → `ride_trend` 추천. 숫자가 하나만 있으면 그 하나로 판단한다.
   이유 예: "팔로워 300 · 지난 캠페인 평균 조회 1.2천 → 새 챌린지를 퍼뜨리기 어려움"
2. 아니고 `with_product`가 쓸 수 있으면 → `with_product`
3. 아니면 → `own_trend`
4. 규모 숫자가 하나도 없으면 추천을 붙이지 않는다("규모 숫자를 받지 못해 추천 없음")

기준값은 회사 설정(테넌트 설정)에 두고 기본값을 코드에 둔다. 기본값을 얼마로 할지는 첫 구현에서 정하고 문서에 적는다.

### 4. 흐름

```
데이터분석 인사이트 → receive_insight
  → 기획: 갈래 3개 계산(쓸 수 있는지·후보·추천)  ← LLM 안 부름
  → 제안 PROP-n "방향 선택 대기"  (할 일·이유는 규칙 초안으로 채워 둠)
사람: 방향 버튼 1번
  → 기획: LLM이 그 방향으로 할 일·이유·목표·형식 작성 (숫자 검사 그대로)
  → "확인 대기" (지금과 같음) → 고치기 · 확정 → 마케팅
```

- 방향을 다시 고를 수 있다(확정 전까지). 다시 고르면 할 일·이유를 새로 쓴다. 사람이 고친 적이 있으면(`written_by == "human"`, 지금 있는 칸) 화면에서 확인 창을 한 번 띄운다(백엔드 칸 추가 없음)
- 방향 고르기 → 글쓰기는 버튼 요청 안에서 끝낸다(지금 받기와 같이 LLM은 상태 잠금 밖, 제한 시간 30초). LLM이 없거나 실패하면 **방향별 규칙 초안**(방향 이름 + 인사이트 제목 + 후보 이름)으로 채운다
- 방향을 고를 때 콘텐츠 카테고리가 있으면 재무 `category_budget_advice`도 같이 묻고 근거에 붙인다. 지금(#1268)은 확정 뒤 마케팅에 넘기기 직전에 묻는데, 그러면 확정하는 사람이 제작비를 못 본다. 넘기기 직전 묻기는 이미 붙어 있으면 다시 묻지 않으므로 그대로 둔다
- 재전송된 같은 인사이트는 지금처럼 중복으로 버린다
- **방향을 고르지 않고도 확정할 수 있다**(예진 님 결정). 마음에 드는 선택지가 없어 넘긴 것일 수 있고, 기획서가 불분명해지는 건 사람이 판단할 일이다. 이때 할 일·이유는 받을 때 채운 규칙 초안(또는 사람이 고친 글)이고, 브리프의 `idea_angle`은 비어서 간다

### 5. 저장 (기획 상태, `ax_workflow.models.Proposal`에 추가)

- `options: list[IdeaOption]` — id·이름·쓸 수 있는지·막힌 이유·후보(트렌드 이름·조회·기준 시각)·추천 여부·추천 이유
- `scale: ScaleFacts | None` — 받은 때의 규모 숫자(출처 skill 포함)
- `angle: str | None` — 사람이 고른 방향 id. 없으면 "방향 선택 대기"
- 11/18 이전 제안은 `options`가 비어 있어 지금 화면 그대로 보인다

방향을 고르면 지금의 할 일·왜·목표·형식 칸이 그 아래에 나온다. 기존 AXcellent 토큰·공용 클래스를 쓴다.

### 7. 마케팅으로 넘기는 것

`CampaignBriefInput`에 선택 칸 추가: `idea_angle`(고른 방향 id), `trend_refs`(올라탈 후보 이름 목록, `ride_trend`일 때).
마케팅이 이 칸을 쓰는 건 재헌 님 몫이다.

### 8. 다른 부서에 부탁할 일

- **데이터분석(재현 님)**: "지금 뜨는 같은 형식 주제" 목록 확인 (11/18 #소통에 부탁 올림)
  - 기획이 쓰려는 방법: 이미 받는 `trend_insight_brief` 주제 목록을 거른다. 조건은 ① 주제의 `shorts_format`이 인사이트 형식과 같음 ② `ad_material` 참 ③ `real_entity` 거짓 ④ 인사이트 자기 주제 아님. 후보는 최대 3개, 주제 이름·`shorts_format_median_views`·`shorts_format_at`을 그대로 옮긴다
  - 확인 1: 주제의 `shorts_format`은 "그 주제 영상에서 가장 많은 형식"이라, 형식이 챌린지여도 따라 할 수 있는 챌린지가 아닐 수 있다. 이렇게 걸러도 뜻이 맞는지
  - 확인 2: `shorts_format_median_views`가 "그 주제의 그 형식 영상" 조회인지 "전체 그 형식" 조회인지. `shorts_format_source`가 `topic`이 아니면 후보에서 빼는 게 맞는지
  - 확인 3: 1이 안 맞으면 "지금 뜨는 챌린지·밈 목록"(이름·대표 조회수·기준 시각)을 주는 칸이나 skill이 필요하다. 가능 여부와 시기
  - 답이 오기 전에도 기획은 먼저 만든다. 후보를 못 찾으면 `ride_trend`를 "지금 뜨는 후보 없음"으로 막는다
- **마케팅(재헌 님)**: ① 공식 SNS 채널별 팔로워 수와 기준 시각을 주는 read skill ② 브리프의 `idea_angle`·`trend_refs` 사용
- 부탁한 값이 오기 전에는 그 숫자를 "확인할 수 없음"으로 두고 기능은 돈다(추천은 받은 숫자만으로)

## 만드는 사람에게 맡기는 것

- 방향 고르기를 기존 `edit_proposal` 관문으로 받을지, 새 액션으로 등록할지(새 액션이면 안전규칙 registry 추가 → 태윤 님 리뷰)
- LLM 프롬프트 문구(방향별 지시)와 규칙 초안 문구
- 추천 기준 기본값
- 마케팅 팔로워 skill이 오기 전 팔로워는 "확인할 수 없음"
- 시험: 같은 입력이면 같은 갈래·추천, 출처 없는 후보는 안 나옴, 실존 인물 주제 제외, 방향 고른 뒤 숫자 검사 유지, 예전 제안 화면 그대로
