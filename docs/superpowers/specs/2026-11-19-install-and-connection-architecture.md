# 고객사별 설치와 연결 구조 — 설계

2026-11-19 · 목적: 서버 이관 전에 데모를 "실제 제품처럼" 만든다. 예진이 구조 판단을 맡김

## 1. 한 줄 요약

AXcellent는 **본사 관제(한 벌)** 와 **고객사 설치(고객사마다 한 벌)** 두 층으로 나눈다.
고객사 설치는 고객사 서버(또는 우리가 그 고객사 전용으로 띄운 서버)에서 돌고, 고객사 데이터는 그 안에만 있다.
본사 관제는 설치 키 발급·설치 목록·건강 상태만 안다. 회사 설정(조직도·지표·키워드)은 레포가 아니라 **설치의 데이터 폴더**에 산다.

## 3. 지금 구조가 "고객사별 설치"와 어긋나는 곳

1. **관제와 고객사가 한 설치에 섞임** — 연결 키를 운영팀이 발급하는데 그 키가 고객사 설치 안에 저장된다. 고객사 관리자가 같은 서버의 키 목록을 볼 수 있다
2. **회사 설정이 레포에 있음** — 새 고객사마다 우리 레포에 PR이 필요하고, 한 설치에 다른 고객사 설정(이름 포함)이 같이 들어 있다
3. **설치 정체성이 고정되지 않음** — run_all이 켤 때마다 토큰을 새로 만든다. 회사는 연결 파일·설치 기록에 흩어져 있다
4. **한 서버에 두 설치를 못 띄움** — 포트 18개·화면 3090 고정, `stop`이 포트로 다른 설치까지 끈다, Redis 이름·포트 고정(재헌 님 조사)
5. **로그인·계정이 브라우저에만 있음** — 데모 계정·가입·현재 계정이 localStorage. 서버는 사람을 모른다
6. **캣북스 흔적** — 테스트 밖 소스 36곳에 캣북스 가정(데이터 감지·설명 문구, 장애 대화 문구, 마케팅 문구)

## 4. 결정과 근거

### 4.1 두 층으로 나눈다: 본사 관제 / 고객사 설치
- 본사 관제(`/control`): 설치 키 발급·폐기, 설치 목록, 설치별 버전·건강(하트비트), 지원 요청. **고객 데이터는 받지 않는다**
- 고객사 설치(`/system` + 서비스 화면 + AI 서비스 전부): 고객사 데이터·계정·회사 설정·사이트 연결을 모두 안에 둔다
- 근거: 키를 발급하는 쪽과 쓰는 쪽이 같은 서버면 키가 의미가 없다(3-1). "고객사 데이터를 운영하지 않는다"는 원칙을 지키려면 데이터가 고객사 설치 밖으로 나가지 않아야 한다. 관제가 아는 건 "설치가 살아 있는가" 정도면 충분하다
- 비용: 관제를 작은 서버 하나로 따로 띄워야 한다(dashboard-api 일부 + `/control` 화면)

### 4.2 설치 정체성 = 설치 데이터 폴더 하나
- 설치마다 `AX_INSTALL_DIR` 하나(지금 `backend/.data`)에 설치 id, 회사 설정, 연결 파일, 계정, 서명 키를 둔다. 환경변수는 이 폴더 경로와 비밀값(LLM 키 등)만
- 토큰은 켤 때마다 만들지 않고 설치 때 한 번 만들어 이 폴더에 둔다(서명 키 `AX_SESSION_SECRET`, AI끼리 토큰)
- 근거: 지금은 정체성이 env·연결 파일·설치 기록에 흩어져 있어 어제처럼 "연결 해제하니 회사 설정이 사라짐"이 생긴다(3-3). 폴더 하나를 백업·이전하면 설치가 통째로 옮겨진다(Tencent 이관에 바로 쓰임)

### 4.3 회사 설정은 업종 템플릿에서 설치 때 만든다
- 레포에는 **업종 템플릿**만 둔다: 쇼핑몰(지금 캣북스), 여행(누비투어), 교육(스터디온에듀). 템플릿 = 지표 카탈로그 + 조직도 뼈대 + 빈 키워드
- 첫 설정(`/setup`)에서 업종을 고르면 템플릿을 설치 폴더로 복사해 그 회사 설정이 된다. 이후 화면에서 고친다(인스타 레이더 계정이 첫 예)
- 캣북스·누비투어 폴더는 데모용 "채워 둔 템플릿"으로 남긴다
- 근거: 회사마다 레포 PR이 필요한 구조는 판매 가능한 제품이 아니다(3-2). 업종만 고르게 하면 다른 고객사 이름이 보이지 않는다. 지금 카탈로그 형식(`MetricCatalog`)을 그대로 쓰므로 데이터 AI 코드는 바뀌지 않는다
- 비용: 회사 설정 파일 위치가 레포 → 설치 폴더로 바뀐다(`AX_TENANTS_DIR`로 이미 바꿀 수 있어 작은 변경)

### 4.4 설치 순서 (실제 고객사가 겪는 흐름)
1. 운영팀이 관제에서 **설치 키** 발급(지금 연결 키) → 고객사 담당자에게 전달
2. 고객사(또는 우리)가 고객사 서버에 설치 스크립트 실행 → 설치 폴더·토큰·서명 키 생성
3. 첫 화면 `/setup`: 설치 키 입력 → **관제에 확인**(설치 등록, 설치 id 받음) → 회사 정보 + 업종 고르기 → 관리자 계정 만들기
4. `/system/connect`: 사이트 연결(아래 4.5) → 연결 확인 → 저장
5. 운영: 설치가 관제에 하트비트(버전·건강·사용량 숫자)만 보낸다
- 근거: 지금 화면 흐름(키 → 회사 정보 → 연결)을 그대로 살리고, 키 확인만 관제로 옮긴다. 고객사에 코드 추가·재시작 요구 없음

### 4.5 사이트 연결 방식 (설치 안)
| 방식 | 대상 | 상태 |
| --- | --- | --- |
| AXcellent 규격 API | 우리 규격을 구현한 사이트(캣북스) | 됨 |
| 다른 형식 API(변환기) | 자기 API가 있는 사이트·SaaS(누비투어) | 됨, 읽기만 |
| 결제대행사 | API 없는 소상공인(주문·매출·환불) | 다음 |
| 파일 올리기(CSV) | 어디서나 되는 마지막 방법 | 다음 |
| 플랫폼 앱 연동(OAuth) | 카페24·스마트스토어 | 보류(사업자 등록) |
- 사이트에 쓰는 일은 모든 방식에서 안전 장치 승인 뒤, 규격 API는 AI가 직접, 나머지는 사람 할 일로 넘긴다(이미 정함)
- 근거: 11/18 논의. 화면 긁기·DB 직접 연결은 하지 않는다

### 4.6 계정과 권한
- 고객사 설치: 관리자·일반회원 계정(서버 저장, 사람별 토큰 — `2026-11-19-human-session-tokens-design.md`)
- 본사 관제: 운영자 계정(팀원 각자). 고객사 설치에는 운영자 계정이 없다. 지원이 필요하면 고객사 관리자가 기한 있는 **지원 접근**을 열어 준다(지금 "지원 모드"를 서버 권한으로)
- 근거: 운영자가 고객사 설치에 늘 들어갈 수 있으면 "고객사 데이터를 운영하지 않는다"와 어긋난다

## 6. 순서 (PR 단위)

1. **설치 정체성 고정**: 설치 폴더(`AX_INSTALL_DIR`)·고정 토큰·`AX_TENANT` 필수화, run_all 포트 오프셋(`AX_PORT_OFFSET`)·Redis 이름 분리 — 두 번째 설치(누비투어)를 띄우는 전제. 재헌 님 조사(포트 18개·stop·Redis)와 같은 범위
2. **계정 서버화**: 사람별 토큰 설계 1~3단계
3. **업종 템플릿**: tenants → templates(쇼핑몰·여행·교육), `/setup`에서 업종 고르면 설치 폴더로 복사
4. **관제 분리**: 설치 키·설치 목록·하트비트를 관제 API로, `/control`을 관제 서버로. 고객사 설치의 연결 키 저장은 "등록된 설치 정보"만 남김
5. **캣북스 흔적 정리**: 소스 36곳의 캣북스 가정을 회사 설정·카탈로그 값으로
6. **연결 방식 추가**: 결제대행사, 파일 올리기

1·2는 이관 전 필수, 3·4는 이관과 함께, 5·6은 이관 뒤.

## 7. 하지 않는 것
- 한 설치에 여러 고객사(멀티 테넌트). 지금 저장소(SQLite·Redis·기억 DB)가 회사별로 나뉘어 있지 않아 섞이면 데이터가 샌다. 설치를 나누는 쪽이 원칙(고객사 데이터 분리)과 맞고 코드도 덜 바뀐다
- 고객 데이터를 관제로 모으기

## 8. 정한 것 (2026-11-19)
- 관제 서버: 서버 이관 때 Tencent Lighthouse로 같이 옮긴다(예진). 관제는 고객 데이터가 없어 외부 서버에 둬도 원칙에 맞는다
- 누비투어 설치 자리: 학원 LAN의 Zabbix 서버(호스트 PC 위 VM)에 두 번째 설치로 둔다(재헌 님 확인, 설치 중). 누비투어 사이트(예진 PC)와 같은 LAN이라 사설망 경로 문제가 없다
  - 남은 것: 누비투어가 도는 PC 주소를 고정(공유기 DHCP 예약)해야 설치가 그 주소를 계속 찾는다
