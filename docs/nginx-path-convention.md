# 새 쓰기 경로와 nginx 허용 목록

운영 서버(251)는 앞단 nginx가 허용한 경로만 백엔드로 넘긴다. 새 쓰기(POST·PUT·PATCH·DELETE) 경로를 만들었는데 허용 목록에 없으면 화면에서 403이 난다.

## 화면에서 보이는 모습

- 앞단 nginx가 막으면 본문이 JSON이 아닌 HTML이다. 화면은 이 경우를 `nginx_blocked`로 구분하고 "서버가 이 요청 경로를 허용하지 않습니다. 관리자에게 서버 허용 경로(nginx) 추가를 요청해 주세요."라고 보여 준다 (403, 405). 구현은 `frontend/src/lib/apiError.ts`의 `failureError`. 이 문구의 "관리자"는 서버 책임자 한 사람이 아니라 게이트 권한자다. 요청 경로는 아래 "서버 작업 요청"을 따른다.
- 앱(dashboard-api 등)이 거절한 403은 `{error:{code,message}}` JSON 봉투가 있어 그 문장을 그대로 보여 준다.
- 문구에는 경로·내부 주소·토큰을 넣지 않는다.

## PR 규약

이 레포는 공개다. PR 본문에는 **서버 작업이 필요한지 여부만** 적는다. 구체 경로·정규식·값(IP·토큰·내부 주소)은 PR 본문·이슈·커밋 메시지에 적지 않는다.

```
## 서버 작업 필요
예 / 아니오
```

- 새 쓰기 경로를 만들었거나, 타임아웃·본문 크기 조정이 필요하거나, 그 밖에 서버에서 무언가 바꿔야 하면 "예".
- "예"일 때 구체 내용은 비공개 팀 채널에 요청 글로 올린다. 양식은 `docs/ops/ssh-gate/REQUEST-TEMPLATE.md`. PR 본문에는 그 요청의 내용을 옮겨 적지 않는다.

## 서버 작업 요청 (비공개 채널에서)

1. 게이트(`docs/ops/ssh-gate/README.md`)로 되는 일인지 먼저 본다. 새 쓰기 경로는 대부분 게이트로 된다: 권한자 한 명이 `nginx-add-location`으로 제안하고 다른 권한자가 승인한다. **게이트로 되는 요청은 서버 책임자가 받지 않는다.**
2. 요청 글에 적을 것(비공개 채널에만):
   - 메서드: 새로 열 메서드. 같은 경로에 GET과 POST가 둘 다 있으면 각각 적는다.
   - 경로 정규식: 가변 부분(`{id}`)은 `[^/]+`처럼 좁게. 앞뒤 `^`·`$`로 고정한다. 중괄호 반복(`{8}`)·`*`·`?`는 게이트가 받지 않으니 `[0-9a-f]+` 같은 묶음으로 적는다.
   - 인증 방식: 아래 "확인 방법"으로 정한다. 사람 토큰 / 공개(읽기 전용) / 별도 토큰 중 하나.
   - 타임아웃: 오래 걸리는 작업(미디어 생성 등)은 기본값보다 길게 요청한다.
3. 읽기용(GET·HEAD) 경로, 허용 접두 밖 경로는 게이트로 못 연다. 요청 양식의 "책임자에게" 칸으로 요청한다.

## 경로가 어떤 인증 방식인지 확인하는 방법

1. 프론트 호출을 찾는다: `frontend/src/lib/*.ts`에서 `fetch` 호출의 주소를 본다(dashboard-api 호출은 모두 `dashboardAuth()`로 사람 토큰을 붙인다). 기본 주소 상수는 `frontend/src/lib/env.ts`.
2. 그 경로를 받는 라우트를 찾는다: `backend/shared/dashboard-api/src/ax_dashboard_api/`에서 경로 문자열을 검색한다.
3. 인증은 `auth.py`의 `require_human`이 정한다. `/api/dashboard/*`는 GET을 포함해 모든 요청에 사람 토큰(`Authorization: Bearer`)이 필요하다. 토큰 없이 열린 것은 `/health`뿐이다. 화면은 `frontend/src/lib/env.ts`의 `dashboardAuth()`로 GET에도 토큰을 붙인다.
4. 다른 서비스(대화 창구·기획·재무 등)로 직접 가는 경로는 그 서비스의 라우트 파일에서 같은 방식으로 확인한다.
