# 서버 위임 게이트 (ax-gate)

> 상태: **운영 중.** 이 폴더에는 일반 구현(스크립트·검증기·테스트)과 설계 문서가 있다. 서버에 설치된 사본은 서버 책임자가 이 레포의 머지된 버전으로 설치한다(`INSTALL.md` 11절). 레포를 고친다고 서버가 바뀌지는 않는다.
>
> **구체 서버 값은 비공개 정책 파일에서 읽는다.** 서버의 경로, 서비스 구성, 주소, 계정 이름, 실제 설치 명령은 이 레포에 없다. 여기 나오는 값(`example-api`, `8201`, `authorized-1` 등)은 전부 가짜 예시다.

서버 책임자가 직접 못 치는 시간에도, 팀원이 **자기 계정으로 직접** 서버 작업을 요청·실행하게 하는 장치다.

## 접수 규칙: 게이트로 되는 요청은 게이트로 한다

**게이트로 되는 요청은 서버 세션(서버 책임자가 직접 치는 관리 경로)이 받지 않는다.** 그런 요청이 오면 대신 실행하지 않고, 요청한 사람이 칠 게이트 명령을 돌려준다.

이유: 관리 경로는 권한표·잠금·감사 로그 밖이고 승인자가 한 명이라, 게이트로 되는 일까지 그쪽으로 모이면 그 한 명이 병목이 된다. 게이트 안에서는 권한자가 책임자 없이 모든 동작을 끝낼 수 있다.

1. 먼저 `help`로 내 계정에 허용된 동작을 본다. 아래 표의 "게이트로 된다"에 있으면 직접 실행한다.
2. 내 계정에 없는 동작이면 **권한자**에게 요청한다(책임자가 아니다).
3. "게이트로 안 된다"에 있는 것만 책임자에게 요청한다. 요청 양식은 [`REQUEST-TEMPLATE.md`](REQUEST-TEMPLATE.md).
4. 공개 PR 본문에는 "서버 작업 필요: 예/아니오"만 적고, 구체 경로·값은 비공개 채널의 요청에 적는다(`docs/nginx-path-convention.md`).

| 하려는 일 | 게이트 | 어떻게 |
| --- | --- | --- |
| 서버 상태 확인 | 된다 | `status` |
| 화면 번들 수동 배포(자동 배포가 막혔을 때) | 된다 | `deploy-bundle <SHA>` |
| 백엔드 재시작 | 된다(권한자) | `restart-backend <SHA> --ack-data-loss`. 서버 HEAD가 그 SHA가 아니면 먼저 `deploy-bundle <SHA>` |
| 번들 되돌리기 | 된다(권한자) | `rollback-bundle <SHA>` |
| 시연 전 게이트 배포 잠금 | 된다(권한자) | `lock <사유> [해제시각]` / `unlock` |
| 자동 배포 잠깐 멈추기·다시 켜기 | 된다(정책에 그 권한이 적힌 권한자) | `autodeploy-pause <사유> [재개시각]` / `autodeploy-resume` |
| 새 쓰기 경로(POST 등) 열기: 정책의 대상 파일, 허용 접두 안, 정책의 블록 모양 | 된다(권한자, 두 사람) | `nginx-add-location` → `nginx-approve-location` |
| nginx 설정을 백업으로 되돌리기 | 된다(권한자) | `nginx-restore <백업폴더명>` |
| 게이트웨이 허용 목록에 읽기(read) 등급 skill 추가 | 된다(정책에 그 권한이 적힌 권한자, 두 사람) | `gateway-allow-propose <skill>` → `gateway-allow-approve <skill> <확인값>` |
| 게이트웨이 허용 목록을 백업으로 되돌리기 | 된다(정책에 그 권한이 적힌 권한자) | `gateway-allow-restore <백업폴더명>` |
| 작업과 PR 번호 연결 | 된다 | `record-pr <참조> <PR번호>` |
| 읽기용(GET·HEAD) 경로, 허용 접두 밖 경로, 블록 모양이 다른 경로 | 안 된다 | 책임자에게 요청 |
| 비밀값·환경변수 파일 변경 | 안 된다 | 책임자에게 요청. 값은 요청 글에도 적지 않는다 |
| 권한 정책·계정·키·방화벽·sudoers·sshd·systemd 구성 | 안 된다 | 책임자만 |
| 데이터·백업 삭제, 코드(레포) 롤백 | 안 된다 | 책임자만 |
| 게이트 스크립트 자체의 변경 | 안 된다 | 레포 PR → 머지 → 책임자가 설치 |

### 비상 절차

게이트가 고장 났거나 권한자가 아무도 없는데 서비스가 멈춘 경우에만 책임자가 관리 경로로 직접 처리한다. 이때도 흔적은 같은 방식으로 남긴다.

1. 처리 전(급하면 직후)에 팀 채널에 한 줄을 올린다: 무엇을 왜 바꿨는지, 되돌리는 방법.
2. 처리 뒤 게이트로 `record-pr <참조> <PR번호>`를 실행해 감사 로그에 연결 줄을 남긴다. 감사 로그 파일에 손으로 줄을 넣지 않는다(형식 보증이 없다).
3. 게이트로 됐어야 하는 일이었다면 왜 안 됐는지를 이슈로 남겨 게이트를 고친다. 서버의 게이트 사본을 직접 고치지 않는다.

## 파일

| 파일 | 설명 |
| --- | --- |
| `ops-gate.sh` | 게이트 본체(bash, 엄격 모드). 서버에는 `/usr/local/sbin/ax-gate`로 둔다 |
| `nginx_location_check.py` | nginx location 검증기(파이썬 표준 라이브러리만). 서버에는 `/usr/local/sbin/ax-gate-location-check` |
| `gateway_allow_check.py` | 게이트웨이 허용 목록 검증기(파이썬 표준 라이브러리만): 카드·등급·요청자 검사, 허용 목록 읽기·쓰기 어댑터. 서버에는 `/usr/local/sbin/ax-gate-gateway-allow-check` |
| `policy.example.toml` | 정책 예시(가짜 값·자리표시자): 계정 → 허용 동작, 경로 접두, location 블록 줄, 잠금·배포·재시작 설정, 경로 |
| `INSTALL.md` | 설치 절차의 일반 형태와 설치 후 검증 체크리스트 |
| `ANNOUNCE.md` | 팀 안내문 |
| `REQUEST-TEMPLATE.md` | 서버 작업 요청 양식(비공개 채널용). 양식만 있고 구체 값은 없다 |
| `autodeploy-paused.sh` | 자동 배포가 멈춰 있는지 판정(읽기 전용). 서버의 자동 배포 스크립트가 부른다. 서버에는 `/usr/local/sbin/ax-gate-autodeploy-paused` |
| `tests/` | 서버 없이 도는 로컬 테스트 |

## 구조

```
팀원 PC ──ssh(자기 키)──▶ sshd ──▶ 그 사람의 개인 계정 (셸 못 씀, 강제 명령)
                                    │  authorized_keys 줄:
                                    │  restrict,from="<허용 출처 IP>",command="/usr/local/sbin/ax-gate <계정>" <공개키>
                                    ▼
                         앞단 ax-gate <계정>            (그 사람 계정 권한)
                           신원 = 실제 로그인 계정(id -un). command= 의 이름은 같은지 확인만
                           SSH_ORIGINAL_COMMAND 를 허용 목록으로만 해석
                           계정별 허용표 · 잠금 · 팀 채널 알림 확인
                                    │  요청을 표준 입력으로 (인자 없음, 이름 없음)
                                    ▼
                         뒷단 sudo -n ax-gate            (root)
                           신원 = sudo 가 넣어 준 SUDO_USER 만 믿는다
                           요청을 처음부터 다시 검증 → 실행 → 감사 로그
```

- **신원은 OS 계정이다.** 팀원마다 서버에 개인 계정을 만든다(공유 계정 없음). 정책 표와 감사 로그가 계정 단위다. SSH 키에 붙인 이름이나 요청에 적힌 이름은 신원이 아니다.
  - 앞단은 `id -un`(실제 로그인 계정)을 쓴다. `command=`에 적힌 계정명이 로그인 계정과 다르면 설정 오류로 거부한다.
  - 뒷단은 `SUDO_USER`만 믿는다. sudo가 직접 넣는 값이라 부르는 쪽이 바꿀 수 없다. `SUDO_USER`가 없거나 root이거나 `SUDO_UID`와 맞지 않으면 실행하지 않는다. 요청(표준 입력)에는 이름 칸이 없고, 이름을 적어 보내면 형식 오류로 거부된다.
- **권한은 정책 파일의 표다.** `계정 → 허용 동작`. 정책 파일은 root만 바꾼다.
- **앞단과 뒷단은 같은 파일이다.** 인자가 하나(계정명)면 앞단, 없으면 뒷단이다. sudoers는 게이트 그룹에 인자 없는 호출 한 줄만 허용한다. 뒷단은 앞단을 믿지 않고 허용표·인자·잠금·알림 확인을 전부 다시 본다.
- **서버마다 다른 것은 전부 정책에 있다.** 경로, 서비스 이름, health 주소 목록, 배포 스크립트에 넘기는 환경변수, location 블록의 모양, 접두 → 포트 표. 스크립트와 검증기에는 특정 서버의 값이 없다.
- 실제 작업은 뒷단(root)이 하고, 배포 스크립트와 git은 `runuser`로 정책의 배포 계정 권한에서 돌린다(root로 빌드하지 않는다).
- 접속 경로는 두 겹으로 한다. 방화벽이 허용 출처에서 오는 SSH만 받고, authorized_keys의 `from=`이 그 계정의 키를 그 출처에서만 받는다.

## 동작

| 동작 | 하는 일 | 알림 확인 |
| --- | --- | --- |
| `help [동작]` | 내 계정에 허용된 동작과 형식을 보여 준다. 앞단에서 끝난다(root로 넘어가지 않고 서버를 바꾸지 않는다). 감사 로그에 `result=help`로 남는다 | |
| `status` | 읽기 전용 점검: 잠금, 정책의 health 주소 목록, 확인 주소들의 응답 코드, 서비스 상태와 최근 로그의 오류 줄 수, 번들의 표시 문자열·비밀값, nginx 사본 비교, 승인 대기 제안 | |
| `lock <사유> [해제시각]` / `unlock` | 배포 금지 잠금 파일. 시연 전 배포를 멈추는 스위치 | |
| `nginx-restore <백업폴더명>` | 백업 폴더의 설정으로 되돌림. 먼저 현재 설정을 백업, `nginx -t` 실패면 원래대로. 대상 파일이 여럿이면 전부 한 번에 | 필수 |
| `nginx-add-location <이름> <메서드> <정규식> [프로필]` | 새 쓰기 경로 **제안**. 검증기만 돌리고 승인 대기 파일을 만든다. nginx는 안 바뀐다. 프로필은 정책에 있는 이름만 | |
| `nginx-approve-location <이름> <확인값>` | 제안자와 **다른** 권한자가 승인하면 그때 적용: 사전 검증 → 백업 → 삽입 → `nginx -t` → reload. 대상 파일이 여럿이면 전부 한 번에 | 필수 |
| `deploy-bundle <SHA>` | 번들 배포(배포 스크립트를 배포 계정으로 실행). 지금 서버 코드보다 **앞선** 커밋만. 번들 백업, 직전 배포 해시 기록, 번들 점검 | 필수 |
| `restart-backend <SHA> --ack-data-loss` | 정책의 파일들을 백업한 뒤 서비스 재시작, health가 전부 뜰 때까지 폴링 | 필수 |
| `rollback-bundle <SHA>` | 그 SHA를 배포하기 직전의 번들 백업으로 되돌림. 코드(레포)는 그대로 | 필수 |
| `gateway-allow-propose <skill>` | 게이트웨이 허용 목록에 skill 추가 **제안**. 검증(이름 형식·중복·카드에 있음·카드 `grade`가 `read`·요청자)만 하고 승인 대기 파일을 만든다. 카드는 정책 `card_repo`의 `expected_card_sha` 커밋 내용(`git cat-file`)으로 읽고, HEAD가 그 SHA가 아니면 거부한다(두 값은 필수). 허용 목록은 안 바뀐다 | |
| `gateway-allow-approve <skill> <확인값>` | 제안자와 **다른** 권한자가 승인하면 그때 재검증 → 백업 → 임시 파일 + `mv` 교체 → 정책의 반영 명령 실행. 실패하면 복구하고 다시 반영한다. 같은 사람은 `[self_approve]` 계정만 | 필수 |
| `gateway-allow-restore <백업폴더명>` | 허용 목록을 `gwa-...` 백업으로 되돌리고 반영한다(복원 전 상태도 백업). 백업 폴더·파일·체크섬 파일이 root 소유이고 체크섬이 맞아야 하며(없으면 거부), 복원될 목록이 형식 검사를 통과해야 한다 | 필수 |
| `record-pr <참조> <PR번호>` | 감사 로그에 "이 작업 ↔ 이 PR"을 남김 | |
| `autodeploy-pause <사유> [재개시각]` / `autodeploy-resume` | 자동 배포를 재개시각까지 멈춤 / 지금 재개. 정책의 정지 표시 파일 **하나만** 쓴다(아래 "자동 배포 정지·재개") | |

동작 뒤 어디에든 붙이는 것(순서 무관): `--dry-run`(할 일만 보여 줌), `--announced`(팀 채널 알림을 올렸다는 확인), `pr=<번호>`(감사 로그의 PR 칸). 동작 이름은 맨 앞에 적는다. `restart-backend`의 `--ack-data-loss`는 SHA 앞에 적어도 된다(앞단이 순서를 맞춰 뒷단에 넘긴다).

사용법 오류가 났을 때

| 거부 사유 | 뜻과 다음 할 일 |
| --- | --- |
| `bad-args` | 인자 개수가 틀렸다. 오류에 그 동작의 형식 한 줄이 같이 나온다 |
| `unknown-action` | 없는 동작이다. 비슷한 동작이 있으면 같이 나온다. `help`로 전체를 본다 |
| `bad-regex` | 정규식에 못 쓰는 글자가 있다. 중괄호 반복(`[0-9a-f]{8}`)은 못 쓰고 허용 묶음(`[0-9a-f]+`)으로 적는다. `*`·`?`도 못 쓴다(`[^/]+`). 정규식만 따옴표로 감싸면 따옴표까지 전달되어 거부되므로 **명령 전체**를 작은따옴표로 감싼다 |
| `not-permitted` | 내 계정에 그 동작이 없다. 허용된 동작 목록이 같이 나온다. 필요하면 권한자에게 요청한다 |
| `not-announced` | 팀 채널에 알림을 올리고 `--announced`를 붙인다. 문안은 게이트가 만들어 준다 |
| `head-mismatch`(재시작) | 서버 레포 HEAD가 그 SHA가 아니다. 먼저 `deploy-bundle <SHA>`로 HEAD를 옮긴다 |

오류 안내는 게이트가 아는 글만 보여 준다. 받은 명령의 원문은 출력하지도 기록하지도 않는다.

공통 규칙

1. 계정별 허용표에 없는 동작은 거부한다.
2. 잠금 파일이 있으면 `status`·`unlock`·`record-pr`·`autodeploy-pause` 말고는 전부 거부한다(자동 배포를 멈추는 것은 잠금 중에도 되고, 재개는 안 된다).
3. SHA는 16진수 소문자 7~40자만 받고, 서버 레포에 있고 origin에 있고 **배포 기준 브랜치**(정책 `[deploy] allowed_branches`)에 들어간 커밋이어야 한다.
4. 모든 인자는 화이트리스트 정규식으로 검증한다. `eval` 없음, 변수는 항상 따옴표, 제어 문자·비ASCII·셸 기호가 든 명령은 통째로 거부한다.
5. 모든 실행과 거부를 추가 전용 감사 로그에 남긴다. 검증을 통과한 값만 적고 원문 명령은 적지 않는다.
6. 비밀값은 출력·기록하지 않는다. 번들 검사는 변수 이름만 알리고, 배포 스크립트의 출력은 서버의 root 전용 파일로만 보낸다.
7. 정책 값도 형식을 검사한다(경로, 환경변수 `이름=값`, 주소는 이 서버 자신의 것만 등). 형식이 틀리면 실행하지 않는다.

### 배포·백업·롤백 규칙

- 배포 스크립트에 넘기는 환경변수는 게이트가 정책 값으로 고정한다: `<ref_env>=<SHA>`, `[deploy] env`의 항목들, 두 번째 번들에는 `env_b`의 항목들. 요청하는 사람은 하나도 바꿀 수 없다.
- 배포 스크립트가 "앞으로 감기(ff) 병합"만 하는 서버에서는 이전 커밋을 주면 아무 일도 하지 않고 지금 코드를 다시 빌드한다. 그래서 게이트는 지금 서버 HEAD보다 앞선 커밋만 받고, 배포 뒤 HEAD가 그 커밋인지 확인한다. **`deploy-bundle`은 코드 롤백에 쓸 수 없다.**
- 백업 이름 `*bak-before-<커밋 8자>`의 해시는 배포 **대상** 커밋이다. 게이트는 번들 백업과 함께 **직전 배포 해시**를 파일과 감사 로그(`result=prev-head:<해시>`)에 남긴다.
- `rollback-bundle <SHA>`는 그 백업을 풀어 번들 폴더만 되돌리고, 기록해 둔 직전 배포 해시를 알려 준다. 레포 체크아웃을 되돌리는 것은 게이트에 없다.
- 번들 점검: 정책의 표시 문자열(`required_strings`)이 번들에 있어야 하고, 정책이 지정한 env 파일들(`secret_env_files`)의 값(12자 이상)이 번들에 들어 있으면 실패한다. 배포 스크립트가 일부러 번들에 넣는 값은 정책 `bundle_allowed_env_names`에 변수 이름을 적어 예외로 둔다.
- sqlite 파일 백업은 파이썬 `sqlite3` 모듈의 backup API로 한다(sqlite3 명령이 없는 서버도 있다).
- `restart-backend`의 폴더 백업은 결과물이 둘로 나뉜다: `<이름>.bak-before-<커밋 8자>.tgz`(sqlite 파일 `*.db`·`*.db-wal`·`*.db-shm`을 뺀 나머지)와 `<이름>.bak-before-<커밋 8자>-sqlite/`(700 폴더, 폴더 바로 아래 `*.db`를 backup API로 뜬 사본). 쓰는 중인 sqlite 파일을 tar가 읽다 실패하는 것을 막기 위해서다. 되돌릴 때는 둘 다 필요하다. 다만 정책 `backup_sqlite`에 적은 파일은 별도 파일(`<이름>.bak-before-<커밋 8자>`)로만 저장되고 `-sqlite/` 폴더에는 들어가지 않는다(같은 파일을 두 번 저장하지 않는다. `--dry-run`에도 `중복 건너뜀: <이름>` 한 줄이 나온다).
- `restart-backend`의 백업 보관 개수: 정책 `[restart] backup_keep`(2 이상의 정수, **기본은 없음 = 하나도 지우지 않는다**). 적으면 백업이 성공적으로 끝난 뒤, 정책 `backup_dirs`·`backup_sqlite`에 적힌 원본의 게이트 백업 세트(`<이름>.bak-before-<커밋 8자>[.<시각>]`의 `.tgz`·`-sqlite`·sqlite 파일 사본, 점으로 시작하는 숨김 이름 포함)를 같은 백업 폴더 안에서 SHA별 세트 단위로 묶어 최신 N세트만 남기고 지운다. 이번에 만든 세트와 직전 세트는 N과 상관없이 남는다(그래서 최소 2). 이름 패턴이 다른 것, 심볼릭 링크, 번들 백업(`www-*`), `.env` 백업, `deploy-*` 파일, 정책에 없는 원본의 백업은 건드리지 않는다. `--dry-run`은 지울 목록(`보관 정리 예정`)만 보여 주고, 실제로는 삭제할 때마다 `보관 정리: <이름> (<크기>)` 한 줄과 감사 로그 `result=backup-prune:<이름>:<크기>`가 남는다. 삭제 실패는 경고만 하고 재시작은 계속한다. 켜기 전에 이미 쌓인 옛 백업도 이름 패턴이 맞으면 켠 뒤 첫 재시작에서 N개를 넘는 만큼 지워지므로, 켜기 전에 `--dry-run` 목록을 확인한다. `status`에 `백업 보관: N세트, 합계 …` 한 줄이 나온다.
- 번들 교체는 정책 `web_root_parent` 바로 아래 폴더에서만 한다.

### 자동 배포 정지·재개

`lock`은 게이트를 거치는 배포만 막는다. 서버에서 따로 도는 자동 배포는 `lock`을 보지 않는다. 시연이나 수동 작업 동안 자동 배포를 멈추려면 `autodeploy-pause`를 쓴다.

```
autodeploy-pause team-demo 2026-01-02T18:00     # 재개시각을 안 적으면 정책의 기본 시간
autodeploy-resume                               # 먼저 끝났으면
```

- **게이트가 쓰는 것은 파일 하나다**: 정책 `[autodeploy] pause_file`(root 소유 644, 파일 이름은 `autodeploy.pause`로 고정). 자동 배포의 타이머·서비스·스크립트는 건드리지 않는다. root 권한 범위와 sudoers는 그대로다.
- 자동 배포를 돌리는 쪽이 매 주기 맨 앞에서 그 파일을 읽고 건너뛰어야 실제로 멈춘다. 서버 책임자가 **한 번** 연결한다. 판정용 스크립트 `autodeploy-paused.sh`를 같이 둔다(끝 코드 0 = 멈춤, 1 = 안 멈춤. 파일이 없으면 안 멈춤, 읽을 수 없거나 해석할 수 없으면 멈춤). 연결 전에는 이 동작이 파일만 쓰고 자동 배포는 그대로 돈다.
- 재개시각이 지나면 저절로 재개된다(재개를 잊어도 배포가 영영 멈추지 않는다). 한 번에 멈출 수 있는 최대 시간은 정책 `max_hours`다.
- `autodeploy-resume`은 파일을 지우지 않는다. 재개 시각을 지금으로 덮어쓰고 `resumed_by=<계정>`을 남긴다. 게이트에는 지우는 동작이 없다.
- 권한자용이다. 정책 `[permissions]`의 그 계정 줄에 적어야 쓸 수 있고, `_default`에 적으면 게이트가 정책을 통째로 거부한다.
- 잠금 중에는 `autodeploy-pause`만 된다. `autodeploy-resume`은 잠금을 푼 뒤에 한다.
- `status`에 "자동 배포: 정지 중 — 건 사람, 사유, 재개 예정"이 나온다. 감사 로그에 `result=paused:<재개시각>`, `result=resumed`가 남는다.
- 정지는 게이트의 수동 배포(`deploy-bundle`)를 막지 않는다. 둘 다 막으려면 `lock`도 건다.
- 알림(`--announced`)은 필수가 아니다. 서버의 코드·설정을 바꾸지 않기 때문이다. 팀 채널에 한 줄 남기는 것은 권한다.

### 재시작과 서버 코드가 어긋날 때 (head-mismatch)

`restart-backend <SHA>`는 서버 레포 HEAD가 그 SHA일 때만 재시작한다. 재시작은 서버 코드를 옮기지 않는다(옮기는 것은 `deploy-bundle`뿐이다). 다르면 어느 쪽이 앞섰는지 가려 다음에 칠 명령을 그대로 보여 주고 멈춘다.

| 상황 | 게이트가 알려 주는 것 |
| --- | --- |
| 서버 코드가 그 SHA보다 **뒤** | `1) deploy-bundle <SHA> --announced` → `2) restart-backend <SHA> --ack-data-loss --announced` |
| 서버 코드가 그 SHA보다 **앞**(그 커밋은 이미 들어 있다) | `restart-backend <지금 HEAD> --ack-data-loss --announced` |
| 서로 다른 갈래 | 명령을 권하지 않는다. 서버 책임자에게 알린다 |

정책 `[restart] deploy_first = true`(기본 false)면, 서버 코드가 **뒤**인 경우에 한해 그 계정에 `deploy-bundle` 권한도 있을 때 번들 배포를 먼저 하고 이어서 재시작한다. 배포의 검사(앞선 커밋만, 번들 백업, 번들 점검, 배포 뒤 HEAD 확인)는 전부 그대로 돌고, 하나라도 실패하면 재시작하지 않는다. 감사 로그에 `result=deploy-first:<SHA 8자>`가 남는다. 이때 알림 문안은 재시작 것만 나오므로, 켠다면 팀 채널 알림에 "번들 배포 포함"을 같이 적는다.

게이트에 넣지 않은 것(사람이 직접): 코드(레포) 롤백, 권한 정책 변경, 계정 생성·삭제, 방화벽, 비밀값 파일, sudoers, sshd 설정, 외부 서비스 게시, 컨테이너 스택, 정책의 블록 줄과 모양이 다른 location, 읽기용(GET) location.

## 권한 단계(예시)

| 단계 | 누구 | 동작 |
| --- | --- | --- |
| 모두 | 개인 계정이 있는 팀원 전부 | `status`, `deploy-bundle`, `record-pr` |
| 권한자 | 정책에 적힌 소수 | 위 + `nginx-restore`, `nginx-add-location`, `nginx-approve-location`, `restart-backend`, `rollback-bundle`, `lock`, `unlock` |

이렇게 나눈 이유

- nginx 구조 변경은 소수의 권한자가 맡는다.
- 새 쓰기 경로는 기본적으로 둘 이상이 확인하고 반영한다 → 제안과 승인을 다른 사람이 한다. 서버 책임자가 위험을 받아들이고 정책 `[self_approve] accounts`에 적은 계정만 예외로 셀프 승인할 수 있다(아래).
- nginx 변경은 PR로도 남겨 누가 언제 바꿨는지 보이게 한다 → 감사 로그에 PR 칸.
- 바꾸기 전에 팀 채널에 한 줄 알림과 되돌리는 방법을 같이 적는다 → `--announced`, 게이트가 문안을 만든다.
- 자동 배포가 막혔을 때의 수동 배포는 모두가 할 수 있어야 하고 같은 방식으로 기록한다 → `deploy-bundle`은 모두에게.
- 시연 전에 배포를 멈출 스위치가 필요하다 → `lock`.
- 다른 레포가 원본인 설정(예: 컨테이너 안의 게이트웨이 설정)은 서버에서 직접 고치지 않고 그 레포의 PR로 바꾼다 → 게이트 범위 밖.

게이트는 "자동 배포가 막혔는지"를 알지 못한다. 모두에게 `deploy-bundle`을 연 만큼, 배포 기준 브랜치에 들어간 커밋만 받는 규칙과 알림·감사 로그가 통제 수단이다.

## 새 쓰기 경로 열기: 두 사람 확인

1. **제안** (권한자 A): `ssh <계정>@<서버> 'nginx-add-location <이름> POST <정규식>'` — 명령 전체를 작은따옴표로 감싼다. 게이트는 원격 셸을 거치지 않으므로 정규식만 따로 감싼 따옴표는 그대로 전달되어 거부된다.
   - 검증기를 통과해야 하고, 지금 설정에 넣을 수 있는지(삽입 표시 줄, 중복)도 미리 본다.
   - 서버에 승인 대기 파일이 생긴다: `/var/lib/ax-gate/pending/<이름>.req` (root 소유)
   - 출력에 **확인값**(16진수 12자)이 나온다. 이름·메서드·정규식·제안자를 sha256한 값의 앞부분이다.
2. **확인** (권한자 B, A와 다른 계정): `status`로 승인 대기 제안의 메서드·정규식·제안자·확인값을 직접 본다. A가 말로 전한 내용이 아니라 서버가 보여 주는 내용을 본다.
3. **알림**: B가 팀 채널에 알림 한 줄(게이트가 문안을 만들어 준다)을 올린다.
4. **승인·적용** (B): `nginx-approve-location <이름> <확인값> --announced`
   - 확인값이 제안 내용과 다르면(제안이 바뀌었으면) 거부. 제안자 본인이면 거부(단, 정책 `[self_approve] accounts`에 든 계정은 예외, 아래). 만료(기본 24시간)면 거부.
   - 제안자와 승인자 **둘 다** 그 경로 접두 권한이 있어야 한다.
   - 적용 순서: 현재 설정 백업(`<백업 폴더>/pre-gate-add-<이름>-<시각>/` + sha256) → 삽입 → `nginx -t` → reload. `nginx -t`가 실패하면 백업으로 되돌리고 reload하지 않는다.

### 정책으로 지정한 계정만 셀프 승인

정책 `[self_approve]`의 `accounts = ["계정", ...]`에 적은 계정은 자기가 제안한 location을 자기가 승인할 수 있다. 서버 책임자의 명시적 결정이 있을 때만 쓴다.

- 기본값은 빈 목록이다. 구역이 없거나 목록이 비면 지금처럼 제안자 본인의 승인을 거부한다(`self-approval`).
- 목록에 있어도 나머지 검증은 그대로다: 허용 접두와 정규식 검증기, 제안 유효시간(기본 24시간), 확인값(12자) 입력, `--announced`, 백업 → `nginx -t` → reload 순서.
- 셀프 승인으로 적용되면 출력과 journal에 "셀프 승인(정책 허용 계정)"이 나오고 감사 로그 note가 `proposer:<계정>,digest:<확인값>,self-approve:yes`가 된다. 다른 사람이 승인하면 `self-approve:no`다.
- 잘못된 값은 안전한 쪽으로 실패한다: 키가 `accounts`가 아니거나, 값이 문자열 목록이 아니거나, 계정이 형식에 안 맞거나 `[permissions]`에 없으면 정책 로드가 실패해 게이트가 모든 요청을 거부한다. 구역 이름 오타는 구역을 못 읽은 것과 같아 셀프 승인이 거부된다.
- 위험: 목록에 든 계정의 키 하나가 새면 단독으로 쓰기 경로를 열 수 있다(허용 접두·POST 전용·정확한 정규식 안에서만). 목록은 최소로 두고, 계정을 뺄 때는 키 줄과 이 목록을 함께 지운다.

승인 기록 형식: 적용되면 제안 파일이 `/var/lib/ax-gate/approved/<이름>-<시각>.rec`로 옮겨진다.

```
name=card-decision
method=POST
regex=^/example-api/api/items/cards/[^/]+/decision$
proposer=authorized-1
created_epoch=...
created=2026-01-02T10:15:00+0900
digest=3f9a1c0b7e2d
approver=authorized-2
approved=2026-01-02T10:31:12+0900
backup=pre-gate-add-card-decision-20260102-103112
```

감사 로그에도 `note=proposer:<제안자>,digest:<확인값>`과 `result=applied:<백업폴더>`가 남는다. 설정 파일 안의 블록에는 `# ax-gate: name=<이름> user=<제안자> added=<시각>` 주석이 붙는다.

### 검증기가 강제하는 것

만들어지는 블록은 한 가지 꼴뿐이다. 블록 안에 들어가는 지시어 줄은 **정책**(`[location] block_lines`)이 정하고, 요청하는 사람이 정하는 것은 이름·메서드·정규식뿐이다.

```nginx
# ax-gate: name=<이름> user=<제안자> added=<시각>
location ~ <정규식> { <정책의 블록 줄 1> <블록 줄 2> ... }
```

예시 정책이라면:

```nginx
location ~ ^/example-api/api/items/cards/[^/]+/decision$ { limit_except POST { deny all; } rewrite ^/example-api/(.*)$ /$1 break; proxy_pass http://127.0.0.1:8201; include snippets/example-proxy.conf; include snippets/example-auth.conf; }
```

- 정규식: `^/`로 시작하고 `$`로 끝난다(끝까지 고정). 쓸 수 있는 것은 글자·숫자·`_-/`, `\.`, 글자 그대로인 선택지 `(a|b)`, 그리고 한 조각 안에서만 맞는 묶음 `[^/]+` `[0-9]+` `[0-9a-f]+` `[0-9a-f-]+` `[a-z0-9-]+` `[A-Za-z0-9_-]+`뿐이다. `.`, `*`, `?`, `{}`, 중첩 괄호, 다른 역슬래시, 공백·`;`·따옴표는 거부한다.
- 메서드 제한 필수. 정책의 허용 메서드만. GET/HEAD는 받지 않는다.
- 경로는 계정별 허용 접두 안이어야 한다(조각 경계에서만 맞음).
- 블록 줄에는 메서드 제한 한 줄과 `proxy_pass http://127.0.0.1:{port};` 한 줄이 반드시 있어야 한다. 포트는 정책의 접두 → 포트 표에서만 온다. 요청하는 사람은 포트·호스트를 고를 수 없다.
- 블록 줄 밖의 지시어는 한 줄도 넣을 수 없다. 적용 전에 만든 블록을 정책으로 다시 만들어 글자 그대로 비교한다.
- 삽입 위치: 설정 파일에 사람이 한 번 넣어 둔 표시 줄 `# AX-GATE-INSERT-BELOW` 바로 아래. 표시 줄은 읽기용 location보다 앞에 둔다(쓰기 location이 앞이어야 정규식 우선순위가 맞다). 표시 줄이 정확히 한 개가 아니면 거부한다.
- 같은 정규식·같은 이름이 이미 있으면 거부한다.

### 대상 파일이 여럿일 때 (정책 `[nginx_targets]`)

같은 경로를 두 화면(예: 두 번째 포트의 server 블록이 다른 파일에 있을 때)에 같이 열어야 하면, 서버 책임자가 정책에 추가 대상을 적는다.

```toml
[nginx_targets]
site-b = "<두 번째 설정 파일의 전체 경로>"
```

- 이 구역이 없으면 `[paths] nginx_conf` 하나만 다룬다. 동작은 예전과 같다(확인값, 백업 위치, 출력 모두).
- 요청하는 사람은 대상을 고르지 못한다. 제안·승인·복원은 언제나 **대상 전부**에 적용된다.
- 승인 순서: ① 대상 전부에 넣을 수 있는지 사전 검증(여기서 걸리면 백업 폴더도 만들지 않는다) → ② 전부 백업 → ③ 전부 교체 → ④ `nginx -t` 한 번 → ⑤ reload. ③~⑤ 어디서든 실패하면 **이미 바꾼 파일까지 전부** 백업으로 되돌리고 실패로 끝낸다(`nginx-replace-failed`, `nginx-test-failed`, `nginx-reload-failed`). 제안은 승인 대기로 남는다.
- 백업 위치: 기본 대상은 예전과 같은 `<백업폴더>/<파일명>`, 추가 대상은 `<백업폴더>/targets/<이름>/<파일명>`. 각각 `.sha256`이 붙는다.
- `nginx-restore`도 같은 원자성이다. 바꾸기 전에 백업 안의 사본을 전부 확인(체크섬)하고, 대상 전부의 현재 상태를 백업한 뒤 한 번에 교체한다. 추가 대상을 다루기 전에 뜬 옛 백업처럼 그 대상의 사본이 없는 백업은 그 대상을 그대로 두고 그 사실을 출력한다.
- 대상마다 삽입 표시 줄이 정확히 한 개 있어야 한다. 하나라도 없으면 제안 단계에서 거부한다.
- 대상의 기존 location 모양이 다르면 `[nginx_target_block_lines] <이름> = [...]`로 그 대상의 블록 줄을 따로 적는다. 규칙(메서드 제한 한 줄, `proxy_pass http://127.0.0.1:{port};` 한 줄)은 같고 검증기가 대상마다 따로 검사한다.
- 정책 값이 잘못되면(이름 형식, 경로 아님, 같은 파일을 두 번, 없는 대상의 블록 줄) nginx를 바꾸는 동작이 설정 오류(끝 코드 5)로 멈춘다. `status`에 "nginx 대상 파일: 기본, <이름>"이 나온다.
- 운영 사본(`ops_copy_file`)과 `status`의 사본 비교는 기본 대상만 본다. 추가 대상은 적용 뒤 sha256 앞 12자만 출력한다.

### 블록 프로필 (정책 `[location_profiles]`)

타임아웃이나 본문 크기가 기본과 달라야 하는 경로는 프로필 이름을 붙여 제안한다.

```
nginx-add-location <이름> POST <정규식> long-timeout
```

- 프로필의 내용은 정책이 정한다(`long-timeout = ["proxy_read_timeout 300s;", "proxy_send_timeout 300s;"]`). 요청하는 사람은 **이름만** 고른다. 쓸 수 있는 이름은 `status`의 "location 프로필"에 나온다.
- 프로필 줄은 정책의 블록 줄 **뒤에 덧붙는다**. 메서드 제한·`proxy_pass`·include는 프로필로 바꿀 수 없다.
- 프로필에 쓸 수 있는 지시어는 검증기에 고정된 목록뿐이다: `proxy_read_timeout`, `proxy_send_timeout`, `proxy_connect_timeout`, `send_timeout`, `client_body_timeout`(1초~3600초, 단위 `s`·`m`), `client_max_body_size`(1k~1024m, 단위 `k`·`m`, 0=무제한 불가). 줄의 꼴은 `<지시어> <숫자><단위>;` 하나다. 정책에 그 밖의 지시어(`proxy_pass`, `include`, `rewrite`, `add_header` 등)나 한도 밖의 값을 적으면 그 프로필을 쓰는 제안·승인이 거부된다. 블록 줄에 이미 있는 지시어도 넣을 수 없다.
- 프로필 이름은 확인값에 묶인다(제안 파일의 프로필을 바꾸면 확인값이 달라져 승인되지 않는다). 프로필 없이 제안하면 확인값은 예전 공식 그대로다.
- 승인할 때 프로필 내용은 **그 시점의 정책**에서 읽는다. 제안 뒤 정책에서 프로필이 빠지면 승인이 거부된다(`profile-unknown`).
- 적용된 블록의 주석에 `profile=<이름>`이 붙고, 감사 로그 note에 `profile:<이름>`이, `status`의 승인 대기 줄에 "프로필 <이름>"이 나온다.
- 한계: 프로필은 응답을 오래 기다리게 하거나 큰 본문을 받게 한다. 그만큼 그 경로가 자원을 더 쓸 수 있다. 한도(3600초, 1024m)는 검증기에 고정돼 있고, 실제로 열어 둘 값은 정책이 더 좁게 정한다.

## 바꾸기 전 알림(팀 채널)

바꾸는 동작을 `--announced` 없이 실행하면 게이트가 알림 문안을 보여 주고 멈춘다.

```
바꾸기 전에 팀 채널에 아래 한 줄을 올린다. 올린 뒤 같은 명령 끝에 --announced 를 붙인다.
  [server] authorized-1: deploy-bundle a1b2c3d4 를 곧 실행합니다. 되돌리는 방법: rollback-bundle a1b2c3d4
```

그 줄을 팀 채널에 올리고 같은 명령에 `--announced`를 붙여 다시 실행한다. 감사 로그에 `announced=yes`로 남는다. 게이트는 메시지를 보내지 않고, 실제로 올렸는지도 확인하지 못한다(한계 참고).

## nginx 변경을 PR로 남기기

nginx 설정을 바꾼 사람(승인자 또는 복원한 사람)이 한다.

1. 바뀐 설정 파일의 사본을 팀이 정한 곳에 PR로 남긴다. **공개 레포라면 올리기 전에 서버 책임자가 공개 범위를 정한다.** 설정 파일에는 내부 구조가 드러난다.
2. 올리기 전에 비밀값이 없는지 본다.
3. PR 본문에 백업 폴더명(되돌리는 방법)과 제안자·승인자를 적는다.
4. PR 번호를 감사 로그에 남긴다: `record-pr <백업폴더명> <PR번호>`
5. 정책에 `repo_nginx_copy`를 적어 두면 `status`가 실제 설정과 그 사본의 체크섬을 비교해 "일치/어긋남"을 알려 준다.

`deploy-bundle`·`restart-backend`는 이미 머지된 PR의 커밋을 다루므로 `pr=<번호>`를 붙여 실행하면 된다.

## 감사 로그

`/var/log/ax-gate/audit.log` (추가 전용, 탭으로 구분). 같은 줄을 `logger -t ax-gate`로 journal에도 보낸다.

```
2026-01-02T10:31:12+0900	user=authorized-2	action=nginx-approve-location	args=card-decision 3f9a1c0b7e2d	mode=real	announced=yes	pr=-	note=proposer:authorized-1,digest:3f9a1c0b7e2d	layer=root	result=start
```

| 칸 | 뜻 |
| --- | --- |
| 시각 | 서버 시각 |
| `user` | OS 계정(누가). 앞단은 로그인 계정, 뒷단은 `SUDO_USER` |
| `action`, `args` | 동작과 검증을 통과한 인자. 검증 실패면 `args=-` |
| `mode` | `real` 또는 `dry` |
| `announced` | 팀 채널 알림 확인 여부 |
| `pr` | PR 번호(없으면 `-`) |
| `note` | 제안자·확인값(프로필을 썼으면 `profile:<이름>`), `record-pr`의 참조 |
| `layer` | `front`(앞단) 또는 `root`(뒷단) |
| `result` | `start`, `end:rc=<코드>`, `denied:<사유>`, `fail:<사유>`, `proposed`, `applied:<백업폴더>`, `prev-head:<해시>`, `help`, `paused:<재개시각>`, `resumed`, `deploy-first:<SHA 8자>` |

끝 코드: 0 성공, 1 실행 실패, 2 인자·사용법, 3 권한 없음, 4 잠금, 5 설정 오류(신원을 알 수 없을 때 포함).

## 위협 모델 (원칙 수준)

지키려는 것: 서버의 비밀값, 데이터, nginx의 쓰기 경로, 서비스 가용성.

| 위협 | 대응 | 남는 위험 |
| --- | --- | --- |
| 개인 계정으로 셸을 얻으려 함 | 강제 명령 + `restrict` + sshd Match 블록(pty·포워딩 금지), 비밀번호 잠금. 명령은 허용 목록·정규식으로만 해석, `eval` 없음 | sshd·bash·sudo 자체의 결함. 강제 명령에는 로그인 셸이 필요하므로, 강제 명령이 빠진 키 줄 하나가 곧 셸이다 |
| 인자에 셸 기호·경로 탈출을 넣음 | 제어 문자·비ASCII 거부, 토큰별 정규식, `..` 거부, 뒷단 재검증 | 검증 정규식의 실수(테스트로 줄임) |
| 남의 이름으로 실행하려 함 | 앞단은 로그인 계정, 뒷단은 `SUDO_USER`만 믿는다. 요청·환경변수·`command=`에 적은 이름은 쓰지 않는다 | 서버에서 이미 root 권한을 가진 주체는 막을 수 없다 |
| 권한 없는 계정이 동작을 시도 | 앞단·뒷단 모두 허용표 확인, 거부도 감사 로그에 남김 | |
| **키가 샘** | 그 계정의 권한만 열린다. 그 계정의 키 줄을 지우면 끝. `from=`과 방화벽으로 출처 제한 | 지우기 전까지는 그 권한만큼 열려 있다. 권한자 키가 새면 재시작·롤백·잠금을 할 수 있다 |
| 권한자 한 명(또는 샌 키 하나)이 새 쓰기 경로를 엶 | 제안자와 다른 계정의 승인 필수, 확인값으로 내용 고정 | **권한자 키 2개가 같이 새면** 열린다. 정책 `[self_approve]`에 든 계정은 **키 하나로** 열 수 있다(허용 접두·POST 전용·정규식 검증 안에서만, 감사 로그에 `self-approve:yes`) |
| 위험한 location | 검증기: 정책이 정한 블록 줄, 끝까지 고정된 정규식, 접두·포트는 정책이 정함. 프로필은 이름만 고르고 지시어는 타임아웃·본문 크기 허용 목록뿐 | 허용 접두 **안**에서는 새 쓰기 경로가 열린다. 접두를 넓게 잡으면 그만큼 넓다 |
| 설정 파일 여럿 중 일부만 바뀜 | 대상 전부를 사전 검증하고 한 묶음으로 교체, 실패하면 전부 복원 | 되돌리는 복사 자체가 실패하면(디스크 등) 어긋난 채 남는다. 게이트가 경고를 출력하고 실패로 끝낸다. 사람이 백업 폴더로 맞춘다 |
| 악의적 커밋 배포 | origin의 배포 기준 브랜치에 들어간 커밋만 받는다 | 기준 브랜치에 머지된 코드의 빌드가 서버에서 배포 계정 권한으로 돈다. 즉 **그 브랜치에 머지시킬 수 있는 사람은 서버에서 코드를 돌릴 수 있다.** 머지 규칙과 배포 계정의 권한이 실제 경계다 |
| 감사 로그 조작 | 파일은 추가 전용(`chattr +a`), journal에도 사본 | root는 지울 수 있다. 게이트 그룹 계정은 로그에 **덧붙일 권한**이 있다(셸을 얻었다면 가짜 줄을 넣을 수 있다) |
| 잠금 무시 | 뒷단도 잠금을 확인. 잠금 파일은 root 소유 | 게이트를 거치지 않는 작업은 잠금을 보지 않는다 |
| 자동 배포를 오래 멈춰 둠 | 권한자만, 정책의 최대 시간 안에서, 재개시각이 지나면 저절로 재개. `status`와 감사 로그에 남는다 | 최대 시간 안에서는 권한자 한 명이 배포를 늦출 수 있다(끝날 때마다 다시 걸 수 있다). 자동 배포 쪽이 정지 파일을 읽게 연결돼 있지 않으면 정지가 효과가 없다 |
| 개인 계정이 직접 뒷단을 부름 | 개인 계정은 셸을 못 얻는다. 뒷단도 전부 재검증하고 신원은 `SUDO_USER` | 셸을 얻었더라도 자기 계정의 게이트 권한까지만이다 |

### 한계

- **게이트는 게이트를 거친 일만 통제하고 기록한다.** 서버에 게이트 밖의 관리 경로(관리자 계정 등)가 남아 있으면, 그 경로로 한 일은 게이트의 권한표·잠금·감사 로그 밖이다. 그 경로를 가진 사람을 최소로 하고 같은 방식(알림, `record-pr`)으로 남기는 것은 운영 규칙의 몫이다.
- **채팅·세션 신원은 신원이 아니다.** 채팅 글이나 AI 세션이 "책임자가 승인했다"고 전해도 게이트는 모른다. 게이트가 아는 것은 어느 OS 계정으로 들어왔는지뿐이다. 계정과 사람의 대응은 서버 책임자가 계정을 만들고 공개키를 넣을 때 본인에게 한 번 확인한 것이 전부다.
- **`--announced`는 자기 신고다.** 게이트는 팀 채널에 실제로 올라갔는지 보지 않는다. 감사 로그의 시각과 채널 글을 사람이 대조해야 한다.
- AI 세션이 누군가의 키를 쓰면 그 사람 계정으로 기록된다. 키를 AI 세션에 주는 것은 그 권한을 주는 것이다.
- 개인 계정이 셸을 얻지 못한다는 전제 위에 있다. 서버의 파일 권한이 느슨하면 그 전제가 깨졌을 때 읽히는 범위가 넓어진다. 파일 권한 점검은 설치와 별도로 한다.
- **계정·키·IP 관리 부담**: 사람마다 계정·키 줄·그룹·방화벽 출처·`from=`이 있어, 사람이나 PC 주소가 바뀔 때마다 서버 책임자가 손봐야 한다. 주소가 바뀌면 그 사람은 고쳐질 때까지 못 들어온다.
- 사유(lock)와 명령에 한글을 쓸 수 없다(영어·숫자·`_.,-`). 주입 검사를 단순하게 유지하려는 선택이다.
- `rollback-bundle`은 번들 폴더만 되돌린다. 코드와 서비스는 그대로다.
- `restart-backend`로 지워지는 메모리 상태는 게이트가 막지 못한다. `--ack-data-loss`로 알고 한다는 확인만 받는다.
- 실행 중 중복 방지(실행 잠금)는 게이트끼리만 막는다.
- 번들에서 비밀값이 발견되면 게이트는 실패를 알리고 `rollback-bundle`을 권할 뿐 자동으로 되돌리지 않는다.
- nginx 설정을 바꾸는 다른 자동화가 서버에 있으면 게이트의 변경과 겹칠 수 있다. 게이트는 그것을 알지 못한다.

## 새 서버에 설치하기 전에 확인할 것 (일반)

구체 항목과 서버별 값은 비공개 문서에 있다. 새 서버에 설치하거나 새 버전을 올릴 때는 다음을 그 서버에서 확인한다.

- 새 버전은 먼저 `--dry-run`과 `help`·`status`로 돌려 본다(로컬 테스트는 가짜 명령으로 돈다. 아래 "로컬 테스트"의 한계).
- sudo가 `SUDO_USER`·`SUDO_UID`를 넣는지(뒷단 신원 판단의 근거).
- 비밀번호가 잠긴 계정의 공개키 로그인이 되는지(sshd의 PAM 설정에 따라 다르다).
- sshd Match 블록이 다른 계정의 설정을 바꾸지 않는지.
- 방화벽 규칙을 고친 뒤 적용하는 순서와, 재부팅 뒤에도 유지되는지.
- 배포 계정으로 `runuser`를 거쳐 돌 때 빌드 도구가 게이트의 고정 PATH에서 잡히는지.
- 정책의 블록 줄이 서버의 기존 location과 같은 모양인지.
- nginx 복원을 실제로 한 번 해 보기.
- 개인 계정으로 서버의 어떤 파일이 읽히는지.
- 팀원 PC 주소가 고정인지.

## 로컬 테스트

서버·네트워크 없이 돈다. 새 패키지는 없다(파이썬 표준 라이브러리 `unittest` + bash). 값은 전부 가짜다.

```bash
python -m unittest discover -s docs/ops/ssh-gate/tests -v
```

- `tests/test_nginx_location_check.py`: 검증기의 통과·거부 규칙, 정책 블록 줄 검사, 블록 비교, 삽입.
- `tests/test_gateway_allow_check.py`: 허용 목록 검증기(이름 형식, 카드 등급·요청자, 허용 목록 어댑터, 모르는 형식 거부, 파일 읽기: 링크·FIFO·장치·크기 한도).
- `tests/test_ops_gate.py`: 인자 파싱(주입 시도 포함), 신원(이름 위조 시도, `SUDO_USER` 없음), 허용표, 잠금, 알림 확인, 두 사람 승인, 배포 환경변수 고정, DRY_RUN, 감사 로그, 비밀값 비출력, 사용성(help, 플래그 순서, 오류 안내). `systemctl`·`nginx`·`sudo`·`id`·`runuser`·`git`·`curl`·`journalctl`과 배포 스크립트는 임시 폴더의 가짜 명령으로 바꿔 부르고(sqlite 백업은 진짜 sqlite 파일로 시험), 게이트는 `OPS_GATE_TEST_ROOT`로 모든 경로를 임시 폴더로 돌린다.
- 시험 모드(`OPS_GATE_TEST_ROOT`)는 SSH 접속 중이거나 root면 켜지지 않는다(테스트로 확인).
- pytest가 있으면 `pytest docs/ops/ssh-gate/tests`로도 돈다.
- 한계: 이 테스트는 Windows Git Bash에서 가짜 명령으로 돈다. 실제 sshd·sudo·nginx와 맞물리는 부분은 테스트가 보증하지 않으므로, 새 버전을 서버에 올릴 때마다 설치 후 검증(`INSTALL.md` 8절)에서 확인한다. 가짜 `sudo`·`id`가 진짜와 같게 동작한다는 가정(특히 sudo가 `SUDO_USER`를 덮어쓴다는 것)도 거기서 확인한다. CI는 이 테스트를 돌리지 않는다(로컬에서 돌리고 PR 본문에 결과를 적는다). `flock` 경로는 로컬에 flock이 없어 시험하지 못했고, shellcheck도 돌리지 못했다(`bash -n`만 통과).

`DRY_RUN`: 명령 끝에 `--dry-run`을 붙이거나(원격) 환경변수 `DRY_RUN=1`(로컬). 바꾸는 명령은 실행하지 않고 `DRY_RUN: ...`으로 찍는다. 허용표·잠금·SHA 확인은 그대로 한다.
