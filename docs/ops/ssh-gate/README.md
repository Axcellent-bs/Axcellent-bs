# 서버 위임 게이트 (ax-gate) — 초안

> 상태: **초안, 설치 전.** 이 폴더에는 일반 구현(스크립트·검증기·테스트)과 설계 문서만 있다. 대상 서버에는 아무것도 설치하지 않았다.
>
> **구체 서버 값은 비공개 정책 파일에서 읽는다.** 서버의 경로, 서비스 구성, 주소, 계정 이름, 실제 설치 명령은 이 레포에 없다. 여기 나오는 값(`example-api`, `8201`, `authorized-1` 등)은 전부 가짜 예시다.

서버 책임자가 직접 못 치는 시간에도, 팀원이 **자기 계정으로 직접** 서버 작업을 요청·실행하게 하는 장치다.

## 파일

| 파일 | 설명 |
| --- | --- |
| `ops-gate.sh` | 게이트 본체(bash, 엄격 모드). 서버에는 `/usr/local/sbin/ax-gate`로 둔다 |
| `nginx_location_check.py` | nginx location 검증기(파이썬 표준 라이브러리만). 서버에는 `/usr/local/sbin/ax-gate-location-check` |
| `policy.example.toml` | 정책 예시(가짜 값·자리표시자): 계정 → 허용 동작, 경로 접두, location 블록 줄, 잠금·배포·재시작 설정, 경로 |
| `INSTALL.md` | 설치 절차의 일반 형태와 설치 후 검증 체크리스트 |
| `ANNOUNCE.md` | 팀 안내문 초안 |
| `tests/` | 서버 없이 도는 로컬 테스트 |

## 구조

```
팀원 PC ──ssh(자기 키)──▶ sshd ──▶ 그 사람의 개인 계정 (셸 못 씀, 강제 명령)
                                    │  authorized_keys 줄:
                                    │  restrict,from="<허용 출처 IP>",command="/usr/local/sbin/ax-gate <계정>" <공개키>
                                    ▼
                         앞단 ax-gate <계정>            (그 사람 계정 권한)
                           신원 = 실제 로그인 계정(id -un). command= 의 이름은 같은지 확인만
                           SSH_ORIGINAL_COMMAND 를 허용 목록으로만 해석
                           계정별 허용표 · 잠금 · 팀 채널 알림 확인
                                    │  요청을 표준 입력으로 (인자 없음, 이름 없음)
                                    ▼
                         뒷단 sudo -n ax-gate            (root)
                           신원 = sudo 가 넣어 준 SUDO_USER 만 믿는다
                           요청을 처음부터 다시 검증 → 실행 → 감사 로그
```

- **신원은 OS 계정이다.** 팀원마다 서버에 개인 계정을 만든다(공유 계정 없음). 정책 표와 감사 로그가 계정 단위다. SSH 키에 붙인 이름이나 요청에 적힌 이름은 신원이 아니다.
  - 앞단은 `id -un`(실제 로그인 계정)을 쓴다. `command=`에 적힌 계정명이 로그인 계정과 다르면 설정 오류로 거부한다.
  - 뒷단은 `SUDO_USER`만 믿는다. sudo가 직접 넣는 값이라 부르는 쪽이 바꿀 수 없다. `SUDO_USER`가 없거나 root이거나 `SUDO_UID`와 맞지 않으면 실행하지 않는다. 요청(표준 입력)에는 이름 칸이 없고, 이름을 적어 보내면 형식 오류로 거부된다.
- **권한은 정책 파일의 표다.** `계정 → 허용 동작`. 정책 파일은 root만 바꾼다.
- **앞단과 뒷단은 같은 파일이다.** 인자가 하나(계정명)면 앞단, 없으면 뒷단이다. sudoers는 게이트 그룹에 인자 없는 호출 한 줄만 허용한다. 뒷단은 앞단을 믿지 않고 허용표·인자·잠금·알림 확인을 전부 다시 본다.
- **서버마다 다른 것은 전부 정책에 있다.** 경로, 서비스 이름, health 주소 목록, 배포 스크립트에 넘기는 환경변수, location 블록의 모양, 접두 → 포트 표. 스크립트와 검증기에는 특정 서버의 값이 없다.
- 실제 작업은 뒷단(root)이 하고, 배포 스크립트와 git은 `runuser`로 정책의 배포 계정 권한에서 돌린다(root로 빌드하지 않는다).
- 접속 경로는 두 겹으로 한다. 방화벽이 허용 출처에서 오는 SSH만 받고, authorized_keys의 `from=`이 그 계정의 키를 그 출처에서만 받는다.

## 동작

| 동작 | 하는 일 | 알림 확인 |
| --- | --- | --- |
| `status` | 읽기 전용 점검: 잠금, 정책의 health 주소 목록, 확인 주소들의 응답 코드, 서비스 상태와 최근 로그의 오류 줄 수, 번들의 표시 문자열·비밀값, nginx 사본 비교, 승인 대기 제안 | |
| `lock <사유> [해제시각]` / `unlock` | 배포 금지 잠금 파일. 시연 전 배포를 멈추는 스위치 | |
| `nginx-restore <백업폴더명>` | 백업 폴더의 설정으로 되돌림. 먼저 현재 설정을 백업, `nginx -t` 실패면 원래대로 | 필수 |
| `nginx-add-location <이름> <메서드> <정규식>` | 새 쓰기 경로 **제안**. 검증기만 돌리고 승인 대기 파일을 만든다. nginx는 안 바뀐다 | |
| `nginx-approve-location <이름> <확인값>` | 제안자와 **다른** 권한자가 승인하면 그때 적용: 백업 → 삽입 → `nginx -t` → reload | 필수 |
| `deploy-bundle <SHA>` | 번들 배포(배포 스크립트를 배포 계정으로 실행). 지금 서버 코드보다 **앞선** 커밋만. 번들 백업, 직전 배포 해시 기록, 번들 점검 | 필수 |
| `restart-backend <SHA> --ack-data-loss` | 정책의 파일들을 백업한 뒤 서비스 재시작, health가 전부 뜰 때까지 폴링 | 필수 |
| `rollback-bundle <SHA>` | 그 SHA를 배포하기 직전의 번들 백업으로 되돌림. 코드(레포)는 그대로 | 필수 |
| `record-pr <참조> <PR번호>` | 감사 로그에 "이 작업 ↔ 이 PR"을 남김 | |

맨 끝에 붙이는 것(순서 무관): `--dry-run`(할 일만 보여 줌), `--announced`(팀 채널 알림을 올렸다는 확인), `pr=<번호>`(감사 로그의 PR 칸).

공통 규칙

1. 계정별 허용표에 없는 동작은 거부한다.
2. 잠금 파일이 있으면 `status`·`unlock`·`record-pr` 말고는 전부 거부한다.
3. SHA는 16진수 소문자 7~40자만 받고, 서버 레포에 있고 origin에 있고 **배포 기준 브랜치**(정책 `[deploy] allowed_branches`)에 들어간 커밋이어야 한다.
4. 모든 인자는 화이트리스트 정규식으로 검증한다. `eval` 없음, 변수는 항상 따옴표, 제어 문자·비ASCII·셸 기호가 든 명령은 통째로 거부한다.
5. 모든 실행과 거부를 추가 전용 감사 로그에 남긴다. 검증을 통과한 값만 적고 원문 명령은 적지 않는다.
6. 비밀값은 출력·기록하지 않는다. 번들 검사는 변수 이름만 알리고, 배포 스크립트의 출력은 서버의 root 전용 파일로만 보낸다.
7. 정책 값도 형식을 검사한다(경로, 환경변수 `이름=값`, 주소는 이 서버 자신의 것만 등). 형식이 틀리면 실행하지 않는다.

### 배포·백업·롤백 규칙

- 배포 스크립트에 넘기는 환경변수는 게이트가 정책 값으로 고정한다: `<ref_env>=<SHA>`, `[deploy] env`의 항목들, 두 번째 번들에는 `env_b`의 항목들. 요청하는 사람은 하나도 바꿀 수 없다.
- 배포 스크립트가 "앞으로 감기(ff) 병합"만 하는 서버에서는 이전 커밋을 주면 아무 일도 하지 않고 지금 코드를 다시 빌드한다. 그래서 게이트는 지금 서버 HEAD보다 앞선 커밋만 받고, 배포 뒤 HEAD가 그 커밋인지 확인한다. **`deploy-bundle`은 코드 롤백에 쓸 수 없다.**
- 백업 이름 `*bak-before-<커밋 8자>`의 해시는 배포 **대상** 커밋이다. 게이트는 번들 백업과 함께 **직전 배포 해시**를 파일과 감사 로그(`result=prev-head:<해시>`)에 남긴다.
- `rollback-bundle <SHA>`는 그 백업을 풀어 번들 폴더만 되돌리고, 기록해 둔 직전 배포 해시를 알려 준다. 레포 체크아웃을 되돌리는 것은 게이트에 없다.
- 번들 점검: 정책의 표시 문자열(`required_strings`)이 번들에 있어야 하고, 정책이 지정한 env 파일들(`secret_env_files`)의 값(12자 이상)이 번들에 들어 있으면 실패한다. 배포 스크립트가 일부러 번들에 넣는 값은 정책 `bundle_allowed_env_names`에 변수 이름을 적어 예외로 둔다.
- sqlite 파일 백업은 파이썬 `sqlite3` 모듈의 backup API로 한다(sqlite3 명령이 없는 서버도 있다).
- 번들 교체는 정책 `web_root_parent` 바로 아래 폴더에서만 한다.

게이트에 넣지 않은 것(사람이 직접): 코드(레포) 롤백, 권한 정책 변경, 계정 생성·삭제, 방화벽, 비밀값 파일, sudoers, sshd 설정, 외부 서비스 게시, 컨테이너 스택, 정책의 블록 줄과 모양이 다른 location, 읽기용(GET) location.

## 권한 단계(예시)

| 단계 | 누구 | 동작 |
| --- | --- | --- |
| 모두 | 개인 계정이 있는 팀원 전부 | `status`, `deploy-bundle`, `record-pr` |
| 권한자 | 정책에 적힌 소수 | 위 + `nginx-restore`, `nginx-add-location`, `nginx-approve-location`, `restart-backend`, `rollback-bundle`, `lock`, `unlock` |

이렇게 나눈 이유

- nginx 구조 변경은 소수의 권한자가 맡는다.
- 새 쓰기 경로는 반드시 둘 이상이 확인하고 반영한다 → 제안과 승인을 다른 사람이 한다.
- nginx 변경은 PR로도 남겨 누가 언제 바꿨는지 보이게 한다 → 감사 로그에 PR 칸.
- 바꾸기 전에 팀 채널에 한 줄 알림과 되돌리는 방법을 같이 적는다 → `--announced`, 게이트가 문안을 만든다.
- 자동 배포가 막혔을 때의 수동 배포는 모두가 할 수 있어야 하고 같은 방식으로 기록한다 → `deploy-bundle`은 모두에게.
- 시연 전에 배포를 멈출 스위치가 필요하다 → `lock`.
- 다른 레포가 원본인 설정(예: 컨테이너 안의 게이트웨이 설정)은 서버에서 직접 고치지 않고 그 레포의 PR로 바꾼다 → 게이트 범위 밖.

게이트는 "자동 배포가 막혔는지"를 알지 못한다. 모두에게 `deploy-bundle`을 연 만큼, 배포 기준 브랜치에 들어간 커밋만 받는 규칙과 알림·감사 로그가 통제 수단이다.

## 새 쓰기 경로 열기: 두 사람 확인

1. **제안** (권한자 A): `ssh <계정>@<서버> 'nginx-add-location <이름> POST <정규식>'` — 명령 전체를 작은따옴표로 감싼다. 게이트는 원격 셸을 거치지 않으므로 정규식만 따로 감싼 따옴표는 그대로 전달되어 거부된다.
   - 검증기를 통과해야 하고, 지금 설정에 넣을 수 있는지(삽입 표시 줄, 중복)도 미리 본다.
   - 서버에 승인 대기 파일이 생긴다: `/var/lib/ax-gate/pending/<이름>.req` (root 소유)
   - 출력에 **확인값**(16진수 12자)이 나온다. 이름·메서드·정규식·제안자를 sha256한 값의 앞부분이다.
2. **확인** (권한자 B, A와 다른 계정): `status`로 승인 대기 제안의 메서드·정규식·제안자·확인값을 직접 본다. A가 말로 전한 내용이 아니라 서버가 보여 주는 내용을 본다.
3. **알림**: B가 팀 채널에 알림 한 줄(게이트가 문안을 만들어 준다)을 올린다.
4. **승인·적용** (B): `nginx-approve-location <이름> <확인값> --announced`
   - 확인값이 제안 내용과 다르면(제안이 바뀌었으면) 거부. 제안자 본인이면 거부. 만료(기본 24시간)면 거부.
   - 제안자와 승인자 **둘 다** 그 경로 접두 권한이 있어야 한다.
   - 적용 순서: 현재 설정 백업(`<백업 폴더>/pre-gate-add-<이름>-<시각>/` + sha256) → 삽입 → `nginx -t` → reload. `nginx -t`가 실패하면 백업으로 되돌리고 reload하지 않는다.

승인 기록 형식: 적용되면 제안 파일이 `/var/lib/ax-gate/approved/<이름>-<시각>.rec`로 옮겨진다.

```
name=card-decision
method=POST
regex=^/example-api/api/items/cards/[^/]+/decision$
proposer=authorized-1
created_epoch=...
created=2026-01-02T10:15:00+0900
digest=3f9a1c0b7e2d
approver=authorized-2
approved=2026-01-02T10:31:12+0900
backup=pre-gate-add-card-decision-20260102-103112
```

감사 로그에도 `note=proposer:<제안자>,digest:<확인값>`과 `result=applied:<백업폴더>`가 남는다. 설정 파일 안의 블록에는 `# ax-gate: name=<이름> user=<제안자> added=<시각>` 주석이 붙는다.

### 검증기가 강제하는 것

만들어지는 블록은 한 가지 꼴뿐이다. 블록 안에 들어가는 지시어 줄은 **정책**(`[location] block_lines`)이 정하고, 요청하는 사람이 정하는 것은 이름·메서드·정규식뿐이다.

```nginx
# ax-gate: name=<이름> user=<제안자> added=<시각>
location ~ <정규식> { <정책의 블록 줄 1> <블록 줄 2> ... }
```

예시 정책이라면:

```nginx
location ~ ^/example-api/api/items/cards/[^/]+/decision$ { limit_except POST { deny all; } rewrite ^/example-api/(.*)$ /$1 break; proxy_pass http://127.0.0.1:8201; include snippets/example-proxy.conf; include snippets/example-auth.conf; }
```

- 정규식: `^/`로 시작하고 `$`로 끝난다(끝까지 고정). 쓸 수 있는 것은 글자·숫자·`_-/`, `\.`, 글자 그대로인 선택지 `(a|b)`, 그리고 한 조각 안에서만 맞는 묶음 `[^/]+` `[0-9]+` `[0-9a-f]+` `[0-9a-f-]+` `[a-z0-9-]+` `[A-Za-z0-9_-]+`뿐이다. `.`, `*`, `?`, `{}`, 중첩 괄호, 다른 역슬래시, 공백·`;`·따옴표는 거부한다.
- 메서드 제한 필수. 정책의 허용 메서드만. GET/HEAD는 받지 않는다.
- 경로는 계정별 허용 접두 안이어야 한다(조각 경계에서만 맞음).
- 블록 줄에는 메서드 제한 한 줄과 `proxy_pass http://127.0.0.1:{port};` 한 줄이 반드시 있어야 한다. 포트는 정책의 접두 → 포트 표에서만 온다. 요청하는 사람은 포트·호스트를 고를 수 없다.
- 블록 줄 밖의 지시어는 한 줄도 넣을 수 없다. 적용 전에 만든 블록을 정책으로 다시 만들어 글자 그대로 비교한다.
- 삽입 위치: 설정 파일에 사람이 한 번 넣어 둔 표시 줄 `# AX-GATE-INSERT-BELOW` 바로 아래. 표시 줄은 읽기용 location보다 앞에 둔다(쓰기 location이 앞이어야 정규식 우선순위가 맞다). 표시 줄이 정확히 한 개가 아니면 거부한다.
- 같은 정규식·같은 이름이 이미 있으면 거부한다.

## 바꾸기 전 알림(팀 채널)

바꾸는 동작을 `--announced` 없이 실행하면 게이트가 알림 문안을 보여 주고 멈춘다.

```
바꾸기 전에 팀 채널에 아래 한 줄을 올린다. 올린 뒤 같은 명령 끝에 --announced 를 붙인다.
  [server] authorized-1: deploy-bundle a1b2c3d4 를 곧 실행합니다. 되돌리는 방법: rollback-bundle a1b2c3d4
```

그 줄을 팀 채널에 올리고 같은 명령에 `--announced`를 붙여 다시 실행한다. 감사 로그에 `announced=yes`로 남는다. 게이트는 메시지를 보내지 않고, 실제로 올렸는지도 확인하지 못한다(한계 참고).

## nginx 변경을 PR로 남기기

nginx 설정을 바꾼 사람(승인자 또는 복원한 사람)이 한다.

1. 바뀐 설정 파일의 사본을 팀이 정한 곳에 PR로 남긴다. **공개 레포라면 올리기 전에 서버 책임자가 공개 범위를 정한다.** 설정 파일에는 내부 구조가 드러난다.
2. 올리기 전에 비밀값이 없는지 본다.
3. PR 본문에 백업 폴더명(되돌리는 방법)과 제안자·승인자를 적는다.
4. PR 번호를 감사 로그에 남긴다: `record-pr <백업폴더명> <PR번호>`
5. 정책에 `repo_nginx_copy`를 적어 두면 `status`가 실제 설정과 그 사본의 체크섬을 비교해 "일치/어긋남"을 알려 준다.

`deploy-bundle`·`restart-backend`는 이미 머지된 PR의 커밋을 다루므로 `pr=<번호>`를 붙여 실행하면 된다.

## 감사 로그

`/var/log/ax-gate/audit.log` (추가 전용, 탭으로 구분). 같은 줄을 `logger -t ax-gate`로 journal에도 보낸다.

```
2026-01-02T10:31:12+0900	user=authorized-2	action=nginx-approve-location	args=card-decision 3f9a1c0b7e2d	mode=real	announced=yes	pr=-	note=proposer:authorized-1,digest:3f9a1c0b7e2d	layer=root	result=start
```

| 칸 | 뜻 |
| --- | --- |
| 시각 | 서버 시각 |
| `user` | OS 계정(누가). 앞단은 로그인 계정, 뒷단은 `SUDO_USER` |
| `action`, `args` | 동작과 검증을 통과한 인자. 검증 실패면 `args=-` |
| `mode` | `real` 또는 `dry` |
| `announced` | 팀 채널 알림 확인 여부 |
| `pr` | PR 번호(없으면 `-`) |
| `note` | 제안자·확인값, `record-pr`의 참조 |
| `layer` | `front`(앞단) 또는 `root`(뒷단) |
| `result` | `start`, `end:rc=<코드>`, `denied:<사유>`, `fail:<사유>`, `proposed`, `applied:<백업폴더>`, `prev-head:<해시>` |

끝 코드: 0 성공, 1 실행 실패, 2 인자·사용법, 3 권한 없음, 4 잠금, 5 설정 오류(신원을 알 수 없을 때 포함).

## 위협 모델 (원칙 수준)

지키려는 것: 서버의 비밀값, 데이터, nginx의 쓰기 경로, 서비스 가용성.

| 위협 | 대응 | 남는 위험 |
| --- | --- | --- |
| 개인 계정으로 셸을 얻으려 함 | 강제 명령 + `restrict` + sshd Match 블록(pty·포워딩 금지), 비밀번호 잠금. 명령은 허용 목록·정규식으로만 해석, `eval` 없음 | sshd·bash·sudo 자체의 결함. 강제 명령에는 로그인 셸이 필요하므로, 강제 명령이 빠진 키 줄 하나가 곧 셸이다 |
| 인자에 셸 기호·경로 탈출을 넣음 | 제어 문자·비ASCII 거부, 토큰별 정규식, `..` 거부, 뒷단 재검증 | 검증 정규식의 실수(테스트로 줄임) |
| 남의 이름으로 실행하려 함 | 앞단은 로그인 계정, 뒷단은 `SUDO_USER`만 믿는다. 요청·환경변수·`command=`에 적은 이름은 쓰지 않는다 | 서버에서 이미 root 권한을 가진 주체는 막을 수 없다 |
| 권한 없는 계정이 동작을 시도 | 앞단·뒷단 모두 허용표 확인, 거부도 감사 로그에 남김 | |
| **키가 샘** | 그 계정의 권한만 열린다. 그 계정의 키 줄을 지우면 끝. `from=`과 방화벽으로 출처 제한 | 지우기 전까지는 그 권한만큼 열려 있다. 권한자 키가 새면 재시작·롤백·잠금을 할 수 있다 |
| 권한자 한 명(또는 샌 키 하나)이 새 쓰기 경로를 엶 | 제안자와 다른 계정의 승인 필수, 확인값으로 내용 고정 | **권한자 키 2개가 같이 새면** 열린다 |
| 위험한 location | 검증기: 정책이 정한 블록 줄, 끝까지 고정된 정규식, 접두·포트는 정책이 정함 | 허용 접두 **안**에서는 새 쓰기 경로가 열린다. 접두를 넓게 잡으면 그만큼 넓다 |
| 악의적 커밋 배포 | origin의 배포 기준 브랜치에 들어간 커밋만 받는다 | 기준 브랜치에 머지된 코드의 빌드가 서버에서 배포 계정 권한으로 돈다. 즉 **그 브랜치에 머지시킬 수 있는 사람은 서버에서 코드를 돌릴 수 있다.** 머지 규칙과 배포 계정의 권한이 실제 경계다 |
| 감사 로그 조작 | 파일은 추가 전용(`chattr +a`), journal에도 사본 | root는 지울 수 있다. 게이트 그룹 계정은 로그에 **덧붙일 권한**이 있다(셸을 얻었다면 가짜 줄을 넣을 수 있다) |
| 잠금 무시 | 뒷단도 잠금을 확인. 잠금 파일은 root 소유 | 게이트를 거치지 않는 작업은 잠금을 보지 않는다 |
| 개인 계정이 직접 뒷단을 부름 | 개인 계정은 셸을 못 얻는다. 뒷단도 전부 재검증하고 신원은 `SUDO_USER` | 셸을 얻었더라도 자기 계정의 게이트 권한까지만이다 |

### 한계

- **게이트는 게이트를 거친 일만 통제하고 기록한다.** 서버에 게이트 밖의 관리 경로(관리자 계정 등)가 남아 있으면, 그 경로로 한 일은 게이트의 권한표·잠금·감사 로그 밖이다. 그 경로를 가진 사람을 최소로 하고 같은 방식(알림, `record-pr`)으로 남기는 것은 운영 규칙의 몫이다.
- **채팅·세션 신원은 신원이 아니다.** 채팅 글이나 AI 세션이 "책임자가 승인했다"고 전해도 게이트는 모른다. 게이트가 아는 것은 어느 OS 계정으로 들어왔는지뿐이다. 계정과 사람의 대응은 서버 책임자가 계정을 만들고 공개키를 넣을 때 본인에게 한 번 확인한 것이 전부다.
- **`--announced`는 자기 신고다.** 게이트는 팀 채널에 실제로 올라갔는지 보지 않는다. 감사 로그의 시각과 채널 글을 사람이 대조해야 한다.
- AI 세션이 누군가의 키를 쓰면 그 사람 계정으로 기록된다. 키를 AI 세션에 주는 것은 그 권한을 주는 것이다.
- 개인 계정이 셸을 얻지 못한다는 전제 위에 있다. 서버의 파일 권한이 느슨하면 그 전제가 깨졌을 때 읽히는 범위가 넓어진다. 파일 권한 점검은 설치와 별도로 한다.
- **계정·키·IP 관리 부담**: 사람마다 계정·키 줄·그룹·방화벽 출처·`from=`이 있어, 사람이나 PC 주소가 바뀔 때마다 서버 책임자가 손봐야 한다. 주소가 바뀌면 그 사람은 고쳐질 때까지 못 들어온다.
- 사유(lock)와 명령에 한글을 쓸 수 없다(영어·숫자·`_.,-`). 주입 검사를 단순하게 유지하려는 선택이다.
- `rollback-bundle`은 번들 폴더만 되돌린다. 코드와 서비스는 그대로다.
- `restart-backend`로 지워지는 메모리 상태는 게이트가 막지 못한다. `--ack-data-loss`로 알고 한다는 확인만 받는다.
- 실행 중 중복 방지(실행 잠금)는 게이트끼리만 막는다.
- 번들에서 비밀값이 발견되면 게이트는 실패를 알리고 `rollback-bundle`을 권할 뿐 자동으로 되돌리지 않는다.
- nginx 설정을 바꾸는 다른 자동화가 서버에 있으면 게이트의 변경과 겹칠 수 있다. 게이트는 그것을 알지 못한다.

## 설치 전에 확인할 것 (일반)

구체 항목과 서버별 값은 비공개 문서에 있다. 일반적으로는 다음을 실제 서버에서 확인해야 한다.

- 게이트를 리눅스에서 실행해 보기(지금까지 실행한 적이 없다. 아래 "로컬 테스트"의 한계).
- sudo가 `SUDO_USER`·`SUDO_UID`를 넣는지(뒷단 신원 판단의 근거).
- 비밀번호가 잠긴 계정의 공개키 로그인이 되는지(sshd의 PAM 설정에 따라 다르다).
- sshd Match 블록이 다른 계정의 설정을 바꾸지 않는지.
- 방화벽 규칙을 고친 뒤 적용하는 순서와, 재부팅 뒤에도 유지되는지.
- 배포 계정으로 `runuser`를 거쳐 돌 때 빌드 도구가 게이트의 고정 PATH에서 잡히는지.
- 정책의 블록 줄이 서버의 기존 location과 같은 모양인지.
- nginx 복원을 실제로 한 번 해 보기.
- 개인 계정으로 서버의 어떤 파일이 읽히는지.
- 팀원 PC 주소가 고정인지.

## 로컬 테스트

서버·네트워크 없이 돈다. 새 패키지는 없다(파이썬 표준 라이브러리 `unittest` + bash). 값은 전부 가짜다.

```bash
python -m unittest discover -s docs/ops/ssh-gate/tests -v
```

- `tests/test_nginx_location_check.py`: 검증기의 통과·거부 규칙, 정책 블록 줄 검사, 블록 비교, 삽입.
- `tests/test_ops_gate.py`: 인자 파싱(주입 시도 포함), 신원(이름 위조 시도, `SUDO_USER` 없음), 허용표, 잠금, 알림 확인, 두 사람 승인, 배포 환경변수 고정, DRY_RUN, 감사 로그, 비밀값 비출력. `systemctl`·`nginx`·`sudo`·`id`·`runuser`·`git`·`curl`·`journalctl`과 배포 스크립트는 임시 폴더의 가짜 명령으로 바꿔 부르고(sqlite 백업은 진짜 sqlite 파일로 시험), 게이트는 `OPS_GATE_TEST_ROOT`로 모든 경로를 임시 폴더로 돌린다.
- 시험 모드(`OPS_GATE_TEST_ROOT`)는 SSH 접속 중이거나 root면 켜지지 않는다(테스트로 확인).
- pytest가 있으면 `pytest docs/ops/ssh-gate/tests`로도 돈다.
- 한계: 지금까지 Windows Git Bash에서만 돌렸다. 리눅스·실제 sshd·sudo·nginx에서는 돌려 보지 않았다. 가짜 `sudo`·`id`가 진짜와 같게 동작한다는 가정(특히 sudo가 `SUDO_USER`를 덮어쓴다는 것)은 설치 후 검증에서 실제로 확인해야 한다. `flock` 경로는 로컬에 flock이 없어 시험하지 못했고, shellcheck도 돌리지 못했다(`bash -n`만 통과).

`DRY_RUN`: 명령 끝에 `--dry-run`을 붙이거나(원격) 환경변수 `DRY_RUN=1`(로컬). 바꾸는 명령은 실행하지 않고 `DRY_RUN: ...`으로 찍는다. 허용표·잠금·SHA 확인은 그대로 한다.
