# 문의·클레임 접수: 저장 → AXcellent가 읽어 오기 (설계)

예진 님 제안(2026-11-10~11): 판매 서버가 고객지원을 직접 부르지 않고, 접수를 자기 서버에 저장해 두면
AXcellent가 정해진 간격으로 읽어 간다. 실제 고객사 기준에서 경계를 맞추기 위해서다.

## 왜
- 고객사가 우리 주소·토큰을 들고 우리 규격으로 보내 줘야 하는 방식은 실제 고객사에 없다.
- 중간이 끊기면 사이트는 "접수됨"인데 우리 쪽엔 아무것도 없이 조용히 사라진다.

## 문의 (구현함)
- `POST /api/shop/inquiries` → 판매 서버 `inquiry_inbox`에 저장, 접수 번호 반환.
- 고객지원이 `GET /api/shop/admin/inquiries`로 읽어 `create_inquiry`로 처리하고
  `POST …/{seq}/synced`로 알린다. 멱등 키 `shop-inquiry:<번호>`.

## 클레임 (취소·반품·교환): 같은 방식
달라지는 점은 **판정 결과를 고객에게 어떻게 보여 주느냐**다. 지금은 접수하는 순간 고객지원이 판정해
고객 화면에 바로 보여 준다. 읽어 오는 방식에서는 "접수됨 → 나중에 처리"가 된다.

1. 접수: `POST /api/shop/claims`는 주문·구매자·형식만 확인하고 `claim_inbox`에 저장한다.
   응답은 `{id, status: "received", order_id, type, reason, created_at}`뿐이다(판정·환불액 없음).
   같은 구매자·주문·종류·사유·품목·설명의 중복 접수는 한 건이다.
2. 읽기: 고객지원이 `GET /api/shop/admin/claims`(support·admin만)로 새 접수를 읽어
   `create_claim`으로 판정한다. 멱등 키 `shop-claim:<번호>`. 판정은 지금과 같은 규칙·사람 확인이다.
3. 결과 되돌려 쓰기: 처리한 뒤 `POST /api/shop/admin/claims/{seq}/result`로 결과(고객이 보던 클레임
   모양 그대로)를 판매 서버에 적는다. 고객 화면은 판매 서버에서만 읽는다(`GET /api/shop/claims`).
   판매 서버가 고객지원을 부르지 않는 경계가 유지된다. 고객지원이 판매 서버에 환불을 적는 것
   (`POST /payments/{id}/refund`)과 같은 방향이다.
4. 상태 갱신: 사람 확인·입고·환불로 클레임 상태가 바뀌면 고객지원이 읽기 주기마다 아직 끝나지 않은
   클레임을 다시 적는다(바뀐 것만).
5. 못 읽으면: `inquiry_pull_status`가 문의와 같이 "연결 끊김"과 남은 접수 수를 보여 준다.

### 고객 화면(ax-frontend)
- 신청 창: 결과 대신 "신청이 접수되었습니다 (#번호). 처리 결과는 주문 상세에서 확인할 수 있어요".
- 주문 상세: `GET /api/shop/claims?buyer_id=&order_id=`로 접수 목록을 읽어 "접수됨 → 처리 중 → 결과"를
  보여 준다. 결과가 오기 전에는 판정·환불액을 지어내지 않는다.

### 바뀌지 않는 것
- 판정 규칙, 사람 확인, 보상 큐, 환불(고객지원 → 판매 서버 `refund`), 결제 전 주문 취소(판매 서버가 자체 처리).
- 입고 처리(`return-received`)는 이번 범위 밖이다(운영자가 판매 서버를 거쳐 고객지원을 부르는 시연용 경로).
  실제 고객사처럼 하려면 입고를 판매 서버에 기록하고 고객지원이 읽어 가게 바꾼다(후속).

### 한계·결정이 필요한 것
- 읽는 간격(기본 10초)과 판정 시간만큼 결과가 늦게 보인다.
- 되돌려 쓰기가 가능한 고객사만 고객 화면에 결과가 나온다. 불가능한 고객사는 고객에게 "접수됨"까지만
  보이고 결과는 그 회사의 상담 도구가 안내한다(우리 상담 화면은 그대로).
- 되돌려 쓰는 값(판정·환불액)이 판매 서버 저장소에 남는다. 보관기간·삭제는 판매 서버 기준이다.

## 단계
1. 판매 서버: `claim_inbox`, 접수 저장, 읽기·결과 쓰기 경로, 고객용 목록. (이 브랜치)
2. 고객지원: 읽기 루프에 클레임 접수·상태 갱신 추가, 상태 skill에 클레임 수.
3. 쇼핑몰 화면(ax-frontend): 신청 창·주문 상세.
4. 입고 처리 읽어 가기(후속).
